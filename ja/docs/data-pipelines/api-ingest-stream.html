DatadogのログインストグーションAPIを使用してイベントを取り込む

このエンドポイントは、構造化データおよび半構造化データの高スループットかつリアルタイムでのインストグーションをサポートします。

このAPIでサポートされている操作： 半構造化されたJSONペイロード。

開始する前に：​

  • Datadog Agentをインストールすることなく、クラウドアプリから直接ログを送信する。
  • 入力データに対して、Grok Parser、Remapper、Lookup Processorなどのパイプライン処理ツールを適用する。
  • コンテンツに基づいて、ルートログをインデックス、アーカイブ、またはアラート先に送信する。
  • このエンドポイントをサンプリング処理やフィルタリングルールと組み合わせることで、インデックス作成のコストを削減する。
注記

認証情報を管理するには、Datadog APIおよびアプリケーションキーを参照してください。

はじめる前に​

以下のものが準備できていることを確認してください：

  • ログのインゲージメント権限を持つDatadog APIキーです。これは組織設定 → APIキーで確認できます。
  • ご利用のDatadogサイトのアドレス。このアドレスは地域によって異なります：
地域サイトアドレス
米国東部datadoghq.com
US3 Westus3.datadoghq.com
US5 Centralus5.datadoghq.com
EUdatadoghq.eu
AP1 Japanap1.datadoghq.com
AP2 オーストラリアap2.datadoghq.com
  • curl または Postman がインストールされていること。
  • JSON 形式で記述されたログペイロード。

取り込みエンドポイント​

POST https://http-intake.logs.{dd_site}/api/v2/logs

{dd_site} をお客様の地域のサイトアドレス（例：datadoghq.com または ap2.datadoghq.com）に置き換えてください。

リクエストヘッダー​

ヘッダー値必須説明
DD-API-KEY<your_api_key>はいDatadog API キー
Content-Typeapplication/jsonはいペイロード形式
Content-Encodinggzipオプション圧縮ペイロード形式。大量データの処理に推奨されます。

リクエストボディ​

リクエストボディは、1つ以上のログオブジェクトからなる JSON 配列です。各ログオブジェクトには以下のフィールドが含まれます：

フィールドタイプ必須説明
message文字列はいログメッセージの内容
ddsource文字列推奨ログの出典となったテクノロジーの名称（例：python または nginx）
ddtags文字列オプションコンマで区切られたタグ（例：env:prod,team:payments）
hostname文字列オプションログを生成したホストの名前
service文字列推奨アプリケーションやサービスの名前
status文字列推奨ログイベントの重大度（例：info または ERROR）
timestamp文字列オプションイベントの時間（例：2025-11-15T08:30:00Z）。タイムスタンプの形式については注記を参照してください。
注記

message を必ず含めてください。Datadog では service、ddsource、ddtags を使用してパイプラインをフィルタリング・分類します。その他のフィールドはオプションです。

ペイロードの例​

Payload: single log
[
  {
    "message": "Transaction failed: Gateway timeout",
    "ddsource": "java",
    "ddtags": "env:prod,region:us-east-1",
    "hostname": "payments-host-01",
    "service": "payment-gateway",
    "status": "ERROR",
    "timestamp": "2025-11-15T08:30:00Z",
    "transaction_id": "txn_998877",
    "customer_id": "cus_554433"
  }
]
注記

timestamp には国際標準化機構（ISO）8601 の協定世界時（UTC）形式を使用してください。Datadog はログエクスプローラー内でこの値に基づいてタイムラインを表示します。タイムスタンプがないログは取り込み時刻が使用されます。Datadog では過去18時間以内のタイムスタンプも受け付けます。

cURL の例​

cURL
export DD_API_KEY="your_datadog_api_key_here"
export DD_SITE="datadoghq.com"

curl -X POST "https://http-intake.logs.$DD_SITE/api/v2/logs" \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "message": "Transaction failed: Gateway timeout",
      "ddsource": "java",
      "ddtags": "env:prod,region:us-east-1",
      "hostname": "payments-host-01",
      "service": "payment-gateway",
      "status": "ERROR",
      "transaction_id": "txn_998877"
    }
  ]'

レスポンスコード​

コードステータス説明
202受理済みペイロードが受け取られ、インデックスングのためにキューに入れられました。
400不正なリクエストフォーマットや検証にエラーがあります。
401権限なしDD-API-KEYヘッダーが欠落しています。
403禁止されていますAPIキーが無効であるか、ログの取り込み権限がありません。
408リクエストタイムアウトリクエストがタイムアウトしました。少し待ってから再試行してください。
413ペイロードが大きすぎますペイロードのサイズが5MBを超えています（圧縮前）。
429リクエスト数が多すぎますクライアントが制限を超えています。
500内部サーバーエラーDatadogで予期しない状況が発生しました。少し待ってから再試行してください。
503サービスが利用できませんDatadogの処理能力に達しています。少し待ってから再試行してください。

202件が受理されました​

202 Acceptedのレスポンスは、Datadogがペイロードを受け取ったことを確認します。レスポンスボディには空のJSONオブジェクトが含まれています。ログイベントは数秒以内にLog Explorerに表示されます。

Response: 202 Accepted
HTTP/1.1 202 Accepted
Content-Type: application/json
Response body: 202 Accepted
{}

不適切なリクエストが400件ありました。​

ペイロードの検証に失敗した場合、Datadogはこのコードを返します：

  • JSONの構文が正しくない、またはエスケープされていない文字が含まれている。
  • 必須のmessageフィールドが省略されている。
  • ペイロードのサイズが5MBの制限を超えています。
Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Invalid JSON",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

401「未認証」および403「アクセス禁止」​

DD-API-KEYヘッダーがない場合、Datadogは401 Unauthorizedを返します。APIキーの検証に失敗したり、ログの取り込み権限がない場合は403 Forbiddenを返します。

Response: 403 Forbidden
{
  "errors": [
    {
      "detail": "Forbidden",
      "status": "403",
      "title": "Forbidden"
    }
  ]
}

413ペイロードが大きすぎます​

リクエストのペイロードサイズが5MBを超えた場合、Datadogはこのコードを返します。

Response: 413 Payload Too Large
{
  "errors": [
    {
      "detail": "Payload too large",
      "status": "413",
      "title": "Payload Too Large"
    }
  ]
}

リクエストが429件もありすぎます。​

リクエスト数が多すぎます。リクエスト数を減らすか、複数のログオブジェクトを1つの配列ペイロードにまとめて送信してください。

再試行可能なその他のエラー​

Datadogは、一時的な障害に対しても408 Request Timeout、500 Internal Server Error、503 Service Unavailableを返します。指数関数的なバックオフを用いてリクエストを再試行してください。408 Request Timeoutが継続する場合は、より小さなバッチで送信してください。

ログイベントのバッチ処理​

配列を渡すことで、1回のリクエストで最大1,000件のログエントリを送信できます。Datadogは大量データを扱うサービスにこの方法を推奨しています。

Payload: batched logs
[
  {
    "message": "User login succeeded",
    "service": "auth-service",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "INFO"
  },
  {
    "message": "Transaction failed: Gateway timeout",
    "service": "payment-gateway",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "ERROR",
    "transaction_id": "txn_998877"
  }
]

一般的な使用例​

  • Datadog Agentをデプロイすることなく、マイクロサービスからログを取り込む。
  • アマゾンウェブサービス（AWS）のLambdaやGoogle Cloud Runなどのサーバーレス関数から、構造化されたJSONイベントを送信する。
  • IoTデバイスやエッジサービスからのストリーミング型テレメトリデータ
  • ローティング処理により、イベント情報をセキュリティ管理システム（SIEM）、S3、またはログパイプライン経由のアラート宛先に送信する。
  • 継続的インテグレーション（CI）および継続的デリバリー（CD）パイプライン、またはデプロイメントスクリプトからのログの送信。

トラブルシューティング​

問題考えられる原因解決策
401 UnauthorizedAPIキーが正しくない、または存在しないOrganizational Settings → API Keys で DD_API_KEY を確認してください。
400 Bad Request横形データ（Malformed data）送信する前に jq . payload.json で確認してください。
エクスプローラーでログインしないパイプラインフィルターでログを除外するフィルターをクリアする。その後、インデックスルーティングルールを確認する。
タイムスタンプの順序が乱れているUTCまたはISO 8601形式ではない、または18時間前のもの"2025-11-15T08:30:00Z"形式を使用してください。イベント発生から18時間以内にログを送信してください。
429 Too Many Requestsレートリミットを超えましたログオブジェクトを一つの配列ペイロードにバッチ処理する
