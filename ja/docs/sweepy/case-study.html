「「92%」が異なる意味を持つとき」

「プレーンテキストインターフェース内で自ら文脈を示すテキストに関するUXライティングケーススタディ。」

Sweepyはターミナルベースの求人検索ツールです。インターフェースではボックス描画用の文字やカラーテキストが使用され、キーボード入力が読み取られます。ツールヒントの表示場所がないため、説明はテキスト自体に含まれなければなりません。ランチパッド（launchpad）ではステータス行が画面端で切り捨てられ、テキストが画面全体を埋め尽くさないようになっています。

そこから1つのルールが導かれました：すべてのテキストは自らの文脈を明確に示さなければならない。スコアラベルにはその数値を作成したユーザー名が記載され、ステータス情報も同様のルールに従って表示されます。特にスコアの場合、読者がその数値がどのように算出されたかを知っているかに関わらず、その数値自体が情報として意味を持ちます。

2つのパーセンテージ、2つの疑問​

Sweepyは履歴書を2つの異なる方法で評価します。

最初のスコアリング手法は決定的なもので、すべての処理で使用される。sweepyが処理の開始を示し、START SWEEPが処理で見つかった各項目にスコアを付ける。sweepy --runはウィザードを開かずに最後に保存された設定内容を再適用する。この処理では、履歴書と投稿内容の間で共通する単語を数え、要件の重複度を60%、キーワードの重複度を40%として評価し、その結果をresume.keywords_weightによって調整する。ある単語が両方の文書に含まれている場合のみ、それがカウントされる。スコアリングシステムは読者がその仕事をこなせるかどうかについては判断しない。

2つ目の評価方法では、Model Context Protocol（MCP）を通じてエージェントが履歴書と投稿内容を解析し、読者がその役割に適しているかを判断します。その結果はsubmit_judgmentsを通じて表示されます。

共有単語数とエージェントの評価は異なる質問に対して答えを出す。共有単語数はテキストの重複度を測定するものであり、適合度を示すものではないため、ラベルには作成者の名前を明記する必要がある。この数値は履歴書と求人情報がどれだけ共通しているかを示している。一方、エージェントはその人がその仕事にどれだけ適しているかを判断する。履歴書が求人情報の内容を一字一句そのまま再現しても、適合度が低いと評価されることがある。また、異なる表現を使った履歴書でも適合度が高いと評価されることがある。単語数は前者のケースを捉えられるが後者を見落とす可能性があるが、エージェントは両方の要素を考慮して評価を行う。

カードには1つのスコアが表示される。最新の作成者がそのスコアを設定し、その後の評価によってレポートの順位が再調整される。エージェントの評価結果が決定的なスコアに取って代わり、単に並んで表示されるだけではない。スコアのみが表示されるため、読者はどちらの情報源に基づいてスコアが算出されたかを判断できない。

リストを開く前に、バッジ内に作成者の名前を明記する必要があった。インターフェースの他の部分も同じルールに従う。

Launchpadから結果まで​

カード3からカード8はこの順序で表示される。カード2にはスコアが表示され、これはスウィープ処理が終了した後にのみ算出される。カード1では問題点が説明され、カード9ではそれぞれの情報の背後にある制約条件が示される。

1つのスコア枠には2人の作成者が関与する可能性がある。各カードに対しては決定的な重複単語数に基づいてスコアが付けられるが、MCP（Machine Learning-based Assessment）の評価結果によってその数値が上書きされる。明確なラベルがない場合、読者はどちらの作成者がスコアを設定したかを判断できず、信頼性も評価できない。重要なのは、バッジ内の数語で作成者を明確に示すことです。

1つのスコアスロット、2人の作成者​

各項目について、決定的な重複度に基づいてスコアが付けられる。しかし、MCPの評価によってそのスコアが上書きされる場合もある。明確なラベルの違いがないため、読者はどの著者がスコアを設定したかを判断できず、信頼性も評価できない。問題は、わずかな言葉の中で著者を区別することだった。

「数」と「判断」の見分け方​

3位の役割に対するPDFレポートカードで、KEYWORDOVERLAPのスコアが88%を示しており、「提出トラック」バッジや「拡張回答」バッジも表示されている](./screenshots/sweepy-11-pdf-extended-status.png)

同じプロフィール、同じ番号、2人のライター。最初のカードはエージェントによって設定されたため、92% MATCHと表示される。2番目のカードは決定的なスコアリングシステムによって設定されたため、92% KEYWORD OVERLAPと表示される。ラベルはライターを識別するためのものです。92％しか内容を見ていない読者には、2つのカードを区別する方法がない。評価結果は同じスロット内の重複スコアを上書きするが、その理由はカウント値と判断基準が異なるからです。

  • 92% KEYWORD OVERLAPとは、履歴書と投稿内容の共通単語数を指す。
  • 92% MATCHとは、エージェントが読者がその役割にどれだけ適しているかを推論した結果得られた数値を指す。

スウィーピー（Sweepy）は、端末から操作する場合でもMCP経由でrun_sweepを使用する場合でも、生成する各カードにその数値を記録する。match_pctという値が提出された場合にのみ、その数値はMATCHに置き換えられる。

PDF形式ではラベルが括弧内に表示される（#1 // COMPANY | [92% MATCH]または[92% KEYWORD OVERLAP]）。CSV形式ではmatch_valueがmatch_kindの隣に記載され、これにより読者は同じ情報を機械可読形式で確認できる。マッチスコアの横には3番目のスコアが表示されることもある。[88% PORTFOLIO FIT]も同様の理由で独自のラベルを表示するが、これはサンプルが履歴書とは異なる質問に答えているためです。

アプリケーションのバッジはまずテキストで表示され、その後色で強調される。[STANDARD / QUICK APPLY]は標準的な提出を示し、[EXTENDED RESPONSES REQUIRED]は執筆サンプルが必要な役割を示す。3枚目のカードにはランク情報とともに[EXTENDED RESPONSES REQUIRED]が表示される。両方のラベルとも色なしで表示されるが、これはアクセシビリティや色表示ができない端末にとって重要です。

1行に表されるアイデンティティ、スコープ、準備状況​

Current profile: none loaded / build one to startはプロフィールが未読み込みの状態と次に取るべきアクションを1行で示す。Current profile: Alex Rivera / 4 titles / Readyは最初のスロットに記載された名前と準備状況を確認するための情報を示す。スラッシュ（/）は各回答を区切り、行は枠の端で切り揃えられる。保存されたプロフィールに履歴書のパスがない場合、Resume missingがReadyに置き換わる。

端末ではステータスラインが唯一持続的に表示される情報となる。これはヘッダーとしても準備状況の指示としても機能する。

動詞、目的語、そして読者の目標​

START SWEEPはRun your job search nowとペアになります。各タイルには2行が表示され、1行には製品名が、もう1行には「Enter」キーが何をするかを読者の言葉で説明したサブタイトルが記載されています。SWEEP SETTINGSはRanking, cards, trackingを表示し、SWEEPY'S TOOLBOXはEdit profile, logs, helpを表示します。EXIT SWEEPYはSave changes and closeを表示し、これにより作業内容が保存されます。

アクションを示すタイルには動詞とその対象が記載されており、その他のタイルには場所や出口が示されています。サブタイトルでは内部用語を平易な言葉で説明しています。2桁の数字は各タイルを識別するためのものであり、グリッドの順序を示すものではありません。最上行では01が04とペアになっています。新しいタイルが追加されても他のタイルの番号は変更されません。ナビゲーションは矢印キーとEnterキーで行います。

プロンプト内の書式ヒント​

プロンプトは質問内容を1行に収め、書式が重要な場合はその下にルールをインデントして表示します。

Job roles
What job titles are you looking for?
  (Separate multiple titles with a comma)

給与に関するプロンプトでは、スキップオプションが質問文内に明記されています。

Salary
What is your minimum target salary? (Leave blank to skip):

ルールはユーザーが決定を下す行に表示されます。端末にはヒント機能（ツールティップ）はありません。

ウィザードを再実行せずに回答を編集する​

ウィザードは15のステップで構成されており、Escキーを押すと各質問が1つずつ戻されます。レビュースクリーンには← Back、Submit profile、そして9つのアクションが表示されます。Edit an answerはSubmit profileの直下にあります。回答を変更したい場合、すべてのプロンプトを再度実行する必要はありません。

5つのステップのステージラベル​

コマンドライン実行により5つのステージが順に処理され、各ステージで実行される作業が示される。

[1/5] Loading profile...
[2/5] Discovering roles...
[3/5] Validating URLs...
[4/5] Scoring against resume...
[5/5] Generating reports...

ログメッセージにはステージ番号が記載されている。MCPからの進捗情報によって実際に行われている作業が報告される（例：step 3、total 5、Validating URLs）。Scoring rolesではスコアリング中の作業内容が表示される。読者は現在の処理状況と残りの作業内容を確認できる。進捗バーは、ツールが把握できない処理時間を示唆する可能性がある。

ジョブIDを返す待機処理​

ライブスキャン処理には1分以上かかる場合もある。MCPモードでは、ツールの呼び出しは全体の処理完了を待たずに実行状態を返す。これにより、クライアントのタイムアウト内で処理が継続されることが確認できる。

デフォルトではrun_sweepは45秒間待機する。wait_secondsではこの待機時間を設定可能で、範囲は0～600秒まで。SWEEPY_MCP_WAIT_SECONDSではより厳格な制限が適用されるホストにおける待機時間を調整する。実行状態にはjob_id、progress、elapsed_seconds、messageのデータが含まれる。

MCP running state
{
  "status": "ok",
  "sweep_status": "running",
  "job_id": "<job id>",
  "progress": { "step": 3, "total": 5, "label": "Validating URLs" },
  "elapsed_seconds": 41.2,
  "debug_log": "<path>",
  "message": "The sweep is still running. Call get_sweep_status to wait for it, then continue with get_jobs."
}

クライアントはget_sweep_statusとjob_idとのやり取りを続け、sweep_statusが"completed"を読み込むまで待つ。クライアントが接続を維持しているかどうかに関わらず、Sweepyは処理を継続する。生成されたコピーはタイムアウト内に収まり、後で再接続したクライアントに正しく表示されなければならない。これは進捗状況を報告するリアルタイムのプロセスです。

45秒間の待機時間は製品のデフォルト設定であり、_DEFAULT_WAIT_SECONDSによって設定され、_MAX_WAIT_SECONDSによって上限が決められる。progressおよびelapsed_secondsでは実行ごとに待機時間が変更される。debug_logも同様です。messageでは次に実行されるツールの名前が示される。

拙い文章を隠す場所などない​

インターフェースはテキストのみを使用しており、画面に表示される情報はすべて自己完結的でなければならない。ステータスメッセージによって現在の処理状況が明確に示されるが、スピナーなどの補助要素はない。

名前の付け方には一定の規則がある。START SWEEP、LOAD PROFILE、BUILD PROFILEはそれぞれの処理内容を示す言葉で始まる。サブタイトルではその処理の目的が再度説明されるため、「プロファイル」といった内部用語は不要です。数字にも同じルールが適用される。KEYWORD OVERLAPは確定的な処理数を示し、MATCHはエージェントの判断結果を示す。

フレームの幅が長い文字列を切り取ってしまう​

ターミナルが条件を設定する。テキストだけが何を意味するのかを説明するものであり、フレームは長すぎる部分を自動的にカットしてしまう。エラーメッセージには問題とその解決策が同じ文内に記載されていなければならない。読者は別の情報を読むためにその行を離れることができない。

各文字列はそれぞれ独自の文脈を持つ。Could not parse salary %r. Enter a number like 65000, 65,000, or 65k.は何が失敗したか、代わりに何を入力すべきかを示し、%rは却下されたデータを示す。Current profile: none loaded / build one to startも同様に、プロファイルが欠落している場合に使用される。GUIでは、これらの文の後半部分をツールヒントとして表示することもできるが、ここでは1行の中に両方の情報が含まれている。

説明としてラベルのみ​

スコアのラベルにはその数値を誰が作成したかが記載されている。ドキュメントでは次のように明確に表現されている：「MATCHのカードは評価結果を示し、KEYWORD OVERLAPのカードは共有された情報を示す。」各カードにはラベルが1つずつ表示され、読者はリストを開く前にどの情報を見ているのかを把握できる。

各ラベルはまた、その数値がどのような比較によって得られたかも示している。KEYWORD OVERLAPは2つの文書に関する情報を示し、MATCHは人物や仕事に関する情報を示す。2つの数値が一致すると期待している読者は、そのうちの1つを誤って解釈してしまう可能性がある。

ラベルはインターフェースではなく、実際に情報を作成した人を示す。パーセンテージなしでもエージェントは評価結果を提出できる。そのカードには依然として「KEYWORD OVERLAP」と表示されるが、それはSweepyがその数値を生成したからです。実際の実行内容はカードの外にある。レポートファイル名にはmcpが使われ、ログヘッダーには実行方法が記載される。

タイルの命名規則は同じです。BUILD PROFILEにはアクションが記載され、そのサブタイトルにはそのアクションの目的が説明されている。Set up your job searchは読者にとってわかりやすい表現に内部用語を置き換えている。LOAD PROFILEはOpen a search you savedを表示し、そのタイルが何をするかを説明している。

私が執筆した内容と、その確認方法​

役割。 このケーススタディで引用されているすべての製品名やテキストは私が作成したものです。これらには、ローンチペッドのサブタイトル、ウィザードのプロンプト、進捗状況のメッセージ、検証用のテキストなどが含まれます。また、クライアントから提供された「スコアの出所」を示すラベルやMCPの引き継ぎ処理（message）も含まれます。ビルド作業はCopilotおよびGeminiを使用して行い、リポジトリレベルのガイドラインおよびCI（継続的インテグレーション）の品質チェックに従って実施しました。作成した製品名などのテキストはSweepyのソースコードと照合して正確性を確認しました。

信頼度を見極めてから行動する​

読者はスコアに基づいて行動する前に、その信頼性を評価し、待機中にシステムが何をしているのかを理解する必要がある。インターフェースではSweepyがどのようにして数値を生成したのか、プロセスにどれくらいの時間がかかるのかを説明することはできない。ラベルやステータスメッセージが、視覚的な補助情報なしでも分かりやすい形でその内容を伝えている。
