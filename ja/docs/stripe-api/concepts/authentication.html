認証とキー管理

Stripeへのリクエストには、Authorizationヘッダー内にAPIキーが含まれます。このキーはアカウントを識別し、作成したロールの権限を継承します。秘密キーが漏洩すると、アカウント内のすべての請求情報、顧客情報、支払い情報が公開されてしまいます。

キーの種類​

各アカウントには3種類のキーがあります。そのうち1種類のみをサーバー上で使用できます。

キープレフィックスブラウザ内での安全性使用目的
公開可能pk_test_, pk_live_はいクライアントサイドでのトークン化処理およびStripe.jsの使用。APIアクセスは許可されない。
秘密情報sk_test_, sk_live_いいえサーバーサイドでのAPI呼び出し。アカウントの全権限が必要。
制限ありrk_test_, rk_live_否サーバーサイドの呼び出しは指定されたリソースおよび操作に限定されます。

シークレットキーは、アカウントが所有するすべてのデータを読み書きすることができます。制限付きキーは、読み取り専用など、特定のリソースへのアクセスを制限します。統合処理にアカウント全体の権限が不要な場合は、必ず制限付きキーを使用してください。

危険

クライアントコード、モバイルバイナリ、パブリックリポジトリ、またはサポートチケットに秘密鍵や制限付きキーを含めてはいけません。その鍵を持っている人なら誰でも資金を移動させることができます。

キーの送信​

curl https://api.stripe.com/v1/balance \
  -u "$STRIPE_SECRET_KEY:"
Node.js
const response = await fetch("https://api.stripe.com/v1/balance", {
  headers: { Authorization: `Bearer ${process.env.STRIPE_SECRET_KEY}` },
});
Python
import os, requests

response = requests.get(
    "https://api.stripe.com/v1/balance",
    auth=(os.environ["STRIPE_SECRET_KEY"], ""),
)

キーの保存​

ランタイム時に環境からキーを読み込む。決してコミットしたり、ログに記録したりしない。

.env
STRIPE_SECRET_KEY=sk_test_51N...
server.js
if (!process.env.STRIPE_SECRET_KEY) {
  throw new Error("STRIPE_SECRET_KEY is not set");
}

環境設定ファイルを.gitignoreに追加する。ホスティングプラットフォームはその値を秘密ストレージに保存し、プロセス環境に注入する。これにより、キーがリポジトリやビルドログに含まれるのを防ぐ。

接続を確認する​

1件のリードリクエストを送信します。200という応答が返され、その中にキー、ベースアドレス、ネットワークパスが含まれています。

curl -s https://api.stripe.com/v1/balance -u "$STRIPE_SECRET_KEY:" | jq '.object, .livemode'

テストキーに対しては「"balance"」および「false」と表示されます。「401」はそのキーがこのアカウントでは無効、または削除されていることを意味します。「403」は制限付きのキーがそのリソースにアクセスするための権限を持っていないことを示します。

制限付きキーの範囲設定​

制限付きキーは、各リソースに対するアクセス権を一覧表示します。インテグレーションに必要な最小限の権限のみを付与してください。

統合推奨される権限
レポーティングジョブ費用の確認、取引のバランス、支払い処理を行う。
チェックアウトサーバー支払いに関する情報や返金処理を行う。顧客データも参照する。
Webhook検証器イベント情報を読み取る。書き込み権限はない。

各キーには、それを使用するサービスの名前を付ける。例えばcheckout-api-prodのような名前を付けると、インシデントの調査が迅速に行える。なぜなら監査ログにどのキーが使用されたかが表示されるからです。

キーのローテーション​

スケジュールに従ってキーをローテーションする。また、何らかのセキュリティ上の問題が疑われた場合にも即座にローテーションを実施する。古いキーは削除するまで引き続き使用可能なので、ローテーションによるダウンタイムは発生しない。

  1. 同じ権限を持つ代替キーを作成する。
  2. その代替キーを新しい名前でシークレットストアに追加する。
  3. 新しい名前でサービスをデプロイする。
  4. 新しいキーでのトラフィック処理が正常に行われていることを確認する。
  5. ダッシュボードで古いキーの権限を取り消す。
  6. デプロイ後、古いキーからのリクエスト履歴を確認する。
警告

まず古いキーを無効にすると本番環境に影響が出ます。新しいキーをデプロイした後で古いキーを無効にし、その2つのステップ間のエラーレートを確認してください。

リークへの対応​

リポジトリ、ログ、またはチャットメッセージ内に含まれる秘密鍵はすべて侵害されたものとみなします。

  1. ダッシュボードの「Developers」 → 「API keys」で該当するキーを無効にします。
  2. 代替キーを作成してデプロイします。
  3. リクエストログを確認し、未知のIPアドレスや異常なエンドポイントがないか調べます。
  4. 自分が行ったものではない取引があるか、残高や支払い履歴を確認します。
  5. 不正なアクティビティが見つかった場合はStripeのサポートに連絡してください。

キーの無効化は即時に効力を発生します。無効になったキーは次回のリクエストに失敗します。

よくある障害​

症状原因修正方法
401 Invalid API Key providedキーが不完全か、無効になっているか、別のアカウントのものです。ダッシュボードからキーを再コピーしてください。
403 が使用されているリソースについてこのキーにはアクセス権限がありません。アクセス権限を追加するか、より広範囲の権限を持つキーを使用してください。
401 は本番環境でのみ使用可能そのデプロイメント環境では環境変数が空です。本番環境用のシークレットストアを確認してください。
リクエストが処理を停止し、その後失敗プロキシが HTTPS から api.stripe.com への通信をブロックしています。ポート443でのホストのアクセスを許可してください。

次のステップ​

  • 非決定性リクエスト を使用して、再試行された POST を安全に実行する。
  • エラーと再試行 を行い、各失敗に対応する復旧手順を定義する。
  • APIのバージョン管理とアップグレード を行い、レスポンスの形式を固定する。
