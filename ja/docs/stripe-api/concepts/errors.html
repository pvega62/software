エラーと再試行

Stripeは失敗をHTTPのステータスコードとJSONのエラーメッセージで報告する。ステータスコードはリクエストがどのように失敗したかを示し、エラーメッセージには失敗の原因や修正すべきパラメータが記載されている。

エラーメッセージの構造​

失敗したリクエストはerrorオブジェクトを返す。含まれるフィールドは失敗の種類によって異なる。

{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds.",
    "charge": "ch_3Rsx4dDtWMrPDtgt1",
    "param": "",
    "doc_url": "https://stripe.com/docs/error-codes/card-declined",
    "request_log_url": "https://dashboard.stripe.com/test/logs/req_UQf6XBwBl9yk66"
  }
}
フィールド機能
typeエラーの種類。処理の方向性を決定する。
codeマシンが読み取り可能な短い原因（例：parameter_invalid_integer）。
decline_codeカードエラーの発生理由（例：insufficient_funds）。
message人間が読み取り可能なテキスト。サポートスタッフ向けであり、顧客には表示しない。
param失敗が特定のフィールドに起因する場合、そのパラメータ。
chargeカードエラーが発生した際のチャージID（チャージが存在する場合）。
doc_url具体のエラーコードを説明するページ。
request_log_urlダッシュボード内のリクエストログエントリ。リクエスト内容と応答内容が表示される。
注記

すべての失敗ケースにおいてrequest_log_urlを記録する。これにより、サポートチケットから具体的に失敗したリクエストまでの最短経路が分かる。

エラータイプ​

4つのtype値がプラットフォーム全体をカバーしている。

type意味再試行
invalid_request_errorパラメータが欠落しているか形式が不正確か、オブジェクトが存在しないか、アクセス権がありません。いいえ。リクエストを修正してください。
card_errorカード発行者がチャージを拒否した、またはカードの認証が必要。decline_codeに依存します。
idempotency_error誰かが異なるパラメータで同じキーを再利用した。いいえ。新しいキーを使用してください。
api_errorStripeが有効なリクエストを処理できなかった。はい。再試行処理を行います。

ステータスコード​

状態通常の処理時間（type）原因再試行
400invalid_request_errorパラメータの形式が不正確、必要なフィールドが欠落している、または互換性のない組み合わせ。いいえ
401invalid_request_errorキーが欠落している、無効になっている、または別のアカウントからのもの。いいえ
402card_error発行者が請求を拒否した。decline_code に依存
403invalid_request_errorキーにそのリソースへのアクセス権限がない。いいえ
404invalid_request_errorこのモードでは該当するオブジェクトが存在しない。いいえ
409idempotency_errorこのキーを使用したリクエストがまだ実行中。はい（一時停止後）
429rate_limit_errorキーのリクエスト頻度が制限を超えている。はい（バックオフ処理あり）
500api_errorStripeが予期しない状況に遭遇した。はい（バックオフ処理あり）
502api_error上流サービスに障害が発生した。はい（バックオフ処理あり）
503api_errorStripeが一時的に利用できない。はい（バックオフ処理あり）
504api_errorリクエストがStripe内でタイムアウトした。はい（バックオフ処理あり）

カードの拒否コード​

card_error の後に decline_code が続きます。このコードは、再試行が有効かどうかを示します。

decline_code意味再試行対応方法
insufficient_fundsアカウントの残高では支払いができません。はい、後でお客様に別のカードを使用するよう依頼するか、待機してください。
expired_cardカードの有効期限が切れています。いいえ新しいカードを入手してください。
incorrect_cvcカードの認証コード（CVC）が一致しません。1回お客様に再度コードを入力してもらってください。
processing_errorネットワークでの処理に失敗しました。はい短時間待った後に再試行してください。
card_declined発行者から特別な理由なく拒否されました。いいえ別の支払い方法をお願いしてください。
authentication_required発行者が3Dセキュリティの利用をリクエストしています。認証後認証手続きを行い、その後再度確認してください。
lost_card, stolen_card発行者が報告されたカードをブロックしました。いいえ再試行しないでください。このケースをリスクチームに連絡してください。
警告

困難な拒否処理を繰り返すと、さらに拒否が発生し、アカウントの拒否率が上昇する可能性があります。はいと表示された場合のみ再試行し、再試行回数の上限に達したら中止してください。

再試行ポリシーの構築​

2回目の試行で成功する可能性のある失敗のみを再試行する：409、429、および5xxファミリー。各試行間には指数関数的な間隔（バックオフ）とジッターを設ける。再試行回数には上限を設ける。

Node.js
// Retry only these status codes.
const RETRYABLE = new Set([409, 429, 500, 502, 503, 504]);

async function requestWithRetry(url, options, attempts = 4) {
  for (let attempt = 0; attempt < attempts; attempt++) {
    const response = await fetch(url, options);
    if (response.ok) return response;

    // Stop on a permanent failure, or when the budget runs out.
    if (!RETRYABLE.has(response.status) || attempt === attempts - 1) {
      return response;
    }

    // Wait 500 ms, then 1 s, then 2 s, plus jitter.
    const base = 2 ** attempt * 500;
    const delay = base + Math.random() * 250;
    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}

再試行は約0.5秒、1秒、2秒後に実行され、その間にジッターが加わる。このスケジュールにより、短時間のサービス停止からもAPIへの過度な負荷を避けることができる。

各POSTには不変性キーをペアリングする。これがない場合、タイムアウト後の再試行によってカードから料金が2回請求される可能性がある。

再試行する前にレスポンスを確認する​

429には、いつ再度試行すべきかを示すヘッダー情報が含まれている。推測するのではなく、必ずその情報を確認する。

ヘッダー意味
Retry-After次の試行までの待機時間（秒）
Stripe-Rate-Limited-Reasonどの制限（global-concurrencyやendpoint-concurrencyなど）が発生したか
  1. 429を確認し、それに基づいて対応する。card_errorの場合は顧客の操作が必要であり、api_errorの場合は再試行が必要です。

障害を診断する​

  1. typeを読み、その内容に基づいてブランチ分岐を行います。card_errorには顧客のアクションが必要です。api_errorには再試行が必要です。
  2. paramを読んで400を取得してください。リクエスト全体ではなく、指定されたフィールドの値を修正してください。
  3. request_log_urlを読みます。Stripeがリクエストを受け取ったことを確認し、正確なペイロードをチェックします。
  4. モードを確認します。有効なオブジェクトに対する404は、テスト用のオブジェクトを読んでいる可能性があります。
  5. キーを確認します。403は許可なくアクセスできないキーを示しています。

よくある間違い​

間違い結果修正方法
すべての4xxを再試行する複数回の拒否処理やクォータの無駄409、429、5xxのみを再試行する。
1秒間の待機時間の設定障害後に同期して再試行する各再試行にジッター（ランダムな遅延）を加える。
キーなしで再試行する複数回の請求が発生する各POSTごとにIdempotency-Keyを送信する。
顧客にmessageを表示する内部情報が誤解を招くか漏洩するdecline_codeを自分のコピーにマッピングする。
request_log_urlを無視するデバッグが遅くなるエラー情報を含むリンクをログに記録する。
