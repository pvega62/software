レートリミットとバックオフ

レートリミットはクレデンシャル単位で設定され、接続単位ではない。1つのAPIキーを使用する10人のユーザーがそのキーの利用枠を共有する。同じサーバー上の異なるAPIキー同士は互いの利用枠に影響しない。

429エラーが返す内容​

429 Too Many Requests
HTTP/1.1 429 Too Many Requests
content-type: application/problem+json
retry-after: 12
x-ratelimit-remaining: 0

{
  "type": "https://api.bludhavenpets.com/errors/rate-limited",
  "title": "Rate Limited",
  "status": 429,
  "detail": "The credential exceeded its window. Retry in 12 seconds.",
  "instance": "/animals"
}
ヘッダー意味
Retry-After次の試行までの待機時間（秒）
X-RateLimit-Remaining現在のウィンドウ内に残っているリクエスト数（ここでは0と表示）

Retry-After | これはサーバー側からの返答値です。推測せずにこの値に従ってください。固定時間の待機は時間の無駄になるか、再利用のタイミングを逃す可能性がある。

公開されている利用枠​

クレデンシャルクラスウィンドウリクエスト数
POSレジスターキー1分間の累計値300
サーバージョブキー1分ごと120回
パートナーベアラートークン1分ごと120回
アドオプターセッショントークン1分ごと60回

“429”というエラーコードは最終的な判断基準となる。この表は計画の参考として、ヘッダーに記載されている情報は事実として扱う。

レジスターが制限に達する理由​

販売後に在庫を同期するレジスターは、混雑した土曜日に予算を使い果たしてしまう。3つの習慣によってこの問題を防いでいる。

  • 在庫データはトランザクションの終了時に一括で書き込まれる（スキャンごとに1回ではない）。
  • GET /retail/inventoryをタイマーで定期的にポーリングする。画面ごとにポーリングするレジスターは自身のトラフィックを増加させてしまう。
  • 動物カタログをキャッシュする。同じ10件のプロフィールを表示する場合は1回のリクエストで済む。

効果的なバックオフ処理​

Retry-Afterを読み取り、その時間待った後、ランダムなオフセットを加えることで、複数のレジスターが同じ秒に再試行しないようにする。

Node.js
async function callWithRetry(request, { attempts = 4 } = {}) {
  for (let attempt = 1; attempt <= attempts; attempt += 1) {
    const response = await request();
    if (response.status !== 429) return response;

    const retryAfter = Number(response.headers.get('retry-after') ?? attempt * 2);
    const jitter = Math.floor(Math.random() * 500);
    await new Promise((resolve) => setTimeout(resolve, retryAfter * 1000 + jitter));

    if (attempt === attempts) return response;
  }
}
Python
import random
import time

import requests


def call_with_retry(request, attempts=4):
    for attempt in range(1, attempts + 1):
        response = request()
        if response.status_code != 429:
            return response
        retry_after = int(response.headers.get("Retry-After", attempt * 2))
        time.sleep(retry_after + random.uniform(0, 0.5))
    return response

どちらのループもエラーコード“429”を返すだけであり、エラーを直接報告するわけではない。予算を使い果たした呼び出し元は失敗内容をログに記録する必要がある。

書き込みの再試行​

429エラーとは、リクエストが実行される前にプラットフォームによって拒否されたことを意味します。GET、PUT、DELETEについては再試行が安全です。

POSTを再試行するにはIdempotency-Keyが必要であり、そうしないと元の書き込みが重複してしまいます。POST /refundsについてはヘッダー情報が既に必要なため、同じ理由で他の書き込み処理にもヘッダーを含めて送信する必要があります。

サンドボックスの役割​

サンドボックスゲートウェイはクォータ制限を適用しません。すべてのリクエストに応答するため、読者はカウンターを確認することなくコンソールを確認できます。429のレスポンスは契約書に記載されており、本番環境のゲートウェイがそれを返します。

自己の処理速度を制御するサンドボックスは「バックオフ」（待機処理）に関する知識を提供しないため、2つのゲートウェイは意図的に異なる動作をします。
