失敗したリクエストのトラブルシューティング

これらの手順を順に試すことで、ほとんどの障害を解決できます。

  1. status：障害の種類を示します。
  2. type：実際に発動したルールの名称（エラーカタログ）。
  3. request_id：その障害がどのプラットフォームで発生したかを特定します。

セキュリティ保護された呼び出しでは401が返されます​

WWW-Authenticateヘッダーにはルートがリクエストする通信方式が記載されている。

WWW-Authenticate: Bearer realm="bludhaven", error="invalid_token"

このようなエラーが発生する原因は以下の5つ：

  • ヘッダーが欠落しています。ブラウザシェルやプロキシによってヘッダーが削除されることがあります。
  • 「scheme」という単語が間違っています。Authorization: Basicはベアラールート（bearer route）に対して正しく動作しません。
  • トークンが偽造または改ざんされています。ゲートウェイはHMACの署名を検証するため、自ら発行したトークンのみが通過します。
  • 伝えられたトークンはexpです。新しいトークンを生成してください（認証）。
  • キーの入力が間違っているか、使用期限が切れているか、またはトークンのみを受け取るルートに送信されています。その場合、チャレンジではApiKeyが表示されます（Bearerではありません）。

プレーンなルートでは401エラーは発生しません。なぜなら、5つのルートでは認証情報が不要だからです（GET /animals、GET /animals/{animalId}、POST /applicants、POST /sessions、POST /webhooks/test-dispatch）。

セキュリティ保護された呼び出しでは403が返されます​

ゲートウェイはトークンを認識しましたが、そのトークンには必要なスコープが含まれていません。チャレンジではそのスコープが明記されています。

WWW-Authenticate: Bearer realm="bludhaven", error="insufficient_scope", scope="write:animals"

typeではhttps://api.bludhavenpets.com/errors/insufficient-scopeが表示され、detailでは不足しているスコープが文章で説明されています。

この状況は2つの理由で発生します：

  • クライアント認証情報トークンのスコープが狭すぎました。チャレンジで指定されたスコープを使用して、トークンリクエストを再度送信してください。
  • 同意画面でサブセットが承認されました。「Connect」を再度実行し、ルートに必要な範囲を承認してください。

この修正は認証時に適用されます。同じトークンで再試行しても、同じ 403 が返されます。

「animal」と指定しても 404 が返されます​

GET /animals/{animalId}は、pet_で始まるインプット識別子を受け取ります。マイクロチップの番号も、名前も、大文字表記された名前も404として返されます。

最初にGET /animals?status=AVAILABLEを送信し、そのページからidをコピーします。この処理により、識別子の形式およびその動物が格納されているブランチが確認されます。

以前は正常に動作していたホールドIDが、現在は404を返すようになりました​

設計上、2つのターゲットではホールド処理が失敗する。

ターゲットホールド処理が失敗する理由
ブラウザデモページを再読み込むとタブ内のホールド情報が削除される。
サンドボックスゲートウェイ再利用されたエッジサーバーがメモリ内に保持していた情報を破棄する。

どちらのターゲットもAPIを通じて動物を解放しなかった。新たなホールド処理を行い、404を「解放済みの動物」としてではなく「未登録の記録」として扱う。

プロダクション環境でのホールド処理は両方のケースでも保持され続ける（データは耐久性のあるストレージに保存されているため）。

保留処理が422エラーで失敗する​

プラットフォームは資格のない動物の解放を拒否する（ホールド処理自体が存在しない場合でも同様）。

  • 動物の状態がAVAILABLE以外（例：MEDICAL_QUARANTINE）である場合がある。
  • spay_neuter_certifiedがfalseの値を読み取ると、市の規則により解放がブロックされる。
  • 狂犬病に関するドキュメントの有効期限が保留期間前に切れました。

動物記録を確認し、statusをカウンセラーに提示してください。リクエスト内容に変更がないため、待機リストに登録する方が再試行よりも適切です。

デモは正常に動作するが、サンドボックスでは拒否される​

サンドボックスゲートウェイは、ブラウザデモで無視されているセキュリティ要件を厳格に適用しており、この違いが両環境間のほぼすべての差異を説明しています。

ゲートウェイが生成したトークンを、開放されている5つのルート以外の任意のルートから送信してください。クライアントの認証情報を使用してトークンを生成するか、リファレンスにある「Connect」ボタンを押してください。架空の文字列を送信すると401が返され、ルートの範囲情報が含まれていない本物のトークンを送信すると403が返されます。

ゲートウェイが、ドキュメントに記載されている操作に対して404を返しています​

古いデプロイメントが原因です。ゲートウェイが読み込んだコントラクトを確認してください。

curl https://sandbox.bludhaven-pets.workers.dev/health

現在のデプロイ状況では、operations: 24 および secured: 19 と報告されています。これより数値が低い場合は、エッジが古いレスポンステーブルを実行していることを意味し、再デプロイを行うことで修正されます（バージョン管理）。

エスカレーション​

  • 失敗したレスポンスから得られた code の値。

  • 失敗した応答から得られるX-Request-Idのデータ

  • 操作内容および対象となる環境（本番環境またはサンドボックス環境）。

  • 状態情報およびtypeのURI

  • タイムゾーン付きのタイムスタンプ

  • コールを再現する必要なく、トレース識別子をサポートします。これがない場合、レポート作成には往復通信が必要になります。
