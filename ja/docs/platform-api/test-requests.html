リファレンス内でのテストリクエスト

スカラーリファレンスはリアルタイムでリクエストを送信します。サンドボックスゲートウェイがサーバーリストの先頭にあり、そこへ送信されたリクエストは実際のネットワークを経由します。シェルでも同じ呼び出しを実行できます。代わりにブラウザデモを選択すると、アカウントやローカルプロセスなしで結果がページ内に表示されます。

ブラウザデモの仕組み​

公開されているコントラクトには3つのターゲットが記載されています。そのうちの1つ（/software/api-mock）は、ユーザーが現在閲覧しているページに対応します。リファレンスページ内のリクエストハンドラーが、コントラクト自体のスキーマ例から生成されたレスポンスボディを使ってそのパスへのリクエストに応答します。

この設計により3つの問題が一度に解決されます：

  • 混合コンテンツブロックは禁止です。 HTTPS を経由して読み込まれたページでは、http://localhost を呼び出すことはできません。同じオリジンからのリクエストを避けることで、ブラウザによる拒否を防ぎます。
  • CORSのプリフライトチェックは行われません。 レスポンスがオリジンをまたぐことは一切ないため、許可すべき事項が存在しないからです。
  • サーバーを常に稼働させる必要はありません。 GitHub Pagesは静的なファイルを提供するため、静的ホストではモックサーバーを実行することができません。処理内容はユーザーのブラウザ内で実行されます。
レスポンスはコントラクトから返されます

各ボディはスキーマの例から生成されています。フィールド名、エンム（enum）、マイクロチップのパターン、およびRFC 9457の形状はすべて仕様に準拠しています。プロダクション環境またはサンドボックス環境を選択すると、実際のホストが対象となります。

最初のリクエストを送信してください​

  1. インタラクティブなAPIリファレンス を開いてください。
  2. サーバーのドロップダウンメニューに「Sandbox gateway」と表示されていることを確認してください。このルートでは認証情報は必要ありません。
  3. GET /animals/{animalId} を展開し、パス値として pet_krypto_210 を入力して、送信 を選択します。

レスポンスには、マイクロチップの情報（985141002348123）、狂犬病予防タグの情報（RB-2026-9921）、およびAVAILABLEのステータスが含まれます。

どのルートに認証情報が必要か​

養子縁組カタログおよびテスト用Webhookの送信を受け付けるルートは公開されたままです。養子縁組を希望する方はアカウントを作成する前にこのカタログを閲覧でき、受取側のテストには認証情報は不要です。その他のルートにはセキュリティ上の要件が適用されます。

ルートリクエスト
GET /animals公開カタログ。
GET /animals/{animalId}公開されている動物のプロフィール。
POST /applicants登録によりアカウントが作成されます。
POST /sessionsログインするとトークンが生成されます。
POST /webhooks/test-dispatch受信側のテストには認証情報は不要です。
その他すべての場合OAuth 2.0 ベアラートークン、またはキーを受け付けるルートでは X-API-Key を使用する。

ブラウザデモではこれらの要件が無視されるため、すべてのルートは認証情報なしで応答する。サンドボックスゲートウェイではこれらの要件がチェックされるため、デモでは成功するリクエストがサンドボックスゲートウェイでは失敗することがある。

リクエストの認証​

契約書には実際の認証サーバーが定義されているため、bludhaven_oauth のエントリーには貼り付けフィールドではなく 「Connect」 ボタンが表示される。「Connect」を押すと、サンドボックスゲートウェイで同意画面が表示される。

コンソールからの操作実行するアクションヘッダー
bludhaven_oauth「Connect」 → 認可 → 送信Authorization: Bearer <token>
api_keyPaste bpk_sandbox_pos_7f3a91c4X-API-Key: <key>

「register」キーは小売ルートを処理します。動物に関する情報を取得する場合は、bpk_sandbox_ops_2d8be05f を貼り付けてください。認証ガイド には、各公開キーがどのような処理を行うかが記載されています。

シェルからの操作ではこのパネルが省略され、ヘッダーが直接送信される。

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

ヘッダーを持たないセキュリティ対策が施されたルートでは、401 Unauthorized と共に ProblemDetails のボディおよび WWW-Authenticate のチャレンジが返される。架空のキーを使用すると同様に失敗する。ゲートウェイはその値を自身のレジストリで照会するからです。

実行する価値のあるフロー​

動物レコードを読み取る​

GET /animals/pet_krypto_210を送信します。応答として、ネストされた健康状態の記録および$150の預かり料金を含むAnimalスキーマが返されます。パス値をpet_krypto_999に置き換えても、ハンドラーはルートテンプレートにマッチするため引き続き応答します。

競合する保留を試みる​

POST /adoptions/holdsをanimal_idでpet_krypto_210に設定し、任意のapplicant_idを付けて送信してください。最初の呼び出しでは新しいホールドIDを持つ201 Createdが返され、30分間のexpires_atとseconds_remainingのカウントダウンが行われます。同じanimal_idで再送信すると、ハンドラーは409 Conflictを返し、あなたをブロックしたホールドのProblemDetailsボディを表示します。

最初の応答からホールドIDをコピーし、カウントダウン情報を確認するためにGET /adoptions/holds/{holdId}を、または動物を解放するためにDELETE /adoptions/holds/{holdId}を送信します。解放するとロックが解除され、次のホールド処理が正常に実行されます。このロックはページセッション中に有効であり、ページを再読み込むとリセットされます。

このフローは、クライアントがtype、title、detailをどのように処理するかを示し、失敗ではなく待機リストを提供します。

払い戻しを記録する​

POST /refundsを送信し、application_idをapp_2026_1188に設定し、amount_centsを10000に、reasonをCANCELLATION_AFTER_48Hに指定します。ハンドラーは預かり料金および必要な用品情報をbreakdownとして返し、差し押さえられた預かり料金やライセンス料金を明記します。調整処理ではこのデータが正確に読み取られます。

コントラクトで宣言されていない操作をリクエストする​

GET /animals/pet_krypto_210/notesを送信します。該当する操作は存在しないため、ハンドラーはProblemDetailsを含む404を返します。この応答によりクライアントが必要とするエラーメッセージが表示されます。

サンドボックスゲートウェイを呼び出す​

サンドボックスゲートウェイは実際のHTTPと同じデータを提供します。ブラウザを使用せずにすべての操作が処理されます。

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210

安全なルートにはこのゲートウェイが署名したトークン、または認識可能なキーが必要です。キーパスにはヘッダーのみが必要で、交換処理は不要です。

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

トークンパスは「mint」で始まります。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=write:animals"

レスポンスからaccess_tokenを次の呼び出しにコピーしてください。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'

そのヘッダーを除外すると、同じ呼び出しでは401とProblemDetailsのボディ、およびWWW-Authenticateのチャレンジが返されます。どちらかの種類の偽の値を送信すると、ゲートウェイは同じように応答します（署名を検証するかキーを照会するため）。write:animalsが欠けている本物の認証情報を送信すると、403とinsufficient_scopeが含まれた結果が返されます。

認証ガイドでは、同意画面、2つの公開キー、および10個のスコープについて説明されています。

この機能の動作はコンソールでの動作と同じです。POST /adoptions/holdsを2回送信し、その後にanimal_idを送信すると、ライブホールド（live hold）状態を示す409が返されます。そのIDをコピーしたら、GET /adoptions/holds/{holdId}を使ってカウントダウンを確認するか、DELETE /adoptions/holds/{holdId}を使って動物を解放します。

GET /healthには、ゲートウェイが読み込んだ契約内容、操作回数、ライブホールドの数、OAuthエンドポイント、および公開されたキーの数が記載されています。デプロイ後に実行して、ゲートウェイがネットワークに接続されていることを確認してください。

ストレージへの直接アップロード（事前署名済み）のテスト​

署名付きアップロードURLを生成し、アプリケーションAPIを経由せずにバイナリデータをストレージに直接ストリーミングします：

# 1. Request presigned upload URL (needs write:animals scope)
curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/photos \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"content_type": "image/jpeg", "caption": "Krypto in harbor yard"}'

範囲外の変更が加えられたり期限切れになった署名を送信するとupload_urlが返されます。正常にアップロードされると、検証済みのSHA-256チェックサムとパブリックCDN URLが含まれたPUTが返されます。

# 2. PUT binary file directly to storage endpoint
curl -X PUT "<UPLOAD_URL>" \
  -H "Content-Type: image/jpeg" \
  --data-binary "@photo.jpg"

篡改されたり期限切れになった署名が送信されると403 が返されます。正常にアップロードされると、検証済みのSHA-256チェックサムとパブリックCDN URLが含まれた200 が返されます。

シミュレートされた Webhook 送信のテスト​

署名済みのWebhookイベントを送信し、ローカルにあるHMAC受信者を検証してください。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/webhooks/test-dispatch \
  -H "Content-Type: application/json" \
  -o webhook-dispatch.json

ゲートウェイは完全なペイロードデータに署名を行い、その応答をwebhook-dispatch.jsonに書き込みます。node scripts/verify-webhook.mjs webhook-dispatch.jsonでその内容を確認してください。WebhookガイドではNode.jsおよびPythonにおける署名方法について説明されています。

参考コンソールでもこの呼び出しはWebhooksの項目にリストアップされています。Browser demoを使ってこの処理を実行すると、応答ヘッダーで署名が確認できます。なぜならデモ環境ではリクエスト時に署名が行われるからです。

保留がリセットされる場合があります

ゲートウェイは短期間使用されるエッジ環境で動作します。再利用されたエッジ環境では保持状態が失われるため、保持IDは処理完了直後に404に返されることがあります。そのため、404のデータを「解放済み」として読み取るのではなく、新しい保持処理を実行する必要があります。

各ターゲットが実行できること​

機能Browser demoSandbox gatewayProduction
配置済みのサイトで動作するかはいはいはい（認証情報が必要）
契約書の内容に忠実な文書を返すはいはいはい
採用状態マシンの実行を強制する保持し、読み取り、解放する保持し、読み取り、解放するYes
30分間のホールドTTLが適用されますカウントダウンのみ、リーパーはありませんカウントダウン、リーパーなし、リセット可能はい
リクエスト間でレコードを保持するリロードするまでのみ保持アイソレートがリセットされるまでのみ保持はい
認証情報が必要いいえはい（セキュリティで保護されたルートでは）はい

ターゲットシステムではリクエストボディをスキーマに基づいて検証していません。契約書（contract）に記述された構造に従って処理が行われ、ゲートウェイ（gateway）がその結果に応じて応答します。
