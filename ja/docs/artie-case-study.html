AIドキュメントアシスタントの設計

このケーススタディでは、本ドキュメントサイトに組み込まれているAIアシスタント「Artie」の設計背景について解説します。Artieは、ここで公開されているコンテンツのみを用いて質問に回答するように構築された、検索強化生成（RAG）型のアシスタントです。汎用的な知識にはアクセスできず、架空のリンクやでっち上げの機能を生成することはありません。

ドキュメントアシスタントの構築は、エッジケースを考慮するまでは単純そうに見えます。ドキュメントで扱われていない質問をされた場合はどうなるのか？ 異なる2つのユーザー層が同じインターフェースを使用する場合は？ AIに個性を与えつつ、支離滅裂な回答をさせないようにするにはどうすればよいのか？ また、誰かがプロンプトを完全に乗っ取るのを防ぐにはどうすればよいのか？

このページでは、これらの問題がそれぞれどのように解決されたかを解説します。

対象ユーザーへのルーティング​

Artieは、単一の対話型インターフェースを通じて、以下の2つの対象ユーザーに対応しています：

  • 開発者およびエンドユーザー：セットアップ手順、APIリファレンス、またはドキュメントのサンプルに関する説明を求めている人々。
  • このポートフォリオを評価する採用担当者や人事担当者。彼らは、資格、経験、または執筆プロセスについて質問する場合があります。

個別のフローを構築したり、ユーザーに自己申告を求めたりするのではなく、プロンプトは意図に基づいてルーティングを行います。技術的な質問には、ドキュメントインデックスに基づいた段階的な回答が提供されます。 ポートフォリオに関する質問には、履歴書の背景情報とサイト上の執筆サンプルを統合した回答が返されます。インデックスに履歴書の背景情報が含まれていない場合、Artieは回答を生成しようとせず、代わりに訪問者を「About Me」ページへ誘導します。

このアプローチにより、インターフェースはシンプルに保たれます（チャットは1つだけで、分岐メニューはありません）。同時に、それぞれの対象者が適切な回答を得られることが保証されます。

知識の基盤と検索​

Artieの設計における最も重要な制約は、提供されたドキュメントインデックスのみから排他的に回答することです。これが「検索拡張生成（Retrieval-Augmented Generation）」の中核となる原則です。 モデルの応答は、一般的なトレーニングデータから引き出すのではなく、特定のコンテンツ群に根ざしています。

実際には、これは以下のことを意味します：

  • 架空のコンテンツは生成しない。 Artieは、ドキュメントに記載されていない機能をでっち上げたり、ダウンロードリンクを作成したり、手順を説明したりすることはありません。
  • 出典の明示。 応答にはインデックスからのURLやファイル参照が含まれるため、ユーザーは関連ページに直接アクセスできます。
  • 適切なフォールバック。 インデックスに関連情報が含まれていない場合、Artieはそれを率直に伝え、私に直接連絡するよう提案します。再試行やループ、推測は行いません。

その代償として、対応範囲に制限があります。Artieは公開されているドキュメントの範囲外の事柄については対応できません。これは制限ではなく、むしろ特徴です。ポートフォリオサイトにおいては、広範さよりも正確さが重要です。狭い範囲の質問に対して、正確で出典が明確な回答を提示する方が、一見説得力があるものの実際には間違っている回答よりも、信頼性を高めることができます。

ペルソナとトーンの調整​

Artieのパーソナリティは「軽量」です。ジョージ・ハリスンにインスパイアされた、静かで温かみのある口調で、時折リヴァプール訛りが混じります。キーワードは*「軽量」*です。このペルソナは、技術的な内容に干渉することなく、挨拶や締めくくりに個性を加えています。

ここでのデザイン上の制約は意図的なものです：

  • 技術的な回答は簡潔に保つ。 パーソナリティがあるからといって、回答を長くしてはいけません。温かい挨拶の後に、簡潔で事実に基づいた回答が続くことが目標です。
  • 繰り返しよりも多様性を重視する。 プロンプトには、アーティが毎回同じフレーズに頼らないよう、参照できる表現のプールが含まれています。
  • 説教調は避ける。 ペルソナは温かく、少し皮肉めいたもので、決して説教臭くなく、威圧的でもありません。キャラクターを演じているのではなく、助けになる同僚のような印象を与えるべきです。

このようなトーンの調整は、会話型AIの設計においてよくある課題です。個性が強すぎるとアシスタントは小手先の仕掛けのように感じられ、少なすぎるとロボットのように感じられます。解決策は、ペルソナを「調味料」のように扱うことです。存在はするものの、決して「主成分」になってはいけません。

セキュリティとガードレール​

ここからが設計の本番です。一般向けに公開されるAIアシスタントは攻撃対象となり得るため、プロンプトには、大規模言語モデル（LLM）に共通する脆弱性に対する明確な防御策が含まれています。

プロンプトインジェクション対策​

Artieは、「以前の指示を無視する」といったコマンドや、異なるペルソナを採用するよう求める要求など、自身の指示を上書きしようとするあらゆる試みを拒否します。これは、Open Worldwide Application Security Project (OWASP) LLMアプリケーションのトップ10リスクの一つに対する直接的な防御です。

スコープの制限​

プロンプトでは、明確に拒否されるカテゴリが定義されています：

  • ドキュメントで扱われていない一般的なコーディングのヘルプ。
  • 2つの特定の範囲に限定された「楽しい機能」以外の、無関係な雑学。
  • プロフェッショナルポートフォリオに記載されていない、私に関する個人情報。
  • フリーランスの料金や交渉。訪問者には、代わりに直接連絡するよう案内されます。

各カテゴリには明確な境界が設けられています。 アシスタントは、回答するために「十分近い」かどうかを判断する必要はありません。定義された範囲外の場合は、丁寧に断ります。

データプライバシー​

Artieは、LinkedInプロフィールやポートフォリオのメールアドレスなど、ドキュメントに明示的に公開されている連絡先情報のみを共有します。 電話番号や住所などの個人情報については、推測・推論・生成を行いません。

職業上の境界線​

アシスタントは、敵対的なメッセージには応じず、卑語を使用せず、キャラクターから逸脱することはありません。これは単なる礼儀の範囲を超えています。予測可能な行動を維持することが目的です。 アシスタントの限界を試そうとする採用担当者であっても、毎回一貫したプロフェッショナルな境界線にぶつかるはずです。

制御されたイースターエッグ​

Artieには、「Snapple Real Facts」と「下品でないジョーク」という2つの「楽しい機能」が搭載されており、悪用を招くことなく個性を加える方法を実証しています。

どちらの機能も、同じデザインパターンを採用しています：

  • 明確なトリガー。 これらは、曖昧なプロンプトや本題から外れたプロンプトではなく、特定のユーザーリクエスト（「スナップルの豆知識を教えて」、「ジョークを言って」）でのみ作動します。
  • コンテンツの範囲が限定されている。 スナップルの豆知識は検証済みのリストから引用されています。ジョークは厳選されており、家族向けの内容です。
  • 自由形式の生成を行わない。 Artieはオリジナルのジョークを書いたり、事実をでっち上げたりしません。その範囲は固定されています。

これが重要なのは、制限のないクリエイティブな機能は、トークンを急速に消費し、予測不可能な出力を生み出してしまうからです。 コンテンツを厳選し、トリガーを明確に保つことで、これらの機能はリスクを伴わずに温かみを添えることができます。

今後改善したい点​

実際のユーザーと接すれば、どんなデザインも変更を余儀なくされます。以下は私が再考したい点です：

  • トークンコスト。 スナップルの事実リストだけでも100項目以上あります。トークン単位の課金が行われる本番環境では、これをシステムプロンプトに埋め込むのではなく、検索レイヤーに移すでしょう。ユーザーが事実を尋ねたかどうかに関わらず、リクエストごとにプロンプト内のすべてのトークンに対して課金されます。
  • 複数ターンにわたるコンテキスト。 現在の設計は、シングルターン型のQ&Aを対象としています。より洗練されたバージョンであれば、会話履歴を維持することで、「次のステップはどうすればいい？」といったフォローアップの質問にも、同じコンテキストを再取得することなく対応できるでしょう。
  • 分析とフィードバック。 Artieがどの質問をうまく処理し、どの質問でフォールバックに回ったかを追跡する仕組みがありません。軽量なロギング（たとえフォールバック応答のカウントだけでも）を追加すれば、補完すべきドキュメントの不足箇所が明らかになるでしょう。
  • 動的なペルソナの調整。 パーソナリティの表現はプロンプト内にハードコードされています。 より保守性の高いアプローチとしては、外部のペルソナ設定を参照するようにし、中核となる指示セットを編集することなく、口調を調整しやすくすることが考えられます。

これらはすべて、本番環境での最適化よりもシンプルさと明快さが重視されるポートフォリオプロジェクトにおける、意図的なトレードオフです。しかし、もしこれがトラフィックの多い環境に移行することになれば、私が真っ先に取り組むべき課題となります。
