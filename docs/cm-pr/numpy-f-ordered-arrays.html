F-ordered array fix

Problem statement​

Protobuf encode/decode of NumPy arrays fails if they were F-ordered

Testing​

import numpy

from mcbackend.npproto.utils import ndarray_from_numpy, ndarray_to_numpy

arrC = numpy.array([
    [1,2,3],
    [4,5,6],
], order="C")

arrF = numpy.array([
    [1,2,3],
    [4,5,6],
], order="F")

assert arrC.strides != arrF.strides

numpy.testing.assert_array_equal(
    arrC,
    ndarray_to_numpy(ndarray_from_numpy(arrC)),
)
numpy.testing.assert_array_equal(
    arrF,
    ndarray_to_numpy(ndarray_from_numpy(arrF)),
)

Commit message​

Fix encoding/decoding of F-ordered NumPy arrays

`bytes(arr.data)` materializes the buffer contents in C order, so encoding a
Fortran-ordered array pairs C-ordered bytes with Fortran strides. Decoding
then reads those bytes with the wrong strides and returns a scrambled array.

Record the memory order in a new `order` field of the `Ndarray` message, and
let `ndarray_to_numpy` transpose and reshape when that field reports "F".
Buffers encoded before 0.2.4 have an empty `order` field, so decoding them
yields C-ordered arrays.

Closes #63

Pull request​

Summary​

Protobuf round-tripping corrupts NumPy arrays that use Fortran order. A Fortran-ordered array comes back with its values in the wrong positions. The decoder raises nothing, and the caller accepts a scrambled array.

Round-trip test
arrF = numpy.array([[1, 2, 3], [4, 5, 6]], order="F")
numpy.testing.assert_array_equal(
    arrF,
    ndarray_to_numpy(ndarray_from_numpy(arrF)),  # returns [[1, 3, 5], [2, 4, 6]] without the fix
)

Root cause​

ndarray_from_numpy stores the raw buffer next to the array strides, and those two values describe different memory layouts:

  1. Encode: bytes(arr.data) materializes the buffer in C order, so a Fortran-ordered source array yields C-ordered bytes.
  2. Strides: ndarray_from_numpy copies strides unchanged, so they still describe the Fortran layout.
  3. Decode: numpy.ndarray(buffer=..., strides=...) applies Fortran strides to C-ordered bytes. Those offsets address the wrong cells and return the wrong values.

Fix​

Record the memory order during encode. Replay it during decode.

  • protobufs/npproto/ndarray.proto and the generated mcbackend/npproto/__init__.py gain an order string field (tag 5) on the Ndarray message.
  • mcbackend/npproto/utils.py writes order="CF"[arr.flags.f_contiguous] during encode. A Fortran-ordered array stores "F". During decode, ndarray_to_numpy transposes and reshapes when nda.order == "F". That step rebuilds the Fortran layout from the C-ordered bytes.
  • mcbackend/test_npproto.py adds test_byteorders, which parametrizes shape and order together.

Tests​

TestUtils.test_byteorders parametrizes shape and order together. Each of (5,), (2, 3), (2, 3, 5), and (5, 2, 1, 7) runs twice, once per memory order. Every case asserts that nda.order matches arr.flags.f_contiguous, then round-trips the array through encode and decode.

TestUtils.test_conversion still covers the int, float, scalar, string, object, and datetime dtypes.

Notes​

  • Bumps the version to 0.2.4.
  • ndarray_to_numpy gains the transpose step and keeps the existing buffer and dtype handling.
  • Buffers encoded before 0.2.4 have an empty order field. Decoding one of those yields a C-ordered array.

How to test​

Verify the fix
pytest mcbackend/test_npproto.py

The suite runs the new test_byteorders cases in both memory orders and re-runs the existing dtype cases.
