معالجة ويبهوكسات المدفوعات

  • الجمهور المستهدف: المطورون الذين لديهم عمليات دفع ويحتاجون إلى آلية تنفيذ طلبات موثوقة.
  • المتطلبات المسبقة: نقطة النهاية خادم قابلة للوصول عبر رابط HTTPS، بالإضافة إلى كلمة المرور السرية من لوحة تحكم خدمة Stripe.
  • الهدف: قبول حدث من خدمة payment_intent.succeeded، التحقق من توقيعه، وتنفيذ الطلب مرة واحدة فقط.

في نهاية الدورة التعليمية، سيكون لديك معالج يرفض البيانات المزورة ويسجل كل طلب مرة واحدة، وكل ذلك ضمن الوقت المحدد للاستجابة. لاحظ أن التحقق من التوقيع يتم قبل تنفيذ أي منطق تجاري.

تقوم خدمة Stripe بإرسال ويبهوكس عندما يتغير حالة الطلب؛ يتلقى نقطة النهاية الخاصة بك الحدث، تتحقق من التوقيع، ثم تتصرف وفقًا لذلك. يجب على المعالج الاستجابة ضمن الوقت المحدد، لأن خدمة Stripe تعتبر الاستجابة البطيئة علامة على فشل في التسليم وتعيد المحاولة.

مسار التسليم​

تقوم خدمة Stripe بإرسال الحدث إلى نقطة النهاية الخاصة بك (endpoint) خلال ثوانٍ قليلة من حدوث التغيير في الحالة (state change). يقوم معالج الحدث (handler) بالاستجابة بحالة تبليغ عن اكتمال المعالجة (“2xx”)، ثم يتم معالجة الحدث نفسه.

الخطوات المرقمة متبعة لترتيب معين؛ توضح الخطوة رقم ٧ أن الحدث يحدث بعد أن رأى العميل النتيجة بالفعل، لذا لا يمكن للعميل أن يكون محفزًا لإتمام العملية.

قم بتكوين نقطة النهاية​

قم بتسجيل نقطة النهاية في لوحة التحكم (Dashboard) تحت المطورون (Developers) → Webhooks → إضافة نقطة النهاية (Add endpoint). ستعرض شركة Stripe كلمة المرور السرية (Signing Secret) عند إنشاء نقطة النهاية، وستظهر هذه الكلمة مرة أخرى لاحقًا في لوحة التحكم.

الإعدادالقيمة
عنوان نقطة النهايةhttps://api.example.com/webhooks/stripe
الأحداث التي يتم إرسالهاpayment_intent.succeeded, payment_intent.payment_failed, charge.refunded
إصدار الواجهة البرمجية التطبيقية (API Version)الإصدار الذي كتبت عليه معالج الطلبات (Handler).

المعالج الذي يشترك في جميع الأحداث لا يقرأ أي بيانات يتم إرسالها؛ اختر الأحداث التي يتفاعل معها المعالج، وأضف المزيد من الأحداث عند تغيير الكود.

ملاحظة

قد يختلف إصدار نقطة النهاية عن إصدار حسابك؛ يتم تنفيذ الأحداث وفقًا للإصدار المرتبط بنقطة النهاية، لذا قم بقراءة قيمة api_version عند تسجيل البيانات المرسلة.

قراءة البيانات الخام​

يتطلب التحقق من التوقيع البايتات الدقيقة التي ترسلها شركة Stripe؛ فإن تحليل البيانات إلى كائن يؤدي إلى فقدان المسافات البيضاء وترتيب المفاتيح، مما يؤدي إلى فشل عملية التحقق من التوقيع.

server.js
import express from "express";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const app = express();

// Keep the raw body for the webhook route only.
app.post(
  "/webhooks/stripe",
  express.raw({ type: "application/json" }),
  handleWebhook
);

// Every other route parses JSON.
app.use(express.json());

قم بتسجيل محلل البيانات الخام قبل محلل JSON، وإلا سيقوم محلل JSON بتناول البيانات أولاً، مما يؤدي إلى حصولك على بيانات خام فارغة وعدم تطابق في التوقيع مع كل طلب.

التحقق من التوقيع​

تقوم شركة Stripe بتوقيع كل عملية تسليم باستخدام مفتاح سري (endpoint secret). يتم حساب التوقيع المتوقع ومقارنته في وقت ثابت.

server.js
async function handleWebhook(req, res) {
  const signature = req.headers["stripe-signature"];

  let event;

  try {
    event = stripe.webhooks.constructEvent(
      req.body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET
    );
  } catch (err) {
    console.error("Signature verification failed:", err.message);
    return res.status(400).send(`Webhook error: ${err.message}`);
  }

  res.status(200).json({ received: true });

  await dispatch(event).catch((err) => {
    console.error("Handler failed:", err.message);
  });
}

يقوم الاستدعاء constructEvent بإعادة حساب التوقيع ويرفض أي بيانات (payload) قديمة جدًا، ثم يُرجع رسالة تفيد بحدوث الحدث. تتم جميع هذه العمليات قبل أن يتمكن كودك من الوصول إلى البيانات نفسها.

خطر

لا تثق أبدًا في أي بيانات غير مؤكدة الصحة؛ فبدون فحص التوقيع، يمكن لأي شخص يعرف عنوان نقطة النهاية (endpoint) أن يعلن عن دفع الطلبات أو يطلب استرداد المبالغ.

رد قبل البدء في التنفيذ​

تنتظر شركة Stripe حوالي 20 ثانية للحصول على رد؛ إذا لم يتم الرد في هذا الوقت، فإن المعالج المسؤول عن تنفيذ الطلب لن يتمكن من إرسال البريد الإلكتروني، مما يزيد من خطر حدوث أخطاء. في هذه الحالة، تقوم شركة Stripe بتكرار عملية المعالجة.

قسّم عملية المعالجة إلى مرحلتين:

  1. التأكيد. تحقق من التوقيع وأرسل الرمز 200.
  2. المعالجة. قم بتحويل المهمة إلى عامل قادر على إعادة محاولة تنفيذ العملية البطيئة.

يقوم المثال أدناه بتنفيذ الاستدعاء dispatch مباشرةً بعد الحصول على الاستجابة. يجب نقل هذا الاستدعاء إلى قائمة انتظار (queue) عندما يستغرق التنفيذ وقتًا أطول من المتوقع.

dispatch.js
async function dispatch(event) {
  switch (event.type) {
    case "payment_intent.succeeded":
      return handleSucceeded(event.data.object);
    case "payment_intent.payment_failed":
      return handlePaymentFailed(event.data.object);
    case "charge.refunded":
      return handleRefunded(event.data.object);
    default:
      return;
  }
}

نوع الحدث المجهول ليس خطأً؛ فشركة Stripe تضيف أنواع أحداث جديدة مع مرور الوقت، والمعالج (handler) الذي يستجيب لنوع حدث غير معروف قد يفشل في إتمام عملية التسليم، بينما كان من الممكن تجاهل هذا النوع من الأحداث.

يتم تنفيذ المهمة مرة واحدة فقط​

تقوم خدمة Stripe بإعادة محاولة تسليم الطلبات التي فشلت في التسليم، وقد تقوم أيضًا بتسليم نفس الحدث مرتين عندما يكون الرد بطيئًا. يجب على معالج الطلبات (handler) أن يتحمل وجود النسخ المكررة من هذه البيانات.

fulfillment.js
async function handleSucceeded(intent) {
  const already = await hasProcessed(intent.id);
  if (already) return;

  const orderId = intent.metadata.order_id;
  if (!orderId) {
    console.warn("Missing order_id on intent", intent.id);
    return;
  }

  await markOrderPaid(orderId, intent.id);
  await recordProcessed(intent.id);
}

قم بتخزين معرف الحدث (event ID) أو معرف الكائن (object ID) في فهرس فريد، واجعل قاعدة البيانات ترفض أي محاولة كتابة ثانية؛ فعند وصول عمليتين في نفس الوقت، قد يحدث تنافس بينهما. لا يمكن لقيود الفريدية أن تمنع هذا التنافس.

تلميح

استخدم event.id كمفتاح لجدول إزالة التكرار (deduplication table) للأحداث ذات المرة الواحدة، وobject.id للأحداث المتكررة. عملية استرداد المبلغ تنتج حدثًا واحدًا من نوع charge.refunded لكل عملية استرداد. يتم تجنب تكرار معرف الكائن فقط في حالات الرسوم المتكررة.

التعامل مع أحداث الفشل​

في حال فشل عملية الدفع، يتم إرسال رمز الرفض (payment_intent.payment_failed). قم بقراءة هذا الرمز واتخاذ قرار بشأن ما إذا كان بإمكان العميل استرداد المبلغ أم لا.

failures.js
async function handlePaymentFailed(intent) {
  const error = intent.last_payment_error;
  const code = error?.decline_code ?? error?.code;

  const recoverable = ["insufficient_funds", "processing_error"];
  const canRetry = recoverable.includes(code);

  await recordDecline(intent.metadata.order_id, code, canRetry);

  if (canRetry) {
    await sendRetryEmail(intent.metadata.order_id);
  }
}

اختبار نقطة النهاية محليًا:​

تقوم أداة سطر الأوامر «Stripe» بإعادة توجيه أحداث الاختبار الحية إلى خادم محلي، مما يتيح لك مراقبة عملية التسليم دون الحاجة إلى النشر.

لا تحاول إعادة محاولة الدفع بعد الرفض القاطع وفقًا لجدولك الزمني الخاص. فقد قام مُصدر البطاقة بحظرها، ومحاولة الدفع مرة أخرى لن تؤدي إلا إلى إضافة رفض آخر إلى سجل الحساب.

stripe login
stripe listen --forward-to localhost:4242/webhooks/stripe

يطبع الأداة سر توقيع يبدأ بـ whsec_؛ استخدم هذه القيمة محليًا، واستخدم سر اللوحة التحكم (Dashboard secret) في البيئة الإنتاجية. ثم قم بتشغيل حدث من تطبيق ترمينال آخر.

stripe trigger payment_intent.succeeded

يعرض المحطة الأولى تفاصيل الحدث، بينما يعرض سجل الخادم نتائج تنفيذ الكود المسؤول عن معالجة الطلب. قم بتغيير القيمة المستخدمة كـ “سر” (secret) إلى قيمة خاطئة، ثم تأكد من أن نقطة النهاية (endpoint) تُرجع القيمة 400، وهو ما يثبت أن عملية التحقق من التوقيع (signature check) قد تمت بنجاح.

تشخيص حالة فشل في التسليم​

العرضالسببالحل
400 في كل عملية تسليمفشلت عملية التحقق من التوقيع.استخدم سر نقطة النهاية (endpoint secret).
بعد ترقية المكتبة، ظهر الرمز 400.قام المحلل (parser) بتغيير محتوى النص قبل عملية التحقق.تم نقل المحلل الخام (raw parser) إلى موقع يسبق المحلل الذي يعالج الرمز JSON.
تم تكرار عملية التسليم مرة واحدة.انتظر المعالج (handler) لفترة أطول من المدة المحددة (timeout).يجب الاعتراف بالطلب أولاً، ثم معالجته في وحدة العمل (worker).
تُظهر سجلات المعالجة (Handler logs) وجود حالات مكررة.تم تجاوز وقت الاستجابة (timeout)، أو تداخلت محاولات إعادة الاتصال.يتم إزالة التكرارات في البيانات المتعلقة بالأحداث المتكررة عند القيمة object.id، وفي البيانات المتعلقة بالأحداث غير المتكررة عند القيمة event.id.
لا يتم أي توصيلات على الإطلاقعنوان نقطة النهاية (endpoint) فشل في اختبار الحالة الصحية (health check).تأكد من أن العنوان يُرجع قيمة 2xx عند إجراء اختبار من لوحة التحكم (Dashboard).

إعادة إرسال حدث قديم​

لإعادة إرسال حدث قديم، افتح لوحة التحكم، ثم اختر Developers → Webhooks → نقطة النهاية الخاصة بك → Events، واختر الحدث المراد إعادة إرساله ثم اختر Resend

تحتفظ لوحة التحكم بحمولات الأحداث وتتيح لك إعادة إرسال إحداها. افتح المطورون → Webhooks → نقطة النهاية الخاصة بك → الأحداث، وحدد عملية التسليم، ثم اختر إعادة الإرسال.

إعادة الإرسال توفر لك أقصر طريقة لاختبار تغيير في معالجة البيانات (handler) باستخدام بيانات حقيقية (real payload). قم بتسجيل رمز الاستجابة (response code)، لأن إعادة الإرسال التي تُرجع قيمة 500 ستفشل أيضًا في البيئة الحقيقية.

الخطوات التالية​

  • قبول دفعة ببطاقة لنقطة النهاية على الخادم التي تنشئ هذه الطلبات.
  • الطلبات غير المتأثرة بتكرار الإجراءات ضمن قواعد إعادة المحاولة للمكالمات الصادرة.
  • ترقية وإصدارات واجهات برمجة التطبيقات للإصدار المرتبط بنقطة النهاية (endpoint).
  • وثائق خدمة الويبكوت (Webhook) الخاصة بـ Stripe للحصول على قائمة كاملة بالأحداث.
