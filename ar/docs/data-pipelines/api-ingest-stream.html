  • واجهة برمجة التطبيقات لاستيراد السجلات

استيراد الأحداث باستخدام واجهة برمجة التطبيقات (API) لاستيراد السجلات في Datadog

تدعم هذه الواجهة استيراد كميات كبيرة من البيانات في الوقت الفعلي، سواء كانت مهيكلة أو شبه مهيكلة.

الإجراءات المدعومة بواسطة هذه الواجهة​

  • إرسال السجلات مباشرةً من التطبيقات السحابية دون تثبيت وكيل Datadog.
  • تطبيق معالجات خطوط العمليات (pipeline processors)، مثل Grok Parser وRemapper وLookup Processor، على البيانات الواردة.
  • توجيه سجلات المسارات (route logs) إلى فهارس (indexes) أو أرشيفات (archives) أو وجهات إشعار (alert destinations) بناءً على المحتوى.
  • تقليل تكلفة الفهرسة عن طريق دمج هذا النقطة النهائية (endpoint) مع قواعد أخذ العينات (sampling) والتصفية (filtering).
ملاحظة

راجع مفاتيح واجهة برمجة التطبيقات (API) لـ Datadog لإدارة بيانات الاعتماد.

قبل أن تبدأ​

تأكد من أن لديك:

  • مفتاح واجهة برمجة التطبيقات (API Key) الخاص بـ Datadog مع صلاحيات استيراد السجلات (log ingestion permissions). يمكن العثور عليه في إعدادات المنظمة (Organization Settings) → مفاتيح واجهات برمجة التطبيقات (API Keys).
  • عنوان موقع Datadog الخاص بك؛ يختلف هذا العنوان حسب المنطقة:
المنطقةعنوان الموقع
الولايات المتحدة الشرقيةdatadoghq.com
US3 Westus3.datadoghq.com
US5 Centralus5.datadoghq.com
الاتحاد الأوروبيdatadoghq.eu
AP1 Japanap1.datadoghq.com
AP2 أسترالياap2.datadoghq.com
  • يجب أن يكون تطبيق curl أو Postman مثبتًا.
  • يجب أن تكون بيانات السجلات مُنسقة وفقًا لتنسيق JSON.

نقطة الاستيراد​

POST https://http-intake.logs.{dd_site}/api/v2/logs

قم باستبدال {dd_site} بعنوان الموقع الخاص بمنطقتك، مثل datadoghq.com أو ap2.datadoghq.com.

رؤوس الطلب​

الرأسالقيمةإلزاميالوصف
DD-API-KEY<your_api_key>نعممفتاح API الخاص بك في Datadog
Content-Typeapplication/jsonنعمتنسيق البيانات المرسلة
Content-Encodinggzipاختياريتنسيق البيانات المضغوط؛ يوصي Datadog باستخدامه للدفعات ذات الحجم الكبير.

جسم الطلب​

جسم الطلب عبارة عن مصفوفة من كائنات السجلات. كل كائن سجلات يحتوي على الحقول التالية:

الحقلالنوعإلزاميالوصف
messageنصنعممحتوى رسالة السجل
ddsourceنصموصى بهاسم التكامل الخاص بالتقنية الذي يأتي منه السجل، مثل python أو nginx
ddtagsنصاختياريعلامات فاصلة (comma-separated tags)، مثل env:prod,team:payments
hostnameنصاختيارياسم الجهاز الذي أنشأ السجل
serviceنصموصى بهاسم التطبيق أو الخدمة
statusنصموصى بهشدة حدث السجل، مثل info أو ERROR
timestampنصاختياريوقت الحدث، مثل 2025-11-15T08:30:00Z. راجع ملاحظة تنسيق التوقيت.
ملاحظة

تم تضمين الرمز message. تستخدم خدمة Datadog الرموز service وddsource وddtags لتصفية البيانات وتنظيمها ومطابقتها؛ بينما الحقول الأخرى اختيارية.

مثال على بيانات السجلات​

Payload: single log
[
  {
    "message": "Transaction failed: Gateway timeout",
    "ddsource": "java",
    "ddtags": "env:prod,region:us-east-1",
    "hostname": "payments-host-01",
    "service": "payment-gateway",
    "status": "ERROR",
    "timestamp": "2025-11-15T08:30:00Z",
    "transaction_id": "txn_998877",
    "customer_id": "cus_554433"
  }
]
ملاحظة

استخدم تنسيق التوقيت العالمي الموحّد (UTC) وفقًا لمعيار منظمة التوحيد الدولية (ISO) 8601 للقيمة timestamp. تقوم خدمة Datadog بمطابقة خط زمن السجلات في أداة Log Explorer مع هذه القيمة؛ أما السجلات التي لا تحتوي على توقيت فإنها تستخدم وقت الاستيراد. تقبل خدمة Datadog توقيتًا يعود إلى ما يصل إلى 18 ساعة مضت.

مثال على استخدام أمر cURL​

cURL
export DD_API_KEY="your_datadog_api_key_here"
export DD_SITE="datadoghq.com"

curl -X POST "https://http-intake.logs.$DD_SITE/api/v2/logs" \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "message": "Transaction failed: Gateway timeout",
      "ddsource": "java",
      "ddtags": "env:prod,region:us-east-1",
      "hostname": "payments-host-01",
      "service": "payment-gateway",
      "status": "ERROR",
      "transaction_id": "txn_998877"
    }
  ]'

أكواد الاستجابة​

الكودالحالةالوصف
202تم قبول الطلبتم قبول البيانات وتم إدراجها في قائمة الانتظار للفهرسة
400طلب غير صحيحخطأ في التنسيق أو التحقق من صحة البيانات
401غير مصرح بهرأس البيانات (header) DD-API-KEY مفقود.
403ممنوعمفتاح الواجهة البرمجية الخاص بك غير صالح أو لا يحتوي على صلاحيات لاستيعاب السجلات
408انتهاء مدة الطلبانتهت مدة تنفيذ الطلب؛ حاول مرة أخرى بعد فترة قصيرة
413حجم البيانات كبير جدًايتجاوز حجم البيانات 5 ميغابايتات (بدون ضغط)
429عدد الطلبات مفرطتجاوز العميل الحد الأقصى لعدد الطلبات
500خطأ داخلي في الخادمواجهت Datadog مشكلة غير متوقعة؛ حاول مرة أخرى بعد فترة قصيرة
503الخدمة غير متاحةيعمل Datadog بكامل طاقته؛ حاول مرة أخرى بعد فترة قصيرة

تم قبول 202 طلبًا​

تأكيد استلام Datadog للبيانات من خلال رد برمجي برقم 202 Accepted؛ يحتوي جسم الرد على كائن فارغ من نوع JSON، وتظهر السجلات في أداة “Log Explorer” خلال ثوانٍ قليلة.

Response: 202 Accepted
HTTP/1.1 202 Accepted
Content-Type: application/json
Response body: 202 Accepted
{}

400: طلب غير صالح​

رد برمجي رقم 400: يُرجع عند فشل التحقق من صحة البيانات المرسلة

ردود برمجية رقم 401 و403: يُرجع عند غياب الرأس المطلوب أو عند فشل التحقق من صحة مفتاح الواجهة البرمجية أو عدم وجود صلاحيات لاستيعاب السجلات.

  • رد برمجي رقم 413: يُرجع عندما يتجاوز حجم البيانات المرسلة 5 ميغابايتات (بدون ضغط).
  • المحتوى المرسل يفتقر إلى الحقل الإلزامي message.
  • الحجم غير المضغوط يتجاوز الحد الأقصى وهو 5 ميجابايت.
Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Invalid JSON",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

رسالة خطأ 401: عدم الصلاحية؛ رسالة خطأ 403: المحتوى ممنوع​

يقوم Datadog بإرجاع القيمة 401 Unauthorized عندما يكون رأس البيانات (DD-API-KEY) غائبًا. كما يقوم Datadog بإرجاع القيمة 403 Forbidden عندما تفشل عملية التحقق من صحة مفتاح الواجهة البرمجية (API key) أو عندما لا تتوفر صلاحيات استيراد السجلات (log ingestion permissions).

Response: 403 Forbidden
{
  "errors": [
    {
      "detail": "Forbidden",
      "status": "403",
      "title": "Forbidden"
    }
  ]
}

حجم البيانات (payload) 413 كبير جدًا​

يقوم Datadog بإرجاع هذا الكود عندما يتجاوز حجم بيانات الطلب ٥ ميغابايتات (MB) قبل فك ضغطها.

Response: 413 Payload Too Large
{
  "errors": [
    {
      "detail": "Payload too large",
      "status": "413",
      "title": "Payload Too Large"
    }
  ]
}

هناك 429 طلبًا أكثر من اللازم​

لقد أرسلت عددًا كبيرًا جدًا من الطلبات؛ يرجى إرسال عدد أقل منها، أو دمج كائنات السجلات في مجموعة واحدة ضمن حمولة البيانات (array payload).

أخطاء قابلة لإعادة المحاولة​

يقوم Datadog أيضًا بإرجاع القيم 408 Request Timeout, 500 Internal Server Error, و503 Service Unavailable في حالات الأعطال المؤقتة. يجب إعادة تنفيذ الطلب باستخدام طريقة التأخير التصاعدي (exponential backoff). إذا استمرت المشكلة (408 Request Timeout)، يجب إرسال دفعات أصغر من البيانات.

تجميع سجلات النشاط​

الحدود:

Payload: batched logs
[
  {
    "message": "User login succeeded",
    "service": "auth-service",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "INFO"
  },
  {
    "message": "Transaction failed: Gateway timeout",
    "service": "payment-gateway",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "ERROR",
    "transaction_id": "txn_998877"
  }
]

الحدود:

  • حجم الحمولة: 5 ميغابايت بدون ضغط.
  • حجم السجل الفردي: 1 ميغابايت.
  • عناصر المصفوفة: 1,000 كائن سجل

حالات الاستخدام الشائعة​

  • استيراد سجلات الخدمات المصغرة (microservices) دون نشر وكيل Datadog.
  • إرسال أحداث منظمة من الدوال “serverless” مثل Amazon Web Services (AWS) Lambda أو Google Cloud Run.
  • بيانات القياس من أجهزة إنترنت الأشياء (IoT) أو الخدمات الطرفية.
  • توجيه الأحداث المُعززة إلى معلومات الأمان وأنظمة إدارة الأحداث (SIEM)، أو إلى وجهات التنبيه عبر خطوط السجل (Log Pipelines).
  • تقديم السجلات (logs) من خطوط العمليات المتكاملة المستمرة (Continuous Integration/Continuous Delivery – CI/CD) أو سكريبتات التنشيط (deployment scripts).

استكشاف وإصلاح المشاكل​

المشكلةالسبب المحتملالحل
401 Unauthorizedمفتاح الواجهة البرمجية (API) غير صحيح أو مفقودتحقق من قيمة DD_API_KEY في إعدادات المنظمة → مفاتيح الواجهات البرمجية.
400 Bad Requestالبيانات غير صحيحة الشكليرجى التحقق منها مع jq . payload.json قبل الإرسال.
لا تسجل الدخول باستخدام متصفح المستكشف (Explorer)استخدم فلتر خاص بأنظمة السجلات لاستبعاد بعض السجلاتقم بمسح جميع الفلاتر (Clear filters). بعد ذلك، راجع قواعد توجيه المؤشرات في النظام (index routing rules).
تاريخ الوقت غير مرتب بشكل صحيحالتنسيق غير متوافق مع معايير UTC أو ISO 8601، أو أقدم من 18 ساعةاستخدم التنسيق "2025-11-15T08:30:00Z". يجب إرسال السجلات خلال 18 ساعة من وقوع الحدث.
429 Too Many Requestsتم تجاوز حد التكرار (Rate Limit)دمج كائنات السجلات في مجموعة واحدة من البيانات (Batch log objects into one array payload).
