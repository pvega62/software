पेमेंट वेबहुक्स (Payment Webhooks) को संभालना

  • लक्षित दर्शक: वे डेवलपर जिनके पास पेमेंट प्रक्रिया है एवं जिन्हें एक विश्वसनीय ऑर्डर पूर्ति तंत्र की आवश्यकता है।
  • पूर्वापेक्षाएँ (Prerequisites): एक सर्वर एंडपॉइंट जो HTTPS के माध्यम से पहुँचा जा सके, एवं स्ट्राइप डैशबोर्ड से प्राप्त हुआ “साइनिंग सीक्रेट” (signing secret)।
  • लक्ष्य: payment_intent.succeeded इवेंट को स्वीकार करें, उसके हस्ताक्षर की जाँच करें, एवं ऑर्डर को केवल एक बार ही पूरा करें।

अंत तक, आपके पास ऐसा हैंडलर (handler) होगा जो जाली डेटा को अस्वीकार करेगा एवं प्रत्येक ऑर्डर को एक बार ही रिकॉर्ड करेगा; सब कुछ प्रतिक्रिया की समय-सीमा (response timeout) के भीतर होगा। ध्यान दें कि हस्ताक्षर-जाँच (signature check) किसी भी व्यावसायिक लॉजिक (business logic) से पहले ही होती है।

जब किसी ऑब्जेक्ट की स्थिति बदलती है, तो स्ट्राइप एक वेबहुक (webhook) भेजता है। आपका एंडपॉइंट उस इवेंट को प्राप्त करता है, उसके हस्ताक्षर की जाँच करता है, एवं आवश्यक कार्रवाई करता है। हैंडलर को समय-सीमा के भीतर ही प्रतिक्रिया देनी होगी; क्योंकि स्ट्राइप धीमी प्रतिक्रिया को डिलीवरी में विफलता मानता है एवं पुनः प्रयास करता है।

डिलीवरी प्रक्रिया​

स्ट्राइप, स्थिति-परिवर्तन के कुछ ही सेकंडों के भीतर इवेंट को आपके एंडपॉइंट तक पहुँचाता है। आपका हैंडलर 2xx स्टेटस के साथ प्रतिक्रिया देता है, फिर उस इवेंट को संसाधित करता है।

नंबरयुक्त चरण एक क्रम में हैं। चरण 7 में दर्शाया गया है कि इवेंट तब आता है जब ग्राहक पहले ही परिणाम देख चुका होता है; इसलिए ग्राहक ऑर्डर पूर्ति का ट्रिगर नहीं बन सकता।

एंडपॉइंट को कॉन्फ़िगर करें​

एंडपॉइंट को डैशबोर्ड में Developers → Webhooks → Add endpoint के तहत पंजीकृत करें। स्ट्राइप (Stripe) एंडपॉइंट बनाते समय “साइनिंग सीक्रेट” (Signing Secret) दिखाता है; डैशबोर्ड बाद में इसे फिर से प्रदर्शित करता है।

सेटिंगमान
एंडपॉइंट पताhttps://api.example.com/webhooks/stripe
भेजने योग्य इवेंटpayment_intent.succeeded, payment_intent.payment_failed, charge.refunded
API संस्करणवह संस्करण जिसके लिए आपने हैंडलर लिखा

हैंडलर जो हर घटना पर कार्य करता है, उसे वह ट्रैफ़िक प्राप्त होता है लेकिन वह उसे पढ़ता नहीं है; हैंडलर पर कार्य करने वाली घटनाओं का चयन करें, एवं कोड में परिवर्तन होने पर अतिरिक्त घटनाएँ जोड़ें।

नोट

एंडपॉइंट का संस्करण आपके खाते के संस्करण से अलग हो सकता है; घटनाएँ उस संस्करण पर ही डिलीवर होती हैं जो एंडपॉइंट से जुड़ा है, इसलिए पेलोड (Payload) लॉग करते समय api_version को अवश्य पढ़ें।

कच्चे डेटा को पढ़ें​

हस्ताक्षर सत्यापन (Signature Verification) के लिए स्ट्राइप द्वारा भेजे गए बाइट्स की सटीक संख्या आवश्यक है; यदि डेटा को ऑब्जेक्ट में पार्स (Parse) कर दिया जाए तो व्हाइटस्पेस (Whitespace) एवं कुंजियों का क्रम खो जाता है, जिससे हस्ताक्षर सत्यापन विफल हो जाता है।

server.js
import express from "express";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const app = express();

// Keep the raw body for the webhook route only.
app.post(
  "/webhooks/stripe",
  express.raw({ type: "application/json" }),
  handleWebhook
);

// Every other route parses JSON.
app.use(express.json());

JSON पार्सर से पहले ही कच्चे डेटा का पार्सर को पंजीकृत करें; अन्यथा JSON पार्सर पहले ही डेटा को पढ़ लेगा। क्रम उलटने से प्रत्येक अनुरोध पर कच्चा डेटा खाली रह जाएगा एवं हस्ताक्षर सत्यापन विफल हो जाएगा।

हस्ताक्षर की जाँच करें​

स्ट्राइप (Stripe) प्रत्येक डिलीवरी पर एंडपॉइंट सीक्रेट (endpoint secret) का उपयोग करके हस्ताक्षर (signature) तैयार करता है, एवं उसे निर्धारित समय में ही जाँचता है।

server.js
async function handleWebhook(req, res) {
  const signature = req.headers["stripe-signature"];

  let event;

  try {
    event = stripe.webhooks.constructEvent(
      req.body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET
    );
  } catch (err) {
    console.error("Signature verification failed:", err.message);
    return res.status(400).send(`Webhook error: ${err.message}`);
  }

  res.status(200).json({ received: true });

  await dispatch(event).catch((err) => {
    console.error("Handler failed:", err.message);
  });
}

constructEvent कॉल, हस्ताक्षर की पुनः गणना करता है एवं ऐसे पेलोड (payload) को अस्वीकार कर देता है जो टाइमस्टैम्प (timestamp) की सीमा से पुराना हो। फिर यह एक इवेंट (event) वापस करता है। ये सभी जाँचें आपके कोड के पेलोड तक पहुँचने से पहले ही हो जाती हैं।

खतरा

कभी भी किसी अप्रमाणित पेलोड पर भरोसा न करें; हस्ताक्षर की जाँच के बिना, कोई भी व्यक्ति ऑर्डर को “पेड” (paid) घोषित कर सकता है या रिफंड (refund) का आदेश दे सकता है।

काम करने से पहले प्रतिक्रिया दें।​

स्ट्राइप, प्रतिक्रिया के लिए लगभग 20 सेकंड का इंतज़ार करता है। यदि कोई हैंडलर (handler) ऑर्डर को पूरा करने में विफल रहता है, तो वह एक ईमेल भेजता है। उसी पथ (request path) में होने वाला एनालिटिक्स अपडेट (analytics update) जोखिम को और बढ़ा देता है; इसलिए स्ट्राइप उस इवेंट को दोबारा भेजता है।

हैंडलर को दो चरणों में विभाजित करें:

  1. नीचे दिया गया उदाहरण, प्रतिक्रिया के बाद ही 200 कॉल करता है; यदि प्रक्रिया लंबी लगती है, तो उस कॉल को कतार में डाल दें।
  2. अज्ञात प्रकार का इवेंट कोई त्रुटि नहीं माना जाता; स्ट्राइप समय के साथ नए इवेंट प्रकार जोड़ता रहता है, इसलिए ऐसे इवेंटों पर हैंडलर को ध्यान देने की आवश्यकता नहीं है।

नीचे दिया गया उदाहरण, प्रतिक्रिया के बाद dispatch को इनलाइन (inline) कॉल करता है। यदि कार्य प्रक्रिया से अधिक समय लेता है, तो उस कॉल को एक कतार (queue) में स्थानांतरित कर दें।

dispatch.js
async function dispatch(event) {
  switch (event.type) {
    case "payment_intent.succeeded":
      return handleSucceeded(event.data.object);
    case "payment_intent.payment_failed":
      return handlePaymentFailed(event.data.object);
    case "charge.refunded":
      return handleRefunded(event.data.object);
    default:
      return;
  }
}

एक अज्ञात इवेंट प्रकार (unknown event type) कोई त्रुटि (error) नहीं है। स्ट्राइप (Stripe) समय के साथ नए इवेंट प्रकार जोड़ता रहता है; ऐसे इवेंट प्रकारों को संभालने वाला हैंडलर (handler), जो किसी अज्ञात प्रकार पर एरर दिखाता है, वह उस डिलीवरी (delivery) को विफल कर देता है, जिसे वह नजरअंदाज़ भी कर सकता था।

बिल्कुल एक बार पूरा करें​

स्ट्राइप (Stripe) असफल डिलीवरी को पुनः प्रयास करता है, एवं यदि प्रतिक्रिया धीमी हो, तो उसी इवेंट (event) को दोबारा भी डिलीवर कर सकता है। आपका हैंडलर (handler) ऐसे डुप्लिकेट डेटा (duplicates) को सहन करना चाहिए।

fulfillment.js
async function handleSucceeded(intent) {
  const already = await hasProcessed(intent.id);
  if (already) return;

  const orderId = intent.metadata.order_id;
  if (!orderId) {
    console.warn("Missing order_id on intent", intent.id);
    return;
  }

  await markOrderPaid(orderId, intent.id);
  await recordProcessed(intent.id);
}

इवेंट आईडी (Event ID) या ऑब्जेक्ट आईडी (Object ID) को एक अद्वितीय सूचकांक (unique index) में संग्रहीत करें, ताकि डेटाबेस दूसरे लेखन (write) प्रयास को अस्वीकार कर सके। जब दो डिलीवरी (deliveries) एक ही समय पर आती हैं, तो “चेक” (check) एवं “लेखन” (write) प्रक्रियाएँ प्रतिस्पर्धा करती हैं; लेकिन अद्वितीय सूचकांक (unique constraint) के कारण ऐसी प्रतिस्पर्धा नहीं हो सकती।

सुझाव

डीडुप्लिकेशन (deduplication) तालिका (deduplication table) को event.id पर “एक-बार होने वाले इवेंट्स” (one-shot events) के लिए, एवं object.id पर “स्थिति-संबंधी इवेंट्स” (state events) के लिए कुंजीकृत करें। प्रत्येक रिफंड (refund) के लिए एक charge.refunded इवेंट भेजा जाता है। केवल ऑब्जेक्ट आईडी ही दोहराई जाती है।

विफलता-संबंधी इवेंट्स (failure events) को संभालें।​

विफल हुए भुगतान के लिए payment_intent.payment_failed इवेंट भेजा जाता है; डिस्क्लाइन कोड (decline code) को पढ़कर तय करें कि क्या ग्राहक अपना पैसा वापस पा सकता है।

failures.js
async function handlePaymentFailed(intent) {
  const error = intent.last_payment_error;
  const code = error?.decline_code ?? error?.code;

  const recoverable = ["insufficient_funds", "processing_error"];
  const canRetry = recoverable.includes(code);

  await recordDecline(intent.metadata.order_id, code, canRetry);

  if (canRetry) {
    await sendRetryEmail(intent.metadata.order_id);
  }
}

कभी भी अपने समय-अनुसार विफल प्रयास न करें। यदि भुगतान-कर्ता ने कार्ड (card) को ब्लॉक कर दिया है, तो दूसरा प्रयास खाते के रिकॉर्ड (account record) में केवल एक और असफलता को जोड़ देगा।

एंडपॉइंट (endpoint) का स्थानीय रूप से परीक्षण (test the endpoint locally) करें।​

स्ट्राइप (Stripe) का कमांड-लाइन टूल (command-line tool), लाइव परीक्षण इवेंट्स (live test events) को स्थानीय सर्वर (local server) पर भेजता है; ताकि आप बिना किसी वितरण प्रक्रिया को शुरू किए ही उन्हें देख सकें।

stripe login
stripe listen --forward-to localhost:4242/webhooks/stripe

यह टूल एक “साइनिंग-सीक्रेट” (signing secret) प्रिंट करता है, जो whsec_ से शुरू होता है; इस मान (value) का उपयोग स्थानीय रूप से करें, एवं उत्पादन (production) में “डैशबोर्ड-सीक्रेट” (Dashboard secret) का उपयोग करें। फिर किसी अन्य टर्मिनल (terminal) से एक इवेंट ट्रिगर (trigger an event) करें।

stripe trigger payment_intent.succeeded

पहले टर्मिनल में इवेंट (event) दिखाया जाता है, जबकि सर्वर लॉग (server log) में हैंडलर का आउटपुट (handler output) दर्शाया जाता है। “सीक्रेट” (secret) को गलत मान (wrong value) में बदलें, और पुष्टि करें कि एंडपॉइंट (endpoint) “400” लौटाता है; यह यह साबित करेगा कि सिग्नेचर चेक (signature check) चल रहा है।

विफल डिलीवरी का निदान​

लक्षणकारणसुधार
प्रत्येक डिलीवरी पर 400हस्ताक्षर जाँच विफल रही।एंडपॉइंट सीक्रेट (endpoint secret) का उपयोग करें। कच्चे डेटा को अपार्स (parse) न करें।
400 लाइब्रेरी अपग्रेड के बादपार्सर ने सत्यापन से पहले ही डेटा को बदल दिया।कच्चे पार्सर (raw parser) को JSON पार्सर के आगे स्थानांतरित करें।
एक डिलीवरी दोहराई गईहैंडलर ने टाइमआउट से परे इंतज़ार किया।पहले इसे स्वीकार करें, फिर एक वर्कर (worker) में प्रोसेस करें।
हैंडलर लॉग में डुप्लिकेट डेटा हैप्रतिक्रिया टाइमआउट से परे आई, या पुनः प्रयास (retry) ओवरलैप हुआ।object.id पर स्टेट इवेंट्स (state events) के लिए और event.id पर एक-बार के इवेंट्स (one-shot events) के लिए डेटा को डुप्लिकेट होने से बचाएँ।
कोई भी डिलीवरी नहीं हुईएंडपॉइंट (endpoint) एड्रेस हेल्थ चेक (health check) में विफल रहा।डैशबोर्ड (Dashboard) से परीक्षण हेतु 2xx का डेटा प्राप्त करें।

पुराने इवेंट को दोबारा भेजें​

डैशबोर्ड इवेंट पेलोड (event payload) को संग्रहीत रखता है और आपको इसे दोबारा भेजने की सुविधा देता है। Developers → Webhooks → अपना एंडपॉइंट (your endpoint) → Events पर जाएँ, डिलीवरी चुनें और Resend चुनें।

दोबारा भेजने से आपको वास्तविक पेलोड (real payload) के साथ हैंडलर परिवर्तन (handler change) का परीक्षण करने का सबसे छोटा तरीका मिलेगा। प्रतिक्रिया कोड (response code) को ध्यान से दें; क्योंकि 500 वापस करने वाला पुनः भेजना (resend) प्रोडक्शन में भी विफल होगा।

अगले कदम​

  • कार्ड भुगतान स्वीकार करें उस सर्वर एंडपॉइंट के लिए जो इन इंटेंट्स (intents) को बनाता है।
  • आउटबाउंड कॉल्स (outbound calls) पर पुनः प्रयास (retry) के लिए इडेम्पोटेंट अनुरोध का उपयोग करें।
  • एंडपॉइंट से जुड़ी संस्करण-विशिष्ट जानकारी के लिए API संस्करणबद्धता एवं अपग्रेड देखें।
  • पूरे इवेंट कैटलॉग के लिए Stripe वेबफ़ुक दस्तावेज़ीकरण देखें।
