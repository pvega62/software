Manejo de webhooks de pago

  • Público objetivo: Desarrolladores que tienen un flujo de pago y necesitan un mecanismo fiable para el procesamiento de pedidos.
  • Requisitos previos: Un punto final de conexión (endpoint) al que se pueda acceder a través de HTTPS, así como la clave de firma obtenida desde el panel de control de Stripe.
  • Objetivo: Aceptar un evento payment_intent.succeeded, verificar su firma y cumplir con el pedido exactamente una vez.

Al final, dispondrás de un gestor de eventos que rechaza datos falsificados y registra cada pedido dentro del tiempo límite de respuesta. Ten en cuenta que la verificación de la firma se realiza antes de cualquier lógica empresarial.

Funcionamiento: Stripe envía un webhook cuando el estado de un objeto cambia; tu endpoint recibe el evento, verifica la firma y actúa según corresponda. El gestor debe responder dentro del tiempo establecido, ya que una respuesta lenta se considerará un error y provocará un intento de reenvío.

Recorrido de entrega​

Stripe envía el evento a tu punto final (endpoint) en cuestión de segundos después del cambio de estado. Tu gestor (handler) responde con un estado 2xx y luego procesa el evento.

Los pasos numerados siguen un orden específico. El paso 7 indica que el evento llega después de que el cliente ya ha visto el resultado del proceso, por lo que el cliente no puede actuar como desencadenante del cumplimiento del pedido.

Configura el punto final de conexión​

Registra el punto final de conexión en el Panel de Control (Dashboard), en la sección Desarrolladores → Webhooks → Añadir punto final de conexión. Stripe muestra el secreto de firma (signing secret) al crear el punto final de conexión; este secreto se volverá a mostrar más tarde en el Panel de Control.

ParámetroValor
Dirección del punto final de conexiónhttps://api.example.com/webhooks/stripe
Eventos a enviarpayment_intent.succeeded, payment_intent.payment_failed, charge.refunded
Versión de la APILa versión contra la que escribiste el gestor de eventos (handler).

Un gestor de eventos que se suscribe a todos los eventos recibirá tráfico que nunca leerá; selecciona los eventos sobre los que debe actuar y añade más según sea necesario cuando cambie el código.

nota

La versión del punto final de conexión puede ser diferente de la versión de tu cuenta; los eventos se enviarán según la versión configurada en el punto final de conexión, por lo que debes consultar el valor de api_version al registrar el contenido enviado.

Lee el cuerpo del mensaje en formato bruto​

La verificación de la firma requiere los datos enviados por Stripe en su formato original. Si el cuerpo del mensaje se analiza en un objeto, se pierden los espacios en blanco y el orden de los campos, lo que hace que la verificación de la firma fallen.

server.js
import express from "express";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const app = express();

// Keep the raw body for the webhook route only.
app.post(
  "/webhooks/stripe",
  express.raw({ type: "application/json" }),
  handleWebhook
);

// Every other route parses JSON.
app.use(express.json());

Registra primero el analizador que procesa el cuerpo en formato bruto; de lo contrario, el analizador correspondiente consumirá el flujo de datos antes de que puedas procesarlo adecuadamente. Invertir el orden de los analizadores provocará que el cuerpo del mensaje quede vacío y que la verificación de la firma fallen en cada solicitud.

Verifica la firma​

Stripe firma cada entrega utilizando una clave secreta (endpoint secret). Calcula la firma esperada y la compara en tiempo constante.

server.js
async function handleWebhook(req, res) {
  const signature = req.headers["stripe-signature"];

  let event;

  try {
    event = stripe.webhooks.constructEvent(
      req.body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET
    );
  } catch (err) {
    console.error("Signature verification failed:", err.message);
    return res.status(400).send(`Webhook error: ${err.message}`);
  }

  res.status(200).json({ received: true });

  await dispatch(event).catch((err) => {
    console.error("Handler failed:", err.message);
  });
}

La llamada a constructEvent recalcula la firma y rechaza los datos (payload) que sean más antiguos que el límite establecido por la fecha de tiempo (timestamp tolerance). A continuación, devuelve un evento correspondiente. Estas tres comprobaciones se realizan antes de que tu código acceda a los datos recibidos.

peligro

Nunca confíes en datos que no hayan sido verificados. Sin esta comprobación de firma, cualquier persona que conozca la dirección del endpoint puede marcar pedidos como pagados o solicitar reembolsos.

Responde antes de comenzar a trabajar​

Stripe espera unos 20 segundos para recibir una respuesta. Un gestor (handler) que procese un pedido y envíe un correo electrónico puede no completar su tarea debido a una dependencia lenta; además, una actualización analítica en la misma ruta puede aumentar el riesgo. En este caso, Stripe repite el proceso.

Divide el proceso de procesamiento en dos etapas:

  1. Confirmar. Verifica la firma y devuelve 200.
  2. Proceso. Pasa el evento a un trabajador que pueda volver a intentar la tarea lenta.

El ejemplo siguiente llama a la función dispatch de forma inmediata después de la respuesta; debes mover esa llamada a una cola de espera si el proceso lleva más tiempo de lo previsto.

dispatch.js
async function dispatch(event) {
  switch (event.type) {
    case "payment_intent.succeeded":
      return handleSucceeded(event.data.object);
    case "payment_intent.payment_failed":
      return handlePaymentFailed(event.data.object);
    case "charge.refunded":
      return handleRefunded(event.data.object);
    default:
      return;
  }
}

Un tipo de evento desconocido no constituye un error. Stripe incorpora nuevos tipos de eventos con el tiempo; por lo tanto, un gestor (handler) que genere una excepción al detectar un tipo de evento no reconocido fallará en la ejecución de una transacción que, de hecho, podría haberse procesado sin problemas.

Cumplir exactamente una vez​

Stripe intenta de nuevo la entrega que falló y también puede enviar el mismo evento dos veces si la respuesta es lenta. Tu función de manejo (handler) debe tolerar estas duplicaciones.

fulfillment.js
async function handleSucceeded(intent) {
  const already = await hasProcessed(intent.id);
  if (already) return;

  const orderId = intent.metadata.order_id;
  if (!orderId) {
    console.warn("Missing order_id on intent", intent.id);
    return;
  }

  await markOrderPaid(orderId, intent.id);
  await recordProcessed(intent.id);
}

Almacene el ID del evento o el ID del objeto en un índice único y permita que la base de datos rechace una segunda escritura. Cuando dos entregas llegan al mismo momento, se produce una competencia (race) entre los procesos de verificación y escritura; sin embargo, las restricciones de unicidad impiden que esto ocurra.

consejo

Clave la tabla de deduplicación en event.id para eventos de una sola vez y en object.id para eventos de estado. Cada reembolso genera un evento charge.refunded. Solo el ID del objeto puede repetirse en casos de cargos duplicados.

Gestiona los eventos de error​

Un pago fallido envía un mensaje payment_intent.payment_failed; lee el código de rechazo y decide si el cliente puede recuperar el dinero.

failures.js
async function handlePaymentFailed(intent) {
  const error = intent.last_payment_error;
  const code = error?.decline_code ?? error?.code;

  const recoverable = ["insufficient_funds", "processing_error"];
  const canRetry = recoverable.includes(code);

  await recordDecline(intent.metadata.order_id, code, canRetry);

  if (canRetry) {
    await sendRetryEmail(intent.metadata.order_id);
  }
}

Prueba el punto final de forma local​

La herramienta de línea de comandos de Stripe reenvía eventos de prueba en tiempo real a un servidor local, para que puedas ver cómo se realiza una entrega sin tener que implementarla.

No vuelvas a intentar un pago que ya ha sido rechazado cuando te apetezca. La entidad emisora ha bloqueado la tarjeta, y un segundo intento solo añadirá otro rechazo al historial de la cuenta.

stripe login
stripe listen --forward-to localhost:4242/webhooks/stripe

La herramienta genera un secreto de firma que comienza con whsec_; utiliza ese valor localmente y el secreto proporcionado por el panel de control (Dashboard) en el entorno de producción. Luego, desencadena un evento desde otro terminal.

stripe trigger payment_intent.succeeded

La primera terminal muestra el evento, y el registro del servidor muestra la salida del procesador correspondiente. Cambia el valor secreto a uno incorrecto y confirma que el punto final de conexión (endpoint) devuelve 400, lo cual demuestra que el proceso de verificación de firmas se ha ejecutado.

Diagnosticar una entrega fallida​

SíntomaCausaSolución
400 En cada entregaFallo en la verificación de la firma.Utilice la clave secreta del punto final (endpoint secret).
400 después de la actualización de una biblioteca.El analizador cambió el contenido del texto antes de la verificación.Mueve el analizador de datos brutos justo antes del analizador que procesa el elemento JSON.
Una entrega se repite.El procesador esperó más allá del tiempo límite (timeout).Primero se debe reconocer la solicitud; luego se procesa en un worker.
Los registros del gestor muestran duplicados.La respuesta excedió el tiempo límite de ejecución, o una intentona se superpuso a otra.Realiza la deduplicación en object.id para los eventos de estado y en event.id para los eventos de uso único.
No hay entregas en absoluto.La dirección del punto final de entrega falla la comprobación de estado (health check).Confirme que la dirección devuelve el valor 2xx para un evento de prueba desde el Panel de Control (Dashboard).

Reenviar un evento antiguo​

El panel de control guarda los datos de los eventos y te permite reenviar uno. Ve a Desarrolladores → Webhooks → tu punto final → Eventos, selecciona el envío y elige Reenviar.

Un reenvío (resend) proporciona el camino más corto para probar un cambio en el procesador con un contenido real (payload). Registre el código de respuesta, ya que un reenvío que devuelva 500 también fallaría en producción.
