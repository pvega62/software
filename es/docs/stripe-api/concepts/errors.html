Errores y reintentos

Stripe informa los fallos con un código de estado HTTP y un conjunto de datos denominado “envoltorio de error” (JSON). El código de estado indica cómo falló la solicitud; el “envoltorio de error” especifica la causa del problema y, en caso de que el error se deba a un parámetro concreto, indica qué debe modificarse.

El sobre de errores​

Una solicitud fallida devuelve un objeto de tipo error. Los campos que se incluyen en dicho objeto dependen del tipo de error que ha ocurrido.

{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds.",
    "charge": "ch_3Rsx4dDtWMrPDtgt1",
    "param": "",
    "doc_url": "https://stripe.com/docs/error-codes/card-declined",
    "request_log_url": "https://dashboard.stripe.com/test/logs/req_UQf6XBwBl9yk66"
  }
}
CampoPropósito
typeLa familia de errores. Dirige la rama de manejo.
codeUna razón breve y legible por las máquinas, como parameter_invalid_integer.
decline_codeLa razón del emisor para un error en la tarjeta, como insufficient_funds.
messageTexto legible para humanos. Se muestra al personal de soporte, no a los clientes.
paramEl parámetro de solicitud es el causante del problema, cuando el error se debe a un solo campo.
chargeEl ID de la carga correspondiente a un error con la tarjeta, cuando dicha carga existe.
doc_urlUna página que explica el código específico del error.
request_log_urlLa entrada en el registro de solicitudes del Panel de Control, que muestra la solicitud completa y la respuesta recibida.
nota

Registre cada error (request_log_url) para poder rastrear el camino más corto desde el ticket de soporte hasta la solicitud que falló.

Tipos de errores​

Cuatro valores de tipo type abarcan toda la plataforma.

typeMeaningRetry
invalid_request_errorFalta un parámetro o su formato es incorrecto; el objeto solicitado no existe, o el usuario no tiene permisos para acceder a los datos.Reenvíe la solicitud.
card_errorEl emisor de la tarjeta rechazó la carga, o se necesita autenticación adicional.Depende del motivo especificado en decline_code.
idempotency_errorEl usuario que realizó la solicitud reutilizó el mismo código de acceso con parámetros diferentes.Utilice un nuevo código de acceso.
api_errorStripe no pudo procesar la solicitud de forma correcta.Sí; intente nuevamente después de un intervalo de tiempo prudencial.

Códigos de rechazo​

Cada valor de tipo card_error contiene un valor de tipo decline_code. El código indica si es posible intentar el proceso nuevamente.

decline_codeSignificadoReintentarAcción
insufficient_fundsLa cuenta no dispone de fondos suficientes para el pago.Sí, más tarde.Pida al cliente que intente con otra tarjeta o espere.
expired_cardLa tarjeta ha superado su fecha de vencimiento.NoSolicite una nueva tarjeta.
incorrect_cvcEl código de verificación de la tarjeta (CVC) no coincide.Una vezPida al cliente que vuelva a proporcionar el código.
processing_errorLa red no pudo procesar el pago.SíIntente de nuevo después de un breve retraso.
card_declinedEl emisor rechazó la transacción sin indicar un motivo específico.NoSolicite otro método de pago.
authentication_requiredEl emisor exige el uso del sistema de seguridad 3D Secure.Después de autenticaciónRealice el procedimiento de verificación y confirme de nuevo.
lost_card, stolen_cardEl emisor ha bloqueado la tarjeta.NoNo intente de nuevo; envíe el caso a su equipo de riesgo.
aviso

Intentar de nuevo un pago rechazado puede generar otro rechazo y aumentar el índice de rechazos de la cuenta. Solo intente los códigos que indiquen “Sí”; detenga los intentos cuando se agote el presupuesto asignado para reintentos.

Configuración de políticas de reintentos​

Solo se deben reintentar los fallos que puedan tener éxito en un segundo intento: las familias de respuestas 409, 429 y 5xx. Los intentos deben separarse con un intervalo de tiempo que aumente exponencialmente (backoff) y con un pequeño margen de variación (jitter). Se debe limitar el número máximo de reintentos.

Node.js
// Retry only these status codes.
const RETRYABLE = new Set([409, 429, 500, 502, 503, 504]);

async function requestWithRetry(url, options, attempts = 4) {
  for (let attempt = 0; attempt < attempts; attempt++) {
    const response = await fetch(url, options);
    if (response.ok) return response;

    // Stop on a permanent failure, or when the budget runs out.
    if (!RETRYABLE.has(response.status) || attempt === attempts - 1) {
      return response;
    }

    // Wait 500 ms, then 1 s, then 2 s, plus jitter.
    const base = 2 ** attempt * 500;
    const delay = base + Math.random() * 250;
    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}

Cada intento espera entre 0,5, 1 y 2 segundos, más un margen de variación. Este esquema permite recuperarse de interrupciones breves sin sobrecargar el API.

Asocie cada política con un clave de idempotencia en cada caso (POST). De lo contrario, un intento de reenvío después de que expire el tiempo de espera podría cargar la tarjeta dos veces.

Lee la respuesta antes de reintentar​

Una respuesta 429 incluye información sobre cuándo se debe volver a intentar; lee esta información en lugar de adivinarlo.

Cabeza de respuestaSignificado
Retry-AfterSegundos que deben pasar antes del siguiente intento.
Stripe-Rate-Limited-Reason¿Qué límite se activó, el global-concurrency o el endpoint-concurrency?

Un valor de 429 en un extremo de la conexión suele indicar demasiadas solicitudes simultáneas, no un número total excesivo de solicitudes. Enviar menos llamadas en paralelo resuelve el problema más rápidamente que prolongar el intervalo entre ellas (backoff).

Diagnostica un fallo​

  1. Lee la respuesta type y actúa en consecuencia: una respuesta card_error requiere acción por parte del cliente, mientras que una api_error necesita un reintento.
  2. Para obtener el valor de 400, lea el contenido de param. Corrige el campo especificado en lugar de modificar toda la solicitud.
  3. Lee request_log_url. Confirma que Stripe ha recibido la solicitud y verifica el contenido del mensaje (payload) enviado.
  4. Comprueba el modo de operación. Un 404 en un objeto válido suele indicar que se está leyendo un dato de un objeto de prueba.
  5. Verifica el tipo de clave (key) solicitada. Un 403 puede referirse a una clave restringida para la cual no se tiene permiso de acceso.

Pasos siguientes​

  • Peticiones idénticas para reintentos seguros al realizar escrituras en los datos.
  • Utilice los puntos de acceso para paginación y listas (Paginación y puntos de acceso) para realizar lecturas masivas sin necesidad de recurrir al valor 429.
  • Versionado y actualizaciones de la API (Versiónamiento y actualizaciones de la API) cuando un cambio en el esquema interfiere con las llamadas a los servicios.
