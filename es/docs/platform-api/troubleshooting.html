Solución de problemas de solicitudes fallidas

Seguir estos tres pasos generalmente resuelve la mayoría de los problemas.

  1. **1. status: Nombre de la clase del error.
  2. **2. type: Nombre de la regla específica que causó el error (ver catálogo de errores).
  3. **3. request_id: Asociación del error con el registro de actividad de la plataforma.

Una llamada segura devuelve un 401​

Los nombres de los encabezados indicados en WWW-Authenticate corresponden al esquema (scheme) requerido por la ruta.

WWW-Authenticate: Bearer realm="bludhaven", error="invalid_token"

Hay cinco posibles razones para que se produzca esta respuesta:

  • El encabezado falta. Un navegador o un proxy puede eliminarlo.
  • La palabra “scheme” está incorrecta. Authorization: Basic no funciona correctamente con una ruta de tipo “bearer”.
  • El token podría estar falsificado o modificado; el sistema solo aceptará tokens generados por él mismo.
  • El token pasado fue exp. Se debe generar uno nuevo (autenticación).
  • La clave introducida está mal escrita, ya no se utiliza, o se ha enviado a una ruta que solo acepta un token. En ese caso, la respuesta es ApiKey y no Bearer.

No se produce un error 401 en las rutas abiertas (sin requisitos de autenticación); las rutas GET /animals, GET /animals/{animalId}, POST /applicants, POST /sessions y POST /webhooks/test-dispatch responden sin necesidad de credenciales.

Una llamada segura devuelve un 403​

El gateway reconoció el token, pero la ruta requiere un alcance (scope) que el token no posee; la respuesta indica qué alcance falta.

WWW-Authenticate: Bearer realm="bludhaven", error="insufficient_scope", scope="write:animals"

La entrada type indica que se necesita el alcance https://api.bludhavenpets.com/errors/insufficient-scope, mientras que detail describe explícitamente dicho alcance.

Hay dos posibles causas de este problema:

  • Un token de credenciales de cliente ha solicitado un conjunto demasiado limitado. Vuelve a enviar la solicitud del token con el ámbito que indica el desafío.
  • Una pantalla de consentimiento ha aprobado un subconjunto. Vuelve a ejecutar Connect y aprueba el alcance que necesita la ruta.

La solución se aplica en el momento de la autorización. Reintentar con el mismo token devuelve el mismo resultado (403).

Un animal devuelve un 404​

El parámetro GET /animals/{animalId} recibe un identificador que comienza por pet_. Un número de microchip también devuelve el resultado 404, al igual que un nombre o su variante en mayúsculas.

Envía primero el elemento GET /animals?status=AVAILABLE y copia el elemento id de la página. Esa acción confirma tanto la forma del identificador como la rama que alberga al animal.

Un ID de retención que antes funcionaba ahora devuelve un 404​

Dos objetivos pierden sus estados de retención por diseño.

Objeto¿Por qué el identificador deja de funcionar?
Demostración en navegadorUna nueva carga de la página borra la tabla de retenciones de la pestaña.
Puerta de enlace de sandboxEl sistema de aislamiento recicla los datos almacenados en memoria y elimina las retenciones.

Ninguno de los dos sistemas liberó al animal a través de la API; realiza una nueva solicitud de retención y continúa con el proceso. Considera el elemento 404 como un registro faltante, no como un animal ya liberado.

Un estado de retención en modo de producción sobrevive en ambos casos, ya que se almacena en un medio duradero.

Una retención falla con el código 422​

La plataforma rechaza a un animal que no cumple los requisitos, incluso cuando no existe ninguna solicitud de retención activa.

  • El animal almacena un estado distinto de AVAILABLE, como MEDICAL_QUARANTINE.
  • El valor de spay_neuter_certified corresponde al valor de false, pero el código municipal bloquea la liberación del animal.
  • La documentación sobre la rabia expiró antes del plazo de espera establecido.

Lea el registro del animal y muestre el valor status al asesor. Una entrada en la lista de espera es preferible a un intento de reenvío, ya que nada en la solicitud puede cambiar el resultado final.

La demo funciona, pero el entorno de pruebas la rechaza​

La puerta de enlace del entorno aislado aplica los requisitos de seguridad que la demostración del navegador omite, y esa diferencia explica casi todas las diferencias entre los dos objetivos.

Envíe un token generado por el portal a través de cualquier ruta que no esté entre las cinco disponibles. Puede generar el token utilizando las credenciales del cliente, o haga clic en “Conectar” para obtenerlo. Un string inventado devolverá el valor 401, mientras que un token real devolverá el valor 403.

La pasarela devuelve un error 404 para una operación documentada​

Una implementación obsoleta es la causa del problema; confirme qué contrato fue cargado por el portal.

curl https://sandbox.bludhaven-pets.workers.dev/health

Una implementación actual devolverá los valores operations: 24 y secured: 19. Cualquier valor inferior indica que el sistema está utilizando una versión antigua de los datos de respuesta; una nueva implementación resolverá este problema (versióning).

Escalación​

Escribe a budbaker@bludhavenpets.com indicando cuatro valores.

  • El valor X-Request-Id que se encuentra en la respuesta fallida.
  • La operación y el destino: producción o entorno de pruebas (sandbox).
  • El estado y la URI type.
  • Una marca de tiempo con la zona horaria correspondiente.

Soporte para rastros (traces) que identifiquen las llamadas sin necesidad de que las reproduzcas; un informe sin estos datos implica un costo adicional.
