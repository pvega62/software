Autenticación y ámbitos de acceso

Dos tipos de credenciales pueden utilizarse para acceder a rutas seguras; elige uno según el entorno en el que se ejecuta el código.

CredencialMétodo de transporteQuién lo utilizaDuración de validez
Token de portadorAuthorization: Bearer <token>Integraciones con portales para personal y rescate de sociosUna hora de vigencia, con un token de actualización que dura treinta días
Clave de APIX-API-Key: <key>Tareas del servidor y terminales de registro de puntos de ventaHasta que un administrador la cambie

Ambas credenciales funcionan en el portal de pruebas (sandbox); cada ruta segura valida cualquiera de ellas. Envíe un token (X-API-Key) en las rutas comerciales para que la llamada se realice sin problemas.

Cinco rutas están abiertas para todos: GET /animals, GET /animals/{animalId}, POST /applicants, POST /sessions y POST /webhooks/test-dispatch no requieren autenticación adicional. Un posible usuario puede navegar por el catálogo antes de crear una cuenta, y el destinatario de un servicio no necesita ninguna credencial.

Inicia sesión desde la referencia​

El portal de entorno de pruebas (sandbox) ejecuta el servidor de autorización; por lo tanto, al pulsar el botón “Conectar” se completa un proceso de inicio de sesión real.

  1. Abre la referencia interactiva. En el menú desplegable aparece primero Sandbox gateway, así que selecciónalo si aparece otro destino.
  2. Abra el panel de autenticación y presione Conectar en bludhaven_oauth.
  3. Aprobar la pantalla de consentimiento. Esta muestra los permisos solicitados por el cliente; tanto los botones Aprobar como Negar están disponibles.
  4. La consola devuelve un token. Envíe una solicitud segura y el gateway verifica la firma, la fecha de vencimiento y los permisos solicitados.

La pantalla de consentimiento permanece activa en el gateway, por lo que el proceso abandona brevemente la página. Si la referencia se ejecuta dentro de un elemento incrustado y la ventana emergente no puede devolver el código, abra la referencia independiente y haga el inicio de sesión allí.

El flujo del código de autorización​

El portal publica ambos tipos de puntos finales (endpoints); el contrato los especifica bajo la etiqueta bludhaven_oauth.

  1. El cliente genera un verificador y envía code_challenge junto con el hash SHA-256 de dicho verificador a https://sandbox.bludhaven-pets.workers.dev/oauth/authorize.
  2. El gateway redirige al cliente con un código de autorización, válido durante dos minutos.
  3. La pasarela redirige al cliente con un código de autorización válido durante dos minutos.
  4. El cliente envía el código y el verificador original a https://sandbox.bludhaven-pets.workers.dev/oauth/token.
  5. La respuesta incluye los datos de autenticación (access_token, token_type, expires_in), el token otorgado (scope) y otros detalles (refresh_token).

PKCE es importante aquí porque la integración con un socio se ejecuta en un dispositivo que nadie controla. Un código interceptado no tiene utilidad sin el verificador.

El ID del cliente es bludhaven-staff-portal. Una demo pública no puede mantener secretos; por lo tanto, este cliente se autentica únicamente con PKCE, y no existe ningún secreto que pueda filtrarse.

Genera un token con curl​

Un script no cuenta con un navegador para aprobar la pantalla de consentimiento. Las credenciales del cliente permiten generar un token en un solo paso (POST).

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=read:animals write:animals"
200 OK
{
  "access_token": "blud_at_eyJzdWIiOiJjbHVk...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:animals write:animals"
}

Si se omite scope, el gateway otorga los cuatro permisos de lectura. Si se solicita un permiso no incluido en el catálogo, la llamada devuelve 400 junto con invalid_scope.

Cada llamada posterior debe incluir el token en el encabezado de la solicitud.

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/health-records \
  -H "Authorization: Bearer <ACCESS_TOKEN>"

Esa ruta requiere el uso de read:animals; por lo tanto, un token que contenga únicamente write:animals devolverá 403 en su lugar.

Actualizar un token​

Publicar el token de actualización antes de que expire el token de acceso. El gateway proporcionará una nueva pareja de tokens, y el antiguo token de acceso dejará de ser válido.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=refresh_token" \
  -d "refresh_token=<REFRESH_TOKEN>" \
  -d "client_id=bludhaven-staff-portal"

Un token de credenciales del cliente no incluye un token de actualización, ya que el cliente puede generar uno nuevo en cualquier momento.

Autentícate con una clave de API​

Un terminal de registro y un proceso nocturno no utilizan navegador ni sesiones; cada uno de ellos utiliza una clave específica, y cada clave cubre únicamente las rutas necesarias para su funcionamiento.

El entorno de pruebas (sandbox) publica dos claves activas. Las credenciales de prueba deben ser copiables, por lo que están disponibles públicamente.

ClaveAlcanceUsuario típico
bpk_sandbox_pos_7f3a91c4read:retail, write:retailCaja registradora de punto de venta
bpk_sandbox_ops_2d8be05fread:animals, write:animals, write:adoptions, read:retailTarea de integración nocturna

Envíe la clave en el encabezado y omita cada paso relacionado con los tokens.

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

La clave de la caja registradora lee los datos de inventario y realiza pedidos de suministro; si se utiliza para registrar información sobre animales, el sistema rechaza la solicitud.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'
403 Forbidden
{
  "type": "https://api.bludhavenpets.com/errors/insufficient-scope",
  "title": "Insufficient Scope",
  "status": 403,
  "detail": "This API key lacks write:animals. Use a key assigned that scope, or send an OAuth token.",
  "instance": "/animals"
}

Si se utiliza la clave correspondiente a las operaciones, la misma solicitud devuelve el valor 201. Las claves determinan el alcance de sus funciones (no todo el catálogo); una clave dejada activa durante la noche no debería permitir la eliminación de registros de animales.

Un valor no reconocido devuelve el valor 401; en este caso, el sistema indica el problema asociado al esquema de funcionamiento de la clave, no el error específico.

WWW-Authenticate: ApiKey realm="bludhaven", error="invalid_key"

El ciclo de rotación de las claves se realiza en tres pasos:

  1. Emisión de la clave de reemplazo.
  2. Implementación del nuevo valor.
  3. Eliminación de la clave antigua después de que el último usuario la haya utilizado.

Una clave que se rota un viernes por la noche puede inhabilitar la caja registradora para realizar ventas el sábado.

Cuando falla una llamada​

El gateway responde indicando dos tipos de errores, y el encabezado (header) distingue entre ellos.

EstadoSignificadoDesafío
401Ausencia de credencial; token falsificado o caducado; sesión obsoleta, o clave no registradaBearer … error="invalid_token" o ApiKey … error="invalid_key"
403Credencial válida pero que carece del alcance (scope) requerido por la rutaerror="insufficient_scope", scope="write:animals"

El cuerpo de texto representado por 403 indica el alcance (scope) que falta en detail. Solicite dicho alcance en el momento de la autorización y luego intente nuevamente. Un portal para el personal que se encontró con este problema en entorno de producción solicitó información insuficiente durante el proceso de inicio de sesión.

El cuerpo de texto representado por 401 describe el motivo para el cual se solicita una credencial específica; de esta manera, el lector entiende qué tipo de información se necesita para completar la ruta. Una ruta que solo acepta un “token” rechaza cualquier clave que no corresponda a ese formato (representada por That route takes an OAuth bearer token, not an API key.).

El catálogo de ámbitos​

Cada alcance permite realizar una acción específica. Solicite únicamente los datos necesarios para el flujo de trabajo; un token de socio con el estado admin:adoptions puede anular una solicitud en curso.

AlcancePermisos otorgados
read:animalsAcceso a registros de animales, historial de admisión y requisitos para su adopción
write:animalsCreación, modificación y eliminación de registros de animales
read:adoptionsContiene las solicitudes de adopción.
write:adoptionsPermite retener los datos de los solicitantes, suspender su liberación y enviar sus solicitudes.
read:applicantsMantiene las cuentas de los solicitantes durante la revisión por parte de los asesores.
write:applicantsCrea y modifica las cuentas de los solicitantes.
vet:clearanceProcesa la presentación de certificados veterinarios; solo para profesionales licenciados.
read:retailControla los niveles de inventario y los pedidos de suministro.
write:retailRealiza el envío y cancelación de pedidos de suministro.
admin:adoptionsResuelve conflictos relacionados con las suspensiones de pedidos y realiza reembolsos en cualquier partida de costo.

Sesiones de los usuarios​

El solicitante nunca ve los detalles del proceso de adopción; el portal público intercambia el correo electrónico y la contraseña por un token de corta duración.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/sessions \
  -H "Content-Type: application/json" \
  -d '{"email": "nadia.okafor@fastmail.com", "password": "<PASSWORD>"}'
200 OK
{
  "token": "blud_sess_eyJzdWIiOiJ1c3JfOTkyMWJjIn0.9c1f4d2b7a",
  "expires_at": "2027-01-15T21:04:11Z",
  "scope": "read:applicants write:applicants"
}

El sistema genera un nuevo token con cada solicitud; copie el valor del token recibido en su respuesta. El ejemplo anterior muestra el formato del token, pero ese token no es una credencial válida para acceder al sistema.

El portal almacena el token en memoria y nunca lo guarda en el almacenamiento; solo el solicitante puede leerlo. Por lo tanto, una sesión robada no puede acceder a datos sensibles. Cuando el token se retira (DELETE /sessions/current), una nueva solicitud con él devolverá un código de éxito (401).

¿Qué destino valida qué?​

ObjetivoVerificación de credenciales
Demostración en navegadorNinguna. Cada ruta responde sin necesidad de credenciales.
Puerta de enlace de entorno de pruebas (sandbox)Firma del token, fecha de vencimiento y alcance; también se realiza una búsqueda en el registro para verificar el alcance del token. Una credencial incorrecta devuelve 401; si falta el alcance necesario, se devuelve 403.
ProducciónLos mismos controles, además de un registro de clientes revocable y un rastro de auditoría para cada clave.

El entorno de producción no añade nada que no pueda ser probado en el entorno de pruebas, ya que la demostración utiliza un servidor de autorización real.

Esquemas compatibles con la plataforma​

Hay cuatro tipos de credenciales que pueden utilizarse con la API. El contrato los denomina tres como esquemas de seguridad; el cuarto tipo utiliza un formato basado en tokens.

Esquema en el contratoQué identificaDónde se utiliza
bludhaven_oauth: Código de autorizaciónMiembro del personal o socio, con un paso de consentimientoPortales para el personal, integraciones para socios
bludhaven_oauth: Credenciales del clienteServicios que no requieren intervención humanaTareas nocturnas, scripts de reconciliación
api_keyUn dispositivo o una integración con un alcance fijo establecidoRegistros de puntos de venta (POS), sincronización entre servidores
Token de portador desde POST /sessionsPara una sesión del navegadorEl portal público de adopción

OAuth se utiliza para integraciones que requieren credenciales personales, mientras que un token se utiliza para credenciales almacenadas en dispositivos.

Lo que aporta la versión de producción​

Detrás de la puerta de enlace de producción hay dos funcionalidades adicionales, ya que una demostración pública no puede incluirlas.

  • Inicio de sesión único para el personal. OpenID Connect delega el proceso de inicio de sesión al proveedor de identidad municipal, y el intercambio de tokens se mantiene sin cambios.
  • TLS mutuo: Los servidores del backend presentan un certificado del cliente en un dominio personalizado. Sin embargo, el servidor de Cloudflare (workers.dev) no lo acepta, por lo que el entorno de pruebas no puede utilizarlo.

Los webhooks salientes firman cada solicitud con HMAC (X-Bludhaven-Signature), y el sandbox ofrece un punto de acceso que acepta envíos de prueba reales (guía de webhooks).

La opción HTTP Basic no se muestra aquí. En cada solicitud, los datos se envían en texto plano, y un token de portador se utiliza para las comunicaciones entre servidores, junto con un ámbito específico de uso.

Solicitar credenciales​

Envíe un correo electrónico a budbaker@bludhavenpets.com para obtener un ID de cliente o una clave API asignada. Indique los ámbitos de uso necesarios para la integración y la rama del código correspondiente. Incluya también el contenido del campo X-Request-Id de cualquier respuesta fallida.
