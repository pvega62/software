Solicitudes de prueba en la referencia

La referencia “Scalar” envía solicitudes en tiempo real. El portal de entorno de pruebas lidera la lista de servidores, y las solicitudes enviadas allí atraviesan una red real. También se pueden ejecutar las mismas llamadas desde una shell. Si se selecciona la opción Demostración en navegador, la respuesta se muestra directamente dentro de la página, sin necesidad de cuenta ni proceso local.

Cómo funciona la demostración del navegador​

El contrato publicado enumera tres destinos. Uno de ellos, /software/api-mock, corresponde a la página en la que te encuentras actualmente. Un gestor de solicitudes en la página de referencia responde a las solicitudes dirigidas a ese camino, generadas a partir de los ejemplos del propio esquema del contrato.

Ese diseño resuelve tres problemas a la vez:

  • Bloque de contenido mixto no permitido. Una página cargada mediante HTTPS no puede acceder a http://localhost. Respetar las reglas de origen evita que los navegadores rechacen la solicitud.
  • No se realiza ninguna comprobación previa („preflight“) para el número CORS. La respuesta nunca atraviesa la frontera de origen, por lo que no hay nada que necesite ser permitido.
  • No se necesita un servidor activo para mantener el funcionamiento del sitio. GitHub Pages proporciona archivos estáticos, y un servidor estático no puede ejecutar un servidor de prueba (mock server). El proceso de manejo de las solicitudes (handler) se lleva a cabo directamente en el navegador del visitante.
Las respuestas provienen del contrato

Cada cuerpo de texto se genera a partir de los ejemplos del esquema. Los nombres de los campos, las opciones enumeradas (enums), el patrón del microchip y las formas especificadas en el RFC 9457 cumplen todas con las especificaciones. Al seleccionar entre “producción” o “sandbox”, se elige un servidor real para el desarrollo.

Envía tu primera solicitud​

  1. Abra la referencia interactiva de la API.
  2. Comprueba que en el menú desplegable del servidor ponga Sandbox gateway. Esa ruta no necesita credenciales.
  3. Despliega GET /animals/{animalId}, introduce pet_krypto_210 como valor de la ruta y selecciona Enviar.

La respuesta devolverá los datos del animal (microchip 985141002348123, etiqueta contra la rabia RB-2026-9921) así como su estado AVAILABLE.

¿Qué rutas necesitan credenciales?​

El catálogo de adopciones y la ruta que acepta envíos de webhooks de prueba son de acceso público. Un posible adoptante puede navegar por el catálogo antes de crear una cuenta, y las pruebas realizadas por los receptores tampoco requieren credenciales. Las demás rutas sí imponen requisitos de seguridad:

RutaRequisito
GET /animalsNinguno. Catálogo público.
GET /animals/{animalId}Ninguno. Perfil del animal público.
POST /applicantsNinguno. Registro para crear una cuenta.
POST /sessionsNinguno. Inicio de sesión para obtener un token.
POST /webhooks/test-dispatchNinguno. Las pruebas realizadas por los receptores no requieren credenciales.
Todo lo demásToken portador de OAuth 2.0, o X-API-Key en las rutas que aceptan una clave.

La demostración para navegador ignora estos requisitos; por lo tanto, todas las rutas responden sin ninguna credencial. Sin embargo, el portal de pruebas (sandbox) los verifica, por lo que una solicitud puede fallar allí mientras que la misma solicitud tiene éxito en la demostración.

Autenticar una solicitud​

El contrato especifica un servidor de autorización real, así que la entrada bludhaven_oauth muestra un botón Conectar en lugar de un campo para pegar. Pulsa «Conectar» y el panel te guía por la pantalla de consentimiento en la pasarela de prueba.

Entrada en la consolaAcciónEncabezado
bludhaven_oauthConecta, aprueba y luego envíaAuthorization: Bearer <token>
api_keyPaste bpk_sandbox_pos_7f3a91c4X-API-Key: <key>

La clave de registro se aplica a las rutas relacionadas con el comercio minorista; para casos relacionados con animales, se debe utilizar bpk_sandbox_ops_2d8be05f en su lugar. La guía de autenticación indica qué funciones corresponde a cada clave publicada.

Un shell omite el panel y envía el encabezado directamente:

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

Una ruta segura que carece de su cabecera devuelve 401 Unauthorized, junto con un cuerpo de datos representado por ProblemDetails y un desafío (challenge) indicado por WWW-Authenticate. Un clave ficticia (made-up key) también fallará de la misma manera, ya que el sistema de seguridad busca ese valor en su registro interno.

Flujos que vale la pena ejecutar​

Lee un registro de animal​

Envía GET /animals/pet_krypto_210. La respuesta devuelve el esquema Animal junto con un registro de estado del animal y la tarifa de alojamiento de $150. Reemplaza el valor de la ruta por pet_krypto_999; el gestor de solicitudes responderá de todos modos, ya que coincide con el patrón de ruta y no con un registro almacenado en la base de datos.

Intenta una reserva conflictiva​

Envía POST /adoptions/holds con animal_id establecido en pet_krypto_210 y cualquier applicant_id. La primera llamada devuelve 201 Created con un identificador de hold nuevo, una 30-minuto expires_at y un seconds_remaining de cuenta regresiva. Envíalo de nuevo con el mismo animal_id y el handler devuelve 409 Conflict con un ProblemDetails que nombra el hold que te bloqueó.

Copia el ID de retención de la primera respuesta y envía GET /adoptions/holds/{holdId} para consultar el contador de cuenta atrás, o DELETE /adoptions/holds/{holdId} para liberar al animal. La liberación del animal desactivará la acción de retención, lo que permitirá que el siguiente intento tenga éxito. El estado de retención se mantiene durante toda la sesión del navegador y se reinicia al recargar la página.

Este flujo muestra al cliente cómo leer los datos type, title y detail en caso de conflicto, y le ofrece la opción de unirse a una lista de espera en lugar de recibir un mensaje de error.

Registra un reembolso​

Envía POST /refunds con application_id configurado en app_2026_1188, amount_cents en 10000 y reason en CANCELLATION_AFTER_48H. El procesador devuelve la tarifa de colocación y la lista de suministros, desglosada en breakdown; además, indica el monto del depósito y la tarifa de licencia que se ha retenido. Un proceso de conciliación lee los datos exactamente en ese formato.

Solicita una operación que el contrato no declare​

Envía GET /animals/pet_krypto_210/notes. Ninguna operación corresponde a ese camino, por lo que el procesador devuelve 404 junto con un cuerpo de respuesta (body) que contiene el código ProblemDetails. Esa respuesta activa la ruta de error que el cliente necesita.

Llama a la puerta de enlace del entorno de pruebas​

El puente de conexión al entorno de pruebas proporciona los mismos datos que se enviarían mediante HTTP en un entorno real, pero sin necesidad de utilizar un navegador.

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210

Las rutas seguras requieren un token firmado por este puente de conexión o una clave reconocida por él; el camino de acceso a dicha clave incluye únicamente un encabezado de solicitud, sin ningún intercambio adicional de datos.

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

La ruta del token comienza con “mint”.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=write:animals"

Copie el contenido de access_token de la respuesta y utilícelo en la siguiente llamada.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'

Omita ese encabezado; la misma llamada devolverá 401 junto con un cuerpo de tipo ProblemDetails y un desafío de tipo WWW-Authenticate. Envíe un valor ficticio de cualquiera de estos tipos y el gateway responderá de la misma manera. Envíe una credencial real que carezca de write:animals y la llamada devolverá 403 junto con insufficient_scope como parte del desafío.

La guía de autenticación explica cómo funciona la pantalla de consentimiento, los dos tipos de claves publicadas y los diez escopios de acceso disponibles.

Los “hold” se comportan tal y como lo hacen en la consola. Envíe POST /adoptions/holds dos veces junto con animal_id; la segunda llamada devolverá 409, que indica el estado de retención del animal. Copie el identificador correspondiente y luego lea el conteo regresivo con GET /adoptions/holds/{holdId} o libere al animal con DELETE /adoptions/holds/{holdId}.

GET /health informa sobre el contrato cargado por el gateway, el número de operaciones realizadas, el número de “holds” activos, los puntos finales (endpoints) de OAuth y cuántas claves se han publicado. Ejecute esta acción después de realizar una implementación para confirmar que el gateway se ha conectado a la red.

Prueba la subida prefirmada directamente al almacenamiento​

Genera una URL de subida firmada y, a continuación, envía los bytes binarios directamente al almacenamiento sin pasar los archivos por la API de la aplicación:

# 1. Request presigned upload URL (needs write:animals scope)
curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/photos \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"content_type": "image/jpeg", "caption": "Krypto in harbor yard"}'

Una firma alterada o caducada provocará que se devuelva upload_url; una carga exitosa devolverá PUT junto con el resumen de verificación SHA-256 y la URL pública del CDN.

# 2. PUT binary file directly to storage endpoint
curl -X PUT "<UPLOAD_URL>" \
  -H "Content-Type: image/jpeg" \
  --data-binary "@photo.jpg"

Una firma que ha sido manipulada o ha expirado devuelve el valor 403. Un carga exitosa devuelve el valor 200 junto con el chequeo de suma SHA-256 verificado y la dirección URL del CDN público.

Prueba el envío simulado de un webhook​

Envía un evento de webhook firmado para verificar tu receptor HMAC de forma local.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/webhooks/test-dispatch \
  -H "Content-Type: application/json" \
  -o webhook-dispatch.json

El gateway firma su carga útil completa y escribe la respuesta en webhook-dispatch.json. Verifícalo con node scripts/verify-webhook.mjs webhook-dispatch.json. La guía de webhooks explica el esquema de firma en Node.js y Python.

La consola de referencia también lista la llamada bajo Webhooks. Envíela contra Demostración del navegador; el encabezado de la respuesta verifica que la firma se realiza en el momento de la solicitud.

Las retenciones pueden reiniciarse

El gateway funciona en entornos aislados de corta duración; un entorno aislado reciclado pierde los “hold” que ha creado, por lo que un identificador de “hold” puede volver a mostrar el valor 404 incluso poco después de haber funcionado correctamente. Es necesario crear un nuevo “hold” en lugar de considerar que el valor 404 indica que el proceso ha finalizado con éxito.
