Demande de test dans la référence

La référence Scalar envoie des demandes en temps réel. Le passerelle de sandbox figure en tête de la liste des serveurs ; les demandes envoyées via ce passage sont transmises via un réseau réel. Un shell peut également effectuer les mêmes appels. Vous pouvez également sélectionner l’option Démo en navigateur ; la réponse sera affichée directement sur la page, sans nécessité d’utiliser de compte ou de processus local.

Comment fonctionne la démo en navigateur​

Le contrat publié liste trois cibles. L’une d’entre elles (/software/api-mock) correspond à la page sur laquelle vous êtes déjà. Un gestionnaire de demandes sur la page de référence répond aux appels effectués vers cette adresse, en utilisant des données générées à partir des exemples de schéma du contrat lui-même.

Ce système résout simultanément trois problèmes :

  • Aucun bloc de contenu mixte. Une page chargée via HTTPS ne peut pas appeler http://localhost. En répondant aux mêmes origines, on évite les demandes rejetées par les navigateurs.
  • Aucun prévol (préflight) n’est effectué pour les données CORS. La réponse ne dépasse jamais la frontière de l’origine, il n’y a donc rien à autoriser.
  • Aucun serveur à maintenir en fonctionnement. GitHub Pages fournit des fichiers statiques, et un hébergeur statique ne peut pas exécuter de serveur d’imitation (mock server). Le traitement des demandes se fait directement dans le navigateur de l’utilisateur.
Les réponses proviennent du contrat

Chaque partie du contenu est générée à partir des exemples fournis dans le schéma. Les noms des champs, les types de données (enums), le modèle de microprocesseur ainsi que les spécifications RFC 9457 sont strictement respectés. La sélection d’un environnement de production (production) ou d’un environnement d’essai (sandbox) cible un hôte réel.

Envoyez votre première demande​

  1. Ouvrez la référence API interactive.
  2. Vérifiez que le menu déroulant affiche Sandbox gateway ; cette route ne nécessite aucune authentification.
  3. Développez l’élément GET /animals/{animalId}, saisissez pet_krypto_210 comme valeur de chemin, puis sélectionnez Envoyer.

La réponse retourne les informations du Krypto : puce électronique 985141002348123, étiquette de vaccination contre la rage RB-2026-9921, ainsi que son état AVAILABLE.

Quelles routes nécessitent une authentification ?​

Le catalogue d’adoption et la route permettant d’envoyer des tests via webhook restent accessibles au public. Un futur adopteur peut consulter le catalogue avant de créer un compte, et un test effectué par le destinataire n’exige aucune authentification. Les autres routes impliquent des exigences de sécurité :

RouteExigence
GET /animalsAucune. Catalogue public.
GET /animals/{animalId}Aucune. Profil de l’animal public.
POST /applicantsAucune. Création d’un compte.
POST /sessionsAucune. Connexion pour obtenir un jeton d’autorisation.
POST /webhooks/test-dispatchAucune. Test effectué par le destinataire n’exige aucune authentification.
Tout le resteToken porteur OAuth 2.0, ou X-API-Key pour les routes qui acceptent une clé.

La démonestration en navigateur ignore ces exigences ; par conséquent, toutes les requêtes sont traitées sans aucune authentification. Le passerelle de sandbox vérifie ces conditions, ce qui peut entraîner un échec de la requête dans cette situation, tandis que la même requête fonctionne correctement dans la démonstration.

Authentifiez une requête​

Le contrat spécifie un véritable serveur d'autorisation ; par conséquent, l'entrée bludhaven_oauth affiche un bouton Se connecter plutôt qu'un champ de saisie. Cliquez sur « Se connecter » et le panneau affiche l'écran de consentement sur la passerelle de test.

Entrée consoleActionEn-tête
bludhaven_oauthConnectez-vous, approuvez le contenu, puis envoyez-leAuthorization: Bearer <token>
api_keyPaste bpk_sandbox_pos_7f3a91c4X-API-Key: <key>

La clé d’autorisation couvre les routes dédiées au commerce de détail. Pour les opérations concernant des animaux, utilisez bpk_sandbox_ops_2d8be05f. Le guide d’authentification indique les fonctionnalités accessibles avec chaque clé publiée.

Un shell contourne le panneau et envoie directement l'en-tête :

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

Une route sécurisée sans en-tête renvoie automatiquement 401 Unauthorized, accompagnée d’un corps de données contenant ProblemDetails et d’une demande d’autorisation (WWW-Authenticate). Une clé fictive échoue également, car le portail vérifie la validité de cette clé dans son registre.

Des parcours qui valent le détour​

Lire un enregistrement d’animal​

Envoyez GET /animals/pet_krypto_210. La réponse retourne le schéma Animal contenant un enregistrement de santé de l’animal ainsi que la frais de placement de 150 $. Remplacez la valeur du chemin par pet_krypto_999 ; le gestionnaire de requêtes répond toujours, car la demande correspond au modèle de route défini et non à un enregistrement stocké dans la base de données.

Essayez d’effectuer une nouvelle demande de blocage de l’animal​

Envoyez POST /adoptions/holds avec animal_id mis à pet_krypto_210 et tout applicant_id. La première appelée renvoie 201 Created avec un identifiant de hold nouveau, une 30-minute expires_at et un seconds_remaining compte à rebours. Envoyez-le à nouveau avec le même animal_id et le gestionnaire renvoie 409 Conflict avec un ProblemDetails corps nommant le hold qui vous a bloqué.

Copiez l’identifiant d’attente présent dans la première réponse, puis envoyez GET /adoptions/holds/{holdId} pour consulter le compte à rebours, ou DELETE /adoptions/holds/{holdId} pour libérer l’animal. La libération de l’animal annule l’opération d’attente, permettant une nouvelle tentative. L’état d’attente est conservé pendant toute la session de navigation et se réinitialise à chaque redémarrage de la page.

Ce processus montre au client comment interagir avec les données type, title et detail en cas de conflit, et propose à l’adoptant d’entrer sur une liste d’attente plutôt que de signaler une erreur.

Enregistrez un remboursement​

Envoyez POST /refunds avec application_id réglé sur app_2026_1188, amount_cents vers 10000 et reason vers CANCELLATION_AFTER_48H. Le gestionnaire de requêtes retourne les frais de placement ainsi que les informations relatives aux fournitures nécessaires (breakdown), et précise également les montants détenus en guise de caution et de frais de licence. Un processus de régularisation interprète ces données correctement.

Demandez une opération qui n’est pas déclarée dans le contrat​

Envoyez GET /animals/pet_krypto_210/notes. Aucune opération ne correspond à ce chemin, donc le gestionnaire retourne 404 accompagné d’un corps de réponse contenant la valeur ProblemDetails. Cette réponse active la branche dédiée aux erreurs, ce qui est nécessaire pour le client.

Appelez le guichet de test​

Le portail Sandbox transmet les mêmes données via le protocole HTTP. Un interpréteur (shell) exécute chaque opération directement, sans l’aide d’un navigateur web.

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210

Une route sécurisée nécessite un jeton signé par ce passerelle, ou une clé qu’il reconnaît. Le chemin de la clé ne comporte qu’un en-tête et aucun échange de données.

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

Le chemin du token commence par “mint”.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=write:animals"

Copiez la valeur access_token de la réponse et utilisez-la dans l’appel suivant.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'

Supprimez ce champ d’en-tête ; l’appel retournera alors la valeur 401 accompagnée d’un corps contenant la valeur ProblemDetails ainsi que d’un défi (“challenge”) sous forme de la valeur WWW-Authenticate. Envoyez une valeur fictive de ce type, et le système répondra de la même manière (en vérifiant la signature ou en recherchant la clé correspondante). Si vous envoyez une authentification réelle mais manquant de la valeur write:animals, l’appel retournera la valeur 403 avec la valeur insufficient_scope incluse dans le défi.

Le guide d’authentification explique comment fonctionne l’écran de consentement, les deux clés publiées par le système, ainsi que les dix scopes disponibles.

Les opérations se déroulent comme dans la console : envoyez « POST /adoptions/holds » deux fois avec un seul appel à « animal_id » ; la seconde demande retourne « 409 » qui identifie l’opération d’attente en cours. Copiez l’identifiant correspondant, puis suivez le décompte à rebours avec « GET /adoptions/holds/{holdId} » ou libérez l’animal avec « DELETE /adoptions/holds/{holdId} ».

La valeur GET /health affiche le contrat chargé par le système, le nombre d’opérations effectuées, le nombre d’opérations de “hold” en cours, les points de terminaison OAuth, ainsi que le nombre de clés publiées par le système. Exécutez cette commande après un déploiement pour confirmer que le système est bien connecté au réseau.

Tester l’envoi direct pré-signé vers le stockage​

Générez une URL de téléchargement signée, puis transférez directement les octets binaires vers le stockage sans faire passer les fichiers par l'API de l'application :

# 1. Request presigned upload URL (needs write:animals scope)
curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/photos \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"content_type": "image/jpeg", "caption": "Krypto in harbor yard"}'

Une signature modifiée ou expirée entraînera le retour de la valeur upload_url. Un téléchargement réussi retournera la valeur PUT accompagnée de la somme de contrôle SHA-256 vérifiée ainsi que de l’URL du contenu diffusé via le CDN public.

# 2. PUT binary file directly to storage endpoint
curl -X PUT "<UPLOAD_URL>" \
  -H "Content-Type: image/jpeg" \
  --data-binary "@photo.jpg"

Une signature modifiée ou expirée retourne « 403 ». Un téléchargement réussi retourne « 200 » accompagné du contrôle de somme SHA-256 vérifié ainsi que de l’URL du CDN public.

Test de l’envoi de webhooks simulés​

Envoyez un événement webhook signé pour vérifier votre récepteur HMAC localement :

curl -X POST https://sandbox.bludhaven-pets.workers.dev/webhooks/test-dispatch \
  -H "Content-Type: application/json" \
  -o webhook-dispatch.json

Le passerelle signe son ensemble de données (payload) et envoie la réponse à webhook-dispatch.json. Vérifiez cette réponse avec node scripts/verify-webhook.mjs webhook-dispatch.json. La guide sur les webhooks explique le processus de signature sous Node.js et Python.

La console de référence liste également cette action sous la catégorie Webhooks. Envoyez une demande via la démonestration en ligne ; l’en-tête de la réponse confirme que la signature a bien été effectuée au moment de la demande.

Les réservations peuvent être réinitialisées

Le passerelle fonctionne dans des environnements isolés de courte durée. Un environnement réutilisé perd les informations qu’il a stockées, donc un identifiant de demande (hold id) peut retourner une valeur de 404 immédiatement après l’expiration de la période de conservation. Il est donc préférable de créer une nouvelle demande plutôt que de lire la réponse de 404 comme si elle représentait une demande déjà traitée.
