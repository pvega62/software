Diagnostic d’une requête échouée

La plupart des problèmes peuvent être résolus en suivant cet ordre de procédure.

  1. **1. status : Nom de la catégorie d’échec.
  2. **2. type : Nom de la règle qui a été déclenchée (catalogue des erreurs).
  3. **3. request_id : Liens entre l’échec et les traces d’exécution de la plateforme.

Un appel sécurisé renvoie un code 401​

L’en-tête WWW-Authenticate spécifie le type de procédure à suivre.

WWW-Authenticate: Bearer realm="bludhaven", error="invalid_token"

Cinq raisons peuvent entraîner ce type de réponse :

  • Le titre (le « header ») est absent. Un navigateur ou un proxy peut le supprimer.
  • Le terme “scheme” est incorrect. La valeur Authorization: Basic ne fonctionne pas correctement avec une route de type “bearer”.
  • Le jeton est falsifié ou modifié. Le passerelle vérifie la signature (indiquée par HMAC) ; seuls les jetons qu’elle a elle-même créés sont autorisés à être utilisés.
  • Le token passé est exp. Il faut en générer un nouveau (authentification).
  • La clé saisie est incorrecte, obsolète, ou elle a été envoyée vers une route qui ne prend en charge que des tokens. Dans ce cas, la réponse est ApiKey et non Bearer.

Une erreur 401 n’apparaît jamais sur une route ouverte, car cinq routes ne nécessitent aucune authentification (GET /animals, GET /animals/{animalId}, POST /applicants, POST /sessions, POST /webhooks/test-dispatch).

Un appel sécurisé renvoie le code d'erreur 403​

Le passerelle a reconnu le token, mais la route requiert un champ de données (un “scope”) qui manque au token. La réponse indique le nom de ce champ de données.

WWW-Authenticate: Bearer realm="bludhaven", error="insufficient_scope", scope="write:animals"

La valeur type correspond à https://api.bludhavenpets.com/errors/insufficient-scope, tandis que detail décrit le champ de données manquant.

Deux situations peuvent entraîner cette erreur :

  • La correction doit être appliquée au moment de l’autorisation ; une nouvelle tentative avec le même token retournera toujours la même réponse.
  • Un écran de consentement a approuvé un sous-ensemble. Relancez Connect et validez la portée requise pour l'itinéraire.

La solution réside dans la phase d'autorisation. Une nouvelle tentative avec le même jeton renvoie le même code d'erreur 403.

Un animal renvoie un code d'erreur 404​

GET /animals/{animalId} récupère l’identifiant d’entrée, qui commence par pet_. Un numéro de puce électronique renvoie la valeur 404, tout comme un nom, ainsi qu’une variante en majuscules.

Envoyez d’abord GET /animals?status=AVAILABLE, puis copiez id depuis la page. Cette action confirme à la fois la forme de l’identifiant et la branche qui contient l’animal.

Un identifiant de réservation qui fonctionnait auparavant renvoie désormais une erreur 404​

Deux cibles perdent automatiquement leur contrôle sur l’animal.

CiblePourquoi cet identifiant ne fonctionne-t-il plus ?
Démo en navigateurLe réenchargement de la page efface la liste des contrôles associés à cette cible.
Portail de test (sandbox)Le système d’isolation Edge élimine les informations de contrôle stockées en mémoire.

Aucune des deux solutions n’a permis de libérer l’animal via l’API ; effectuez donc un nouveau contrôle et considérez 404 comme un enregistrement manquant, et non comme un animal déjà libéré.

Un contrôle en mode production survit à ces deux cas, car il est stocké dans un espace de stockage fiable.

Une suspension échoue avec le code 422​

La plateforme refuse de libérer un animal qui ne répond pas aux critères requis, même s’il n’existe aucun contrôle actif sur cet animal.

  • L’animal conserve un état autre que AVAILABLE, par exemple MEDICAL_QUARANTINE.
  • La valeur spay_neuter_certified correspond à celle de false, mais le code municipal bloque la libération de l’animal.
  • La documentation sur la rage est expirée avant la période de suspension des services.

Lisez le dossier de l’animal et présentez la valeur status au conseiller. Une entrée sur la liste d’attente est préférable à une tentative de réémission de la demande, car rien dans celle-ci ne peut changer le résultat final.

La démo fonctionne, mais le bac à sable la refuse​

La passerelle « sandbox » applique les exigences de sécurité que la démonstration dans le navigateur ne respecte pas, et c'est cette différence qui explique la quasi-totalité des divergences entre les deux cibles.

Envoyez un token généré par le portail depuis une route autre que celles autorisées. Vous pouvez créer ce token avec les informations d’authentification fournies par le client, ou cliquez sur “Connecter” dans l’interface de référence. Une chaîne de caractères inventée retournera la valeur 401, tandis qu’un token valide mais provenant d’une route non autorisée retournera la valeur 403.

La passerelle renvoie un code 404 pour une opération documentée​

Un déploiement obsolète est probablement à l’origine du problème ; vérifiez le contrat chargé par le portail.

curl https://sandbox.bludhaven-pets.workers.dev/health

Un déploiement actuel retournera les valeurs operations: 24 et secured: 19. Un nombre inférieur à ces valeurs indique que l’environnement d’exécution utilise une ancienne version des données de réponse ; un redéploiement résoudra ce problème (versionning).

Remontée d'incident​

Écrivez à budbaker@bludhavenpets.com en indiquant quatre valeurs.

  • Le X-Request-Id présent dans la réponse erronée.
  • L'opération et la cible : environnement de production ou bac à sable.
  • L’état de l’application et l’URI correspondant (type).
  • Une date-horaire avec l’heure de zone.

La fonctionnalité de suivi des appels (traces) qui permet d’identifier les problèmes sans avoir à reproduire l’appel lui-même ; un rapport sans cette information coûte un aller-retour en réseau.
