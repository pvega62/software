Authentification et champs d’application

Deux types de données d’authentification permettent d’accéder à des routes sécurisées ; le choix dépend du contexte d’exécution du code.

Type de données d’authentificationMode de transmissionUtilisateursDurée de validité
Jeton porteur (Bearer Token)Authorization: Bearer <token>Portails pour le personnel et intégrations avec les partenairesValide pendant une heure, avec un jeton de rafraîchissement valable pendant trente jours.
Clé API (API Key)X-API-Key: <key>Tâches serveur et terminaux de point de vente (POS)Valide tant que l’administrateur ne l’a pas remplacée.

Les deux types de données d’identification fonctionnent sur le portail de test (sandbox) ; chaque route sécurisée vérifie celui qu’elle accepte. Il s’agit d’alternatives, et non d’une séquence obligatoire. Envoyez un jeton (X-API-Key) pour accéder à une route commerciale, et l’appel se fera sans besoin de jeton.

Cinq routes restent accessibles à tous : GET /animals, GET /animals/{animalId}, POST /applicants, POST /sessions et POST /webhooks/test-dispatch n’ont aucune exigence de sécurité. Un futur utilisateur peut consulter le catalogue avant de créer un compte, et un destinataire n’a pas besoin de données d’identification pour effectuer un test.

Se connecter à partir de la référence​

Le portail de sandbox exécute le serveur d’autorisation ; par conséquent, le bouton “Connect” effectue une véritable connexion.

  1. Ouvrez la référence interactive. La liste déroulante présente en premier l’option Sandbox gateway ; sélectionnez-la si une autre cible est affichée.
  2. Ouvrez le panneau d’authentification et cliquez sur Connect à partir de bludhaven_oauth.
  3. Approuvez l’écran de consentement : il liste les autorisations demandées par le client ; les boutons Approve et Deny sont disponibles pour accepter ou refuser ces autorisations.
  4. La console retourne un jeton d’autorisation. Envoiez une demande sécurisée ; le passerelle vérifie la signature du jeton, sa date d’expiration ainsi que les autorisations accordées.

L’écran de consentement reste affiché sur la passerelle pendant le processus d’authentification. Si la demande est effectuée depuis un élément intégré (embed) et que la fenêtre pop-up ne peut pas retourner le code d’autorisation, ouvrez la référence indépendante (standalone reference) et connectez-vous depuis là.

Le flux du code d’autorisation​

Le gateway publie les deux points de terminaison (endpoints), et le contrat les déclare sous la mention bludhaven_oauth.

  1. Processus d’autorisation : Le client génère un “verifier” et envoie code_challenge accompagné du hash SHA-256 de ce dernier à https://sandbox.bludhaven-pets.workers.dev/oauth/authorize.
  2. La passerelle redirige alors le client vers une page contenant le code d’autorisation, valable pendant deux minutes.
  3. La passerelle redirige le client vers une page contenant un code d'autorisation, valable pendant deux minutes.
  4. Le client envoie le code et le vérificateur d'origine à l'adresse https://sandbox.bludhaven-pets.workers.dev/oauth/token.
  5. Réponse de l’api : La réponse contient access_token, token_type, expires_in, le jeton scope accordé, ainsi que des informations relatives à refresh_token.

PKCE est important ici car l’intégration avec un partenaire se déroule sur un appareil que personne ne contrôle. Un code intercepté est inutile sans le vérificateur correspondant.

L’ID du client est bludhaven-staff-portal. Une démo publique ne peut pas conserver de secrets ; donc ce client s’authentifie uniquement avec PKCE, et il n’existe aucun secret à divulguer.

Générer un jeton avec curl​

Un script ne dispose pas de navigateur pour valider l’écran de consentement. Les informations d’authentification du client permettent de créer un jeton en une seule opération.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=read:animals write:animals"
200 OK
{
  "access_token": "blud_at_eyJzdWIiOiJjbHVk...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:animals write:animals"
}

Si l’ID du client (scope) est omis, le passerelle accorde les quatre droits de lecture requis. Si un droit hors catalogue est demandé, la réponse contient à la fois 400 et invalid_scope.

Chaque appel ultérieur inclut le jeton dans son en-tête.

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/health-records \
  -H "Authorization: Bearer <ACCESS_TOKEN>"

Cette route nécessite l’ID du client (read:animals) ; un jeton contenant uniquement write:animals renvoie alors la réponse 403.

Actualiser un jeton​

Envoyer le jeton de rafraîchissement avant qu’il n’expire. Le passerelle fournit une nouvelle paire de jetons, et l’ancien jeton d’accès devient obsolète.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=refresh_token" \
  -d "refresh_token=<REFRESH_TOKEN>" \
  -d "client_id=bludhaven-staff-portal"

Un jeton d’authentification client ne contient pas de jeton de rafraîchissement, car le client peut en créer un nouveau à tout moment.

Authentification à l'aide d'une clé API​

Un terminal de gestion et une tâche nocturne n’utilisent pas de navigateur ni de session ; chacun d’eux possède sa propre clé, qui couvre uniquement les routes nécessaires à ses fonctions.

Le environnement de test (sandbox) publie deux clés utilisables. Les informations d’authentification de test doivent être copiables, donc elles sont mises à disposition publiquement.

CléAccessiblesAppelants typiques
bpk_sandbox_pos_7f3a91c4read:retail, write:retailRegistre de point de vente
bpk_sandbox_ops_2d8be05fread:animals, write:animals, write:adoptions, read:retailTâche d’intégration nocturne

Envoyez la clé dans l’en-tête et sautez chaque étape liée aux tokens

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

La clé permet de consulter les stocks et de passer des commandes d’approvisionnement ; si cette même clé est utilisée pour modifier les informations d’un animal, le système refuse l’opération

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'
403 Forbidden
{
  "type": "https://api.bludhavenpets.com/errors/insufficient-scope",
  "title": "Insufficient Scope",
  "status": 403,
  "detail": "This API key lacks write:animals. Use a key assigned that scope, or send an OAuth token.",
  "instance": "/animals"
}

Remplacez-la par une clé de gestion des opérations : la même demande retourne alors la valeur 201. Les clés définissent un ensemble d’autorisations spécifiques, et non l’ensemble du catalogue ; un registre laissé ouvert toute la nuit ne devrait pas pouvoir modifier les données des animaux

Une valeur non reconnue retourne la valeur 401, et le système indique le nom du problème (le schéma de fonctionnement plutôt que le token en cause)

WWW-Authenticate: ApiKey realm="bludhaven", error="invalid_key"

La rotation des clés se fait en trois étapes :

  1. Émettre la nouvelle clé de remplacement.
  2. Déployer la nouvelle valeur.
  3. Supprimer l’ancienne clé après le dernier appelant ayant utilisé celle-ci.

Une clé qui est remplacée un vendredi soir rend le registre inutilisable pour les ventes le samedi.

Lorsqu'un appel échoue​

Le passerelle détecte deux types d’échecs, et l’en-tête permet de les distinguer.

StatutSignificationProblème
401Aucune authentification (credentiel manquant, jeton falsifié ou expiré, session obsolète, ou clé non répertoriée dans le registre)Bearer … error="invalid_token" ou ApiKey … error="invalid_key"
403Credentiel valide mais ne possédant pas la portée requise par la routeerror="insufficient_scope", scope="write:animals"

Le corps de la ligne 403 indique l’élément manquant dans la ligne detail. Demandez cet élément au moment de l’autorisation, puis essayez à nouveau. Un portail interne qui a rencontré ce problème en production n’a pas demandé suffisamment d’informations lors de l’identification de l’utilisateur.

Le corps du message 401 explique le problème de manière claire, afin que l’utilisateur sache quel credentiel est nécessaire. Une route qui ne nécessite que un jeton refuse tout autre type de clé (indiqué par That route takes an OAuth bearer token, not an API key.).

Le catalogue des périmètres​

Chaque portée autorise l’accès à des fonctionnalités spécifiques. Il faut demander uniquement les informations nécessaires au flux de travail, car un jeton provenant d’un partenaire (indiqué par admin:adoptions) peut annuler une restriction temporaire („hold“).

PortéeAutorisations accordées
read:animalsAccès aux données des animaux, historique des admissions, et conditions d’adoption
write:animalsCréation, modification et suppression des fiches d’animaux
read:adoptionsGère les demandes d’adoption.
write:adoptionsRetient les informations relatives à l’accueil des animaux, à leur libération et aux soumissions de demandes.
read:applicantsConserve les comptes des candidats pendant la révision par le conseiller.
write:applicantsCrée et modifie les comptes des candidats.
vet:clearanceDépose les certificats vétérinaires (seuls les professionnels agréés peuvent le faire).
read:retailGère les niveaux de stock et les commandes d’approvisionnement.
write:retailPlace et annule les commandes d’approvisionnement.
admin:adoptionsSurmonte les conflits liés aux restrictions d’accès et effectue les remboursements pour toute ligne de coût.

Sessions des utilisateurs​

Le candidat ne voit jamais les détails précis de l’adoption ; le portail public échange son e-mail et son mot de passe contre un jeton temporaire.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/sessions \
  -H "Content-Type: application/json" \
  -d '{"email": "nadia.okafor@fastmail.com", "password": "<PASSWORD>"}'
200 OK
{
  "token": "blud_sess_eyJzdWIiOiJ1c3JfOTkyMWJjIn0.9c1f4d2b7a",
  "expires_at": "2027-01-15T21:04:11Z",
  "scope": "read:applicants write:applicants"
}

Le système génère un nouveau jeton à chaque demande ; copiez donc la valeur du jeton présent dans votre réponse. L’exemple ci-dessus montre la structure de ce jeton, mais il ne s’agit pas d’une carte d’accès fonctionnelle.

Le portail conserve le jeton en mémoire et ne l'enregistre jamais sur le support de stockage. Il permet uniquement au demandeur d'accéder aux informations de lecture, rien de plus ; ainsi, une session piratée ne peut pas affecter les services d'accueil ni la vente au détail. La commande DELETE /sessions/current désactive le jeton, et tout appel ultérieur utilisant ce jeton renvoie le code d'erreur 401.

Quelle cible valide quoi ?​

CibleVérification des identifiants
Démo en navigateurAucun besoin d’identifiant ; chaque requête est traitée sans authentification.
Portail de sandboxSignature du jeton, date d’expiration et portée des droits ; ou recherche dans un registre pour vérifier la portée des droits. Un identifiant invalide renvoie 401, une portée manquante renvoie 403.
ProductionMêmes vérifications, plus un registre des clients révocables et un historique des actions effectuées pour chaque identifiant.

La production n’ajoute rien de nouveau par rapport à ce que le lecteur peut tester dans l’environnement de sandbox, car la démo utilise un serveur d’autorisation réel.

Schémas pris en charge par la plateforme​

Quatre types d’identifiants sont acceptés par l’API : trois sont considérés comme des schémas de sécurité, et le quatrième est utilisé sous forme de jeton.

Schéma déclaré dans le contratCe qu’il permet d’identifierOù il est applicable
bludhaven_oauth : Code d’autorisationMembre du personnel ou partenaire, avec une étape de consentementPortails pour le personnel, intégrations avec des partenaires
bludhaven_oauth : Identifiants du clientServices fonctionnant automatiquement, sans intervention humaineTâches nocturnes, scripts de conciliation
api_key : Identifiant d’un appareil ou d’une intégrationPortée des droits fixeEnregistreurs de paiements, synchronisation entre serveurs
Token porteur provenant de POST /sessionsPour une seule session d’utilisateurLe portail d’adoption public

OAuth couvre les intégrations qui nécessitent des informations d’identification fournies par une personne, tandis qu’un token couvre les informations stockées sur un appareil.

Ce qu'apporte la version de production​

Deux fonctionnalités sont disponibles derrière le portail de production, car une démo publique ne peut pas les présenter.

  • Sécurisation par connexion unique pour le personnel. OpenID Connect déléguera l’authentification au fournisseur d’identité municipal, et l’échange de tokens reste inchangé.
  • TLS mutuel. Les serveurs internes présentent un certificat client sur un domaine personnalisé. Cependant, le serveur de Cloudflare (workers.dev) ne l’accepte pas, ce qui empêche le sandbox de le démontrer.

Les webhooks sortants signent chaque requête avec HMAC (X-Bludhaven-Signature), et le sandbox expose un point de terminaison qui accepte des envois de test réels (guide des webhooks).

La version « Basic » de ce système n’est pas mentionnée ici. Une paire de données codées en Base64 est transmise sous forme de texte brut avec chaque demande, tandis qu’un token porteur gère les communications entre serveurs, avec des paramètres d’accès spécifiques.

Demander des identifiants d'accès​

Envoyez un e-mail à budbaker@bludhavenpets.com pour obtenir un identifiant de client partenaire ou une clé API attribuée. Indiquez les paramètres d’accès requis par l’intégration ainsi que la branche logicielle concernée. Incluez également le contenu du champ X-Request-Id présent dans toute réponse erronée.
