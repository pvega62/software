Signatures et vérification des webhooks

La plateforme Blüdhaven Pets envoie des webhooks asynchrones lorsque des événements de cycle de vie se produisent en dehors d’un cycle de demande direct.

Deux événements sont envoyés aujourd’hui :

ÉvénementDéclenché lorsquePoints forts de la charge utile
adoption.hold.expiredUne réservation est annulée après 30 minutes en l’absence de demande d’approbationhold_id, animal_id, reason
veterinary.clearance.filedLe vétérinaire municipal délivre un certificat, rendant l’animal éligible à l’adoptionanimal_id, certificate_number, status

Chaque livraison est identifiée par une étiquette « HTTP POST » contenant un contenu (« JSON ») et une signature (« HMAC-SHA256 ») dans l’en-tête de la livraison (« X-Bludhaven-Signature »).

Pourquoi vérifier les signatures ?​

Un point de terminaison webhook public accepte le trafic HTTP en provenance d’Internet. Sans vérification cryptographique :

  • Un attaquant peut falsifier un événement représenté par adoption.hold.expired afin de libérer prématurément les animaux.
  • Un attaquant peut injecter un événement faux de type veterinary.clearance.filed pour contourner la quarantaine obligatoire liée à la rage.
  • Un attaquant peut rejouer un ancien contenu valide afin de provoquer un traitement redondant.

La vérification de la signature prouve que Blüdhaven Pets est l’auteur des données transmises et que celles-ci sont fraîches.

Format de l'en-tête de signature​

L’en-tête « X-Bludhaven-Signature » comprend une date horaire (« UNIX ») et un digest hexadécimal (« HMAC-SHA256 ») calculé à partir du contenu de la livraison :

X-Bludhaven-Signature: t=1795123456,v1=5d41402abc4b2a76b9719d911017c5926c459992f026a0b72a6a8b1a7f05252b
  • t : L’horodatage de l’époque UNIX, exprimé en secondes, au moment où le passerelle a signé la livraison.
  • v1 : Le résumé hexadécimal en minuscules HMAC–SHA256 calculé à partir de t={timestamp},v1={raw_body} en utilisant votre secret de signature webhook.

Vérifier la signature dans Node.js​

La vérification nécessite le corps de la demande brute exact avant l’analyse par JSON. Un analyseur modifie les espaces et l’ordre des clés, ce qui perturbe la validation cryptographique.

verify-webhook.mjs
import crypto from 'node:crypto';

export function verifyWebhookSignature({ rawBody, signatureHeader, secret, toleranceSeconds = 300 }) {
  if (!signatureHeader) {
    throw new Error('Missing X-Bludhaven-Signature header');
  }

  // 1. Extract timestamp and signature from the header
  const elements = Object.fromEntries(
    signatureHeader.split(',').map((pair) => pair.split('='))
  );

  const timestamp = parseInt(elements.t, 10);
  const expectedSignature = elements.v1;

  if (isNaN(timestamp) || !expectedSignature) {
    throw new Error('Malformed X-Bludhaven-Signature header');
  }

  // 2. Reject replays outside tolerance window (default 5 minutes)
  const currentTime = Math.floor(Date.now() / 1000);
  if (Math.abs(currentTime - timestamp) > toleranceSeconds) {
    throw new Error('Webhook timestamp falls outside tolerance window');
  }

  // 3. Recreate the signed string: t={timestamp},v1={raw_body}
  const signedPayload = `t=${timestamp},v1=${rawBody}`;

  // 4. Compute expected HMAC-SHA256
  const computedSignature = crypto
    .createHmac('sha256', secret)
    .update(signedPayload, 'utf8')
    .digest('hex');

  // 5. Compare in constant time to prevent timing attacks. A digest of the
  // wrong length makes timingSafeEqual throw RangeError, so check the length.
  const computed = Buffer.from(computedSignature, 'hex');
  const expected = Buffer.from(expectedSignature, 'hex');
  const valid =
    computed.length === expected.length &&
    crypto.timingSafeEqual(computed, expected);

  if (!valid) {
    throw new Error('Invalid webhook signature');
  }

  return JSON.parse(rawBody);
}

Vérifier la signature en Python​

verify_webhook.py
import hmac
import hashlib
import time
import json

def verify_webhook(raw_bytes: bytes, sig_header: str, secret: str, tolerance: int = 300) -> dict:
    parts = dict(item.split("=", 1) for item in sig_header.split(","))
    timestamp = int(parts.get("t", 0))
    expected_hex = parts.get("v1", "")

    if abs(time.time() - timestamp) > tolerance:
        raise ValueError("Timestamp outside acceptable replay window")

    signed_data = f"t={timestamp},v1=".encode("utf-8") + raw_bytes
    computed_hex = hmac.new(secret.encode("utf-8"), signed_data, hashlib.sha256).hexdigest()

    if not hmac.compare_digest(computed_hex, expected_hex):
        raise ValueError("Signature mismatch")

    return json.loads(raw_bytes.decode("utf-8"))

Test de l'envoi dans l'environnement de test​

Le portail de sandbox fournit un point d’arrivée (endpoint) pour les tests. Il signe le contenu du paquet de données (payload) et retourne les en-têtes (headers) correspondants. Dirigez votre récepteur vers ce point d’arrivée pour tester la gestion des signatures sans attendre d’événement en arrière-plan.

La console de référence liste la même appel sous Webhooks. Sélectionnez le serveur Browser demo et envoyez-y l’information correspondante. La démo effectue la signature au moment de la demande à l’aide du secret publié ; l’en-tête que vous copiez depuis la console doit donc correspondre à whsec_sandbox_bludhaven_test_secret_9981. Un fichier de test stocké contiendrait un timestamp obsolète ainsi qu’un digest basé sur des données incorrectes.

curl -X POST https://sandbox.bludhaven-pets.workers.dev/webhooks/test-dispatch \
  -H "Content-Type: application/json" \
  -o webhook-dispatch.json

Ne transmettez aucun contenu dans le corps de l’envoi ; le gateway signera alors l’intégralité du contenu envoyé. L’objet {"event": "veterinary.clearance.filed"} deviendra le payload de l’envoi.

webhook-dispatch.json
{
  "dispatched": true,
  "event": "adoption.hold.expired",
  "secret_used": "whsec_sandbox_bludhaven_test_secret_9981",
  "headers": {
    "Content-Type": "application/json",
    "X-Bludhaven-Signature": "t=1795123456,v1=5d41402abc4b...",
    "X-Bludhaven-Timestamp": "1795123456"
  },
  "payload": {
    "id": "evt_wh_901ab2cd",
    "event": "adoption.hold.expired",
    "created_at": "2026-11-19T13:30:00Z",
    "data": {
      "hold_id": "hld_a8f90b",
      "animal_id": "pet_krypto_210",
      "reason": "30_MINUTE_WINDOW_LAPSED"
    }
  },
  "verification_guide": {
    "scheme": "HMAC-SHA256",
    "signed_template": "t={timestamp},v1={raw_body}",
    "header_format": "t={timestamp},v1={hex_signature}"
  }
}

La réponse contient le secret de signature, la signature calculée ainsi que le payload. Vérifiez ces informations avec l’outil de vérification présent dans le répertoire des exemples de test (sandbox worker).

node scripts/verify-webhook.mjs webhook-dispatch.json
Output
event             adoption.hold.expired
secret            whsec_sandbox_bludhaven_test_secret_9981
signature header  t=1795123456,v1=5d41402a...
computed header   t=1795123456,v1=5d41402a...
signature match   YES
delivery age      2s (tolerance 300s): fresh

PASS: HMAC-SHA256 signature verified.

L’outil de vérification lit la réponse depuis un fichier et recalcule le digest. Ne passez jamais le payload via une variable shell ou une chaîne de caractères node -e incluse directement dans le code. Le traitement des chaînes de caractères peut entraîner des problèmes de syntaxe, ce qui peut conduire à un résultat incorrect (ReferenceError au lieu d’un résultat valide).

Modifiez un caractère du contenu transmis (payload), et le programme de vérification sort de l’état 1 pour entrer dans l’état FAIL: signature does not match.

Le vérificateur rejette également les envois effectués il y a plus de 300 secondes, ce qui ferme la fenêtre de répétition (replay). Activez la valeur --ignore-age lorsque vous répétez un test archivé.
