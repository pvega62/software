Présentation de l’API Stripe

L’API Stripe permet de transférer de l’argent entre les clients, votre plateforme et votre compte bancaire. Chaque point de terminaison (endpoint) de cette référence fonctionne avec un ensemble d’objets commun. Lisez cette page avant d’envoyer votre première demande.

Tous les points de terminaison partagent une adresse de base : https://api.stripe.com

Le modèle d’objet de paiement​

Un paiement laisse derrière lui une série d’objets qui permettent de suivre le processus depuis le moment de la commande jusqu’au compte bancaire. Chacun de ces objets enregistre une étape du processus, ce qui facilite l’audit ultérieur.

ObjetPréfixe d’IDRôle
Customercus_Conserve les informations du payeur, les méthodes de paiement enregistrées et l'historique des factures. Obligatoire pour les paiements ponctuels.
PaymentIntentpi_Enregistre une tentative de collecte de paiement. Contient le montant, la monnaie et l’état actuel de la transaction.
Chargech_Enregistre les mouvements de fonds liés à une méthode de paiement. Une tentative de paiement (PaymentIntent) réussie génère une seule opération de débit (Charge).
BalanceTransactiontxn_Enregistre l’effet d’un paiement, d’un remboursement ou d’un virement sur votre solde, y compris les frais afférents.
Payoutpo_Le solde régularisé est transféré sur votre compte bancaire selon le calendrier de paiement.

Un paiement commence sous forme d’une “intention” (PaymentIntent). Cette intention enregistre le montant et l’état du paiement jusqu’à ce que la méthode de paiement confirme celui-ci. La confirmation crée une charge (Charge) et transfère les fonds ; par la suite, une transaction (BalanceTransaction) enregistre le montant brut, la commission de Stripe et le montant net. Les fonds régularisés apparaissent dans le solde et sont ensuite versés via un virement (Payout).

Comment les fonds se déplacent via Stripe explique chaque étape du processus, y compris les refus de paiement, les remboursements et les litiges.

Conventions​

Les corps des demandes et des réponses suivent les mêmes conventions sur toute la plateforme. Les exemples de code présentés dans cette référence s’appuient sur ces conventions.

ConventionRègleExemple
MontantsEntiers, exprimés dans la plus petite unité monétaire (sans décimales).2120 facture 21,20 $ USD.
HorodatagesTemps Unix en secondes, UTC.1754447247
MonnaieCode ISO 4217 en minuscules.usd, eur, jpy
Noms de champssnake_casepayment_method_types
Type d’objetChaque réponse répète son type dans object."object": "payment_intent"
NulabilitéUn champ non défini ou vide retourne null. Le champ lui-même est conservé."customer": null
Remarque

Une monnaie à zéro décimal considère l’amount comme une unité entière ; par exemple, une charge de 1 000 yens est enregistrée sous la forme de 1000 et non de 10.00.

Authentification en un coup d’œil​

Envoyez une clé API secrète avec chaque demande, en utilisant le nom d’utilisateur “Basic Auth” accompagné d’un mot de passe vide. Les clés de test commencent par sk_test_, tandis que les clés réelles commencent par sk_live_. Une clé secrète accorde tous les droits d’accès à l’ compte ; elle ne doit donc être envoyée que depuis le code du serveur.

curl https://api.stripe.com/v1/balance \
  -u "$STRIPE_SECRET_KEY:"

Gestion de l’authentification et des clés aborde les questions relatives aux clés restreintes et à leur rotation. Elle indique également où stocker une clé sans la rendre accessible.

Mode de test et mode réel​

Chaque compte dispose de deux environnements distincts : les objets créés dans le mode de test ne manipulent jamais d’argent réel.

ModePréfixe de la cléDonnéesUtilisation
Testsk_test_Indépendantes des données réellesDéveloppement, tests automatisés, démos
Réelsk_live_Charges et paiements réelsProduction

Le mode de test associe les numéros de carte à des résultats spécifiques (refus de paiement, échec d’authentification). Mode de test et cartes de test liste les cartes utilisées dans les exemples.

Erreurs en un coup d’œil​

En cas d’échec, un envoi est effectué dans un format spécifique, contenant une information stable (type) et une explication lisible par l’humain (message). Les codes code et param fournissent des détails supplémentaires sur la cause de l’échec.

{
  "error": {
    "code": "parameter_invalid_integer",
    "doc_url": "https://stripe.com/docs/error-codes/parameter-invalid-integer",
    "message": "Invalid integer: 21.20",
    "param": "amount",
    "type": "invalid_request_error"
  }
}
État de HTTPType d’erreurCause typique
400invalid_request_errorUn paramètre est manquant, mal formé ou hors plage autorisée.
401invalid_request_errorLa clé est manquante, révoquée ou appartient à un autre compte.
402card_errorL’émetteur a refusé la transaction.
403invalid_request_errorLa clé ne dispose pas des autorisations nécessaires pour accéder à cette ressource.
404invalid_request_errorL’objet n’existe pas dans ce mode.
429rate_limit_errorLa clé a dépassé sa vitesse de demande autorisée.

Erreurs et tentatives de répétition associe chaque type d’erreur à une étape de récupération et explique quels échecs peuvent être sûrement réessayés.

Versions de l’API​

Stripe associe une version de son API à votre compte. Les demandes sans en-tête Stripe-Version utilisent cette version fixe ; par conséquent, une mise à jour du serveur ne modifie pas le format de la réponse sans avertissement. Vous pouvez surcharger cette version pour chaque demande pendant les tests.

curl https://api.stripe.com/v1/balance \
  -u "$STRIPE_SECRET_KEY:" \
  -H "Stripe-Version: 2024-06-20"

La versionning et les mises à niveau des API expliquent le processus de mise à niveau. Elles décrivent également ce que protège la fonctionnalité “pin”.

Assurer la sécurité des tentatives de réémission des demandes grâce à l’idempotence​

Un temps d’attente réseau vous laisse incertain de savoir si Stripe a traité la demande. Envoyez une… Idempotency-Key header on every POST Et répéter la même opération lors d’une nouvelle tentative. Stripe renvoie le résultat initial au lieu de facturer deux fois.

Le document Demandes idempotentes explique comment sélectionner une clé et combien de temps Stripe conserve les résultats des transactions. Il décrit également les erreurs qui peuvent survenir lors de la réutilisation d’une clé avec de nouveaux paramètres.

Structure de la référence​

  • Concepts. Ces pages expliquent le comportement commun de chaque point de terminaison (endpoint). Commencez par ici.
  • Début rapide. En acceptant les paiements par carte (Accept a card payment) et en gérant les webhook de paiement (Handle payment webhooks), vous pouvez mettre en place une intégration fonctionnelle à partir de ces concepts.
  • Référence d’extrémité de pointe (Endpoint reference). Le document sur les groupes de solde, d’intention de paiement et de remboursement présente une extrémité de pointe (endpoint) par page, accompagnée des paramètres, des attributs de réponse et des exemples d’erreurs.
  • Guides. Utiliser Postman pour se connecter à l’API de Stripe permet d’établir des demandes authentifiées sans avoir à écrire de code.
