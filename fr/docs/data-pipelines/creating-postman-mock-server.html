Créer un serveur de simulation Postman

Utilisez les fichiers d’exemple fournis par Postman pour simuler localement l’API d’ingestion des données de connexion à Datadog. Vérifiez les formats des demandes et les réponses aux erreurs, et exécutez les exemples pratiques sans envoyer de données vers un compte Datadog en ligne.

Prérequis​

  • Postman (version bureau ou web).
  • Les fichiers JSON inclus dans ce projet doivent être téléchargés avant de commencer.
FilePurpose
DataPipeline-Environment.jsonDéfinit des variables réutilisables : dd_site, mock_base_url et dd_api_key.
DataPipeline-postman-collection.jsonEnvoie des requêtes réelles à l'API d'ingestion de logs de Datadog (/api/v2/logs).
DataPipeline-MockServer-Collection.jsonConfigure des réponses simulées pour les mêmes points de terminaison à l'aide d'un serveur de simulation Postman.
Vous pouvez consulter ces mêmes fichiers dans le dépôt de logiciels sur GitHub.

1. Importez les fichiers dans Postman​

  1. Ouvrez Postman et sélectionnez Importer.
  2. Sélectionnez les trois fichiers JSON téléchargés en même temps.
  3. Dans le sélecteur d'environnement de la barre d'outils, sélectionnez Environnement du pipeline de données. Une fois l'importation terminée, Postman affiche trois éléments :
  • Le projet de documentation du pipeline de données envoie les requêtes en temps réel.
  • La collection de serveurs de simulation du pipeline de données définit les réponses de simulation enregistrées.
  • L'environnement du pipeline de données fournit les variables communes aux deux collections.

2. Créer le serveur fictif​

  1. Dans la barre latérale de Postman, ouvrez le menu « Ajouter », puis sélectionnez Mock Server.
  2. Sélectionnez Collection existante.
  3. Dans la section Collection, sélectionnez Collection de serveurs de simulation de pipeline de données. Dans la section Environnement, sélectionnez Environnement de pipeline de données.
  4. Sélectionnez Déployer.
  5. Copiez l'adresse du serveur de simulation depuis le Workbench. Postman génère une adresse unique pour le serveur fictif, par exemple : https://a12b34cd-1234-5678.mock.pstmn.io

3. Mettre à jour la variable d'environnement​

  1. Accédez à Environnements et ouvrez Environnement de pipeline de données.
  2. Recherchez la variable mock_base_url.
  3. Remplacez cet espace réservé par l'adresse que vous avez copiée :
mock_base_url
# Before
https://mock-server-url-from-postman.io

# After
https://a12b34cd-1234-5678.mock.pstmn.io

  1. Cliquez sur Enregistrer pour conserver les modifications.

  2. Ouvrez POST /api/v2/logs dans la Collection de serveurs d' simulation de pipelines de données (Data Pipeline Mock Server Collection).

  3. Vérifiez que le sélecteur d'environnement affiche Environnement du pipeline de données.

  4. Choisissez Envoyer.

Le serveur de simulation retourne une réponse simulant la valeur 202 Accepted et rejoue le contenu de l’exemple enregistré.

4. Envoyez votre première requête de test​

Response: 202 Accepted
{
  "status": "accepted",
  "message": "Log event received by mock server."
}

La véritable API d’ingestion des logs de Datadog retourne 202 Accepted accompagné d’un objet JSON vide ({}). La collection fictive (mock) retourne un objet lisible afin de confirmer que le serveur de simulation a bien reçu la demande.

5. Tester une réponse d’erreur​

Datadog rejette les événements qui omettent le champ obligatoire message. Pour reproduire ce rejet, supprimez le champ message du corps de la demande et sélectionnez à nouveau Envoyer. Postman compare le contenu de la demande avec chaque exemple enregistré et affiche alors l’exemple correspondant (indiqué par le numéro 400).

Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Malformed payload: the 'message' field is required",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

Pour renvoyer un exemple spécifique, quel que soit le corps de la requête, ajoutez un en-tête x-mock-response-code avec le code d'état souhaité, par exemple 400.

Le serveur de simulation rejoue un exemple enregistré et ne valide jamais les informations d’identification (les « credentials »), donc il ne retourne aucune réponse (pas de valeur correspondant à 401). Pour tester le cas où une clé API est manquante, supprimez l’en-tête DD-API-KEY et envoyez la requête POST /api/v2/logs depuis le Projet de documentation du pipeline de données (Data Pipeline Documentation Project). La page API d’ingestion des journaux liste la réponse associée à chaque code d’erreur.

6. Alterner entre les tests en temps réel et les tests de simulation​

Les deux collections utilisent le même fichier d’environnement. Pour passer d’un environnement réel à un environnement de simulation (mock), il suffit de modifier ce fichier. Pour les tests, changez la collection que vous utilisez :

ObjectifCollectionVariable d’adresse de base
Tester avec le véritable DatadogDataPipeline-postman-collection.json{{dd_site}} → datadoghq.com
Tester localement ou hors ligneDataPipeline-MockServer-Collection.json{{mock_base_url}} → votre adresse de simulation

Définissez la valeur de dd_api_key dans l’environnement avant d’envoyer une demande en temps réel. Cette approche vérifie les formats des demandes et des réponses avant que les données ne soient envoyées sur votre compte Datadog.

Vérification avant le trafic réel​

Cette configuration de serveur d’simulation illustre le même schéma de vérification que celui utilisé lors du développement ou de la documentation d’une intégration API réelle :

  • Vérifiez la structure de la requête et les en-têtes obligatoires (DD-API-KEY, Content-Type) avant d'envoyer du trafic en production.
  • Vérifiez que les données JSON correspondent au schéma attendu : un tableau d'objets de journalisation, chacun comportant un champ message.
  • Tester le traitement des erreurs (400, 401, 429) sans consommer de quotas API ni polluer l’index des journaux de production.
  • Élaborer et valider la documentation à l'aide d'exemples basés sur un point de terminaison stable et reproductible.

Les fonctions sont traitées dans le flux de journalisation dev avant d’être promues au niveau production, ce qui permet de configurer leur évaluation correctement. Vérifier correctement les métriques avant que le trafic réel des utilisateurs ne commence à circuler.
