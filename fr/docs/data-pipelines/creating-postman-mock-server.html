Créer un serveur de simulation Postman

Utilisez les fichiers d'exemple Postman fournis pour reproduire localement l'API d'ingestion de logs Datadog. Vérifiez les formats de requête et les réponses d'erreur, et exécutez les exemples pratiques sans envoyer de données vers un compte Datadog réel.

Prérequis​

  • Postman (version bureau ou web).

  • Les fichiers JSON fournis avec ce projet. Téléchargez chacun d'eux avant de commencer :

    FichierObjectif
    DataPipeline-Environment.jsonDéfinit les variables réutilisables : dd_site, mock_base_url et dd_api_key.
    DataPipeline-postman-collection.jsonEnvoie de vraies requêtes vers l'API d'ingestion de logs Datadog (/api/v2/logs).
    DataPipeline-MockServer-Collection.jsonConfigure des réponses simulées pour les mêmes points de terminaison avec un serveur de simulation Postman.

Parcourez les mêmes fichiers dans le dépôt software sur GitHub.

1. Importer les fichiers dans Postman​

  1. Ouvrez Postman et sélectionnez Import.
  2. Sélectionnez les trois fichiers JSON téléchargés en une seule fois.
  3. Dans le sélecteur d'environnement de la barre d'outils, sélectionnez Data Pipeline Environment.

Après l'import, Postman affiche trois éléments :

  • Data Pipeline Documentation Project envoie les requêtes réelles.
  • Data Pipeline Mock Server Collection définit les réponses simulées enregistrées.
  • Data Pipeline Environment fournit les variables que les deux collections partagent.

2. Créer le serveur de simulation​

  1. Dans la barre latérale Postman, ouvrez le menu d'ajout, puis choisissez Mock Server.
  2. Sélectionnez Existing collection.
  3. Sous Collection, sélectionnez Data Pipeline Mock Server Collection. Sous Environment, sélectionnez Data Pipeline Environment.
  4. Sélectionnez Deploy.
  5. Copiez l'adresse du serveur de simulation depuis l'espace de travail.

Postman génère une adresse unique pour le serveur de simulation, par exemple : https://a12b34cd-1234-5678.mock.pstmn.io

3. Mettre à jour la variable d'environnement​

  1. Accédez à Environments et ouvrez Data Pipeline Environment.
  2. Recherchez la variable mock_base_url.
  3. Remplacez la valeur de départ par l'adresse que vous avez copiée :
mock_base_url
# Avant
https://mock-server-url-from-postman.io

# Après
https://a12b34cd-1234-5678.mock.pstmn.io
  1. Sélectionnez Save pour conserver la modification.

4. Envoyer votre première requête simulée​

  1. Ouvrez POST /api/v2/logs dans Data Pipeline Mock Server Collection.
  2. Vérifiez que le sélecteur d'environnement affiche Data Pipeline Environment.
  3. Sélectionnez Send.

Le serveur de simulation renvoie une réponse 202 Accepted simulée et rejoue le corps d'exemple enregistré :

Response: 202 Accepted
{
  "status": "accepted",
  "message": "Log event received by mock server."
}

La vraie API d'ingestion de logs Datadog renvoie 202 Accepted avec un objet JSON vide ({}). La collection simulée renvoie un objet lisible pour que vous confirmiez que le serveur de simulation a reçu la requête.

5. Tester une réponse d'erreur​

Datadog rejette un événement qui omet le champ message obligatoire. Pour reproduire ce rejet, supprimez le champ message du corps de la requête et sélectionnez de nouveau Send. Postman compare le corps à chaque exemple enregistré et renvoie l'exemple 400 :

Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Malformed payload: the 'message' field is required",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

Pour renvoyer un exemple précis quel que soit le corps, ajoutez un en-tête x-mock-response-code avec le code d'état voulu, comme 400.

Le serveur de simulation rejoue un exemple enregistré et ne valide jamais les identifiants : il n'a donc aucune réponse 401 à renvoyer. Pour tester une clé API absente, supprimez l'en-tête DD-API-KEY et envoyez POST /api/v2/logs depuis Data Pipeline Documentation Project. La page API d'ingestion de logs liste la réponse de chaque code d'erreur.

6. Basculer entre tests réels et tests simulés​

Les deux collections utilisent le même fichier d'environnement. Pour basculer entre tests réels et tests simulés, changez de collection :

ObjectifCollectionVariable d'adresse de base
Tester avec le vrai DatadogDataPipeline-postman-collection.json{{dd_site}} → datadoghq.com
Tester en local ou hors ligneDataPipeline-MockServer-Collection.json{{mock_base_url}} → votre adresse simulée

Renseignez dd_api_key dans l'environnement avant d'envoyer une requête réelle. Cette approche vérifie les formats de requête et de réponse avant l'envoi de données vers votre compte Datadog.

Vérification avant le trafic réel​

Cette configuration de serveur de simulation applique le même schéma de vérification que vous utilisez pour développer ou documenter une intégration API réelle :

  • Vérifiez la structure des requêtes et les en-têtes obligatoires (DD-API-KEY, Content-Type) avant d'envoyer du trafic réel.
  • Confirmez que les charges utiles JSON correspondent au schéma attendu : un tableau d'objets de log, chacun avec un champ message.
  • Testez la gestion des erreurs (400, 401, 429) sans consommer de quota API ni polluer un index de logs de production.
  • Développez et vérifiez les exemples de documentation sur un point de terminaison stable et reproductible.

Le même schéma s'applique lorsque vous documentez le kit de développement logiciel (SDK) Galileo. Vous testez les fonctions instrumentées dans un flux de logs dev avant de les promouvoir en production, ce qui garantit une configuration correcte des métriques d'évaluation avant l'arrivée du trafic utilisateur réel.
