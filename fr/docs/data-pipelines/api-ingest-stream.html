Ingérer des événements à l’aide de l’API d’ingestion de journaux de Datadog

Cette API prend en charge l’ingestion à haute vitesse et en temps réel de données structurées et semi-structurées.

Actions prises en charge par cette API​

  • Envoyer les journaux (logs) directement depuis les applications cloud sans installer l’agent Datadog.
  • Appliquer des traitements de pipeline, tels que le Grok Parser, le Remapper et le Lookup Processor, aux données reçues.
  • Diriger les journaux de route vers des index, des archives ou des destinations d’alerte en fonction de leur contenu.
  • Réduire le coût d’indexation en combinant cet endpoint avec des règles d’échantillonnage et de filtrage.
Remarque

Consultez la section API et clés d’application de Datadog pour gérer vos identifiants d’accès.

Avant de commencer​

Assurez-vous d’avoir :

  • Une clé API de Datadog dotée des autorisations d’ingestion des logs. La trouver dans Paramètres de l’organisation → Clés API.
  • Votre adresse du site Datadog. Cette adresse varie en fonction de la région.
RégionAdresse du site
US Estdatadoghq.com
US3 Westus3.datadoghq.com
US5 Centralus5.datadoghq.com
UEdatadoghq.eu
AP1 Japonap1.datadoghq.com
AP2 Australieap2.datadoghq.com
  • Vérifiez que curl ou Postman est installé.
  • Les données de journalisation doivent être au format spécifié par JSON.

Pointe de terminaison d’ingestion​

POST https://http-intake.logs.{dd_site}/api/v2/logs

Remplacez {dd_site} par l’adresse du site de votre région, par exemple datadoghq.com ou ap2.datadoghq.com.

En-têtes de la demande​

En-têteValeurObligatoireDescription
DD-API-KEY<your_api_key>OuiVotre clé API Datadog
Content-Typeapplication/jsonOuiFormat du contenu de la demande
Content-EncodinggzipOptionnelFormat compressé du contenu de la demande. Datadog le recommande pour les lots de données volumineux.

Corps de la demande​

Le corps de la demande est un tableau contenant un ou plusieurs objets de journalisation. Chaque objet de journalisation comprend les champs suivants :

ChampTypeObligatoireDescription
messageChaîne de caractèresOuiContenu du message de journalisation
ddsourceChaîne de caractèresRecommandéLe nom d’intégration de la technologie à partir de laquelle provient le journal (log), tel que python ou nginx
ddtagsChaîne de caractèresOpcionalDes balises séparées par des virgules, comme env:prod,team:payments
hostnameChaîne de caractèresOptionnelNom de l’hôte qui a généré le journalisation
serviceChaîne de caractèresRecommandéNom de l’application ou du service concerné
statusChaîne de caractèresRecommandéLa gravité de l’événement de journalisation, par exemple info ou ERROR
timestampChaîne de caractèresOpcionalL’heure de l’événement, par exemple 2025-11-15T08:30:00Z. Voir la note sur le format de l’horodatage.
Remarque

Incluez obligatoirement message. Datadog utilise service, ddsource et ddtags pour filtrer, trier et comparer les données. Les autres champs sont optionnels.

Exemple de contenu de la demande​

Payload: single log
[
  {
    "message": "Transaction failed: Gateway timeout",
    "ddsource": "java",
    "ddtags": "env:prod,region:us-east-1",
    "hostname": "payments-host-01",
    "service": "payment-gateway",
    "status": "ERROR",
    "timestamp": "2025-11-15T08:30:00Z",
    "transaction_id": "txn_998877",
    "customer_id": "cus_554433"
  }
]
Remarque

Utilisez le format Coordonné Universel du Temps (UTC) de l’Organisation Internationale de Normalisation (ISO) pour timestamp. Datadog aligne la chronologie des journaux dans l’explorateur de journaux (Log Explorer) sur cette valeur. Les journaux sans horodatage utilisent l’heure d’ingestion. Datadog accepte des horodatages allant jusqu’à 18 heures dans le passé.

Exemple de commande cURL​

cURL
export DD_API_KEY="your_datadog_api_key_here"
export DD_SITE="datadoghq.com"

curl -X POST "https://http-intake.logs.$DD_SITE/api/v2/logs" \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "message": "Transaction failed: Gateway timeout",
      "ddsource": "java",
      "ddtags": "env:prod,region:us-east-1",
      "hostname": "payments-host-01",
      "service": "payment-gateway",
      "status": "ERROR",
      "transaction_id": "txn_998877"
    }
  ]'

Codes de réponse​

CodeÉtatDescription
202AcceptéLe contenu de la demande a été accepté et mis en file d’attente pour indexation
400Demande incorrecteErreur de formatage ou de validation
401Non autoriséL’en-tête DD-API-KEY manque
403InterditLa clé API est invalide ou ne dispose pas des autorisations nécessaires pour l’ingestion des journaux
408Délai d’attente de la demande expiréLa demande a expiré. Essayez à nouveau après un bref délai.
413Contenu de la demande trop volumineuxLe contenu dépasse les 5 Mo (non compressé)
429Trop de demandesLe client a dépassé la limite d’envoi de demandes
500Erreur interne du serveurDatadog a rencontré un problème inattendu. Essayez à nouveau après un bref délai.
503Service indisponibleDatadog est à pleine capacité. Essayez à nouveau après un bref délai.

202 : La demande a été acceptée​

Une réponse de type 202 Accepted confirme que Datadog a reçu le contenu de la demande. Le corps de la réponse contient un objet JSON vide. Les événements journaliers apparaîtront dans l’explorateur de journaux en quelques secondes.

Response: 202 Accepted
HTTP/1.1 202 Accepted
Content-Type: application/json
Response body: 202 Accepted
{}

400 : Demande incorrecte​

Datadog retourne ce code lorsque le contenu de la demande ne passe pas la validation :

  • 401 : Non autorisé et 403 : Interdit​

  • Le contenu du payload omet le champ obligatoire message.

  • 413 : Contenu de la demande trop volumineux​

Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Invalid JSON",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

401 non autorisé et 403 interdit​

Datadog retourne la valeur 401 Unauthorized lorsque l’en-tête DD-API-KEY est absent. Datadog retourne la valeur 403 Forbidden lorsque la clé API ne passe pas la validation ou que les autorisations d’ingestion des journaux sont manquantes.

Response: 403 Forbidden
{
  "errors": [
    {
      "detail": "Forbidden",
      "status": "403",
      "title": "Forbidden"
    }
  ]
}

413 contenu trop volumineux​

Datadog retourne ce code lorsque le contenu de la demande dépasse 5 Mo non compressés.

Response: 413 Payload Too Large
{
  "errors": [
    {
      "detail": "Payload too large",
      "status": "413",
      "title": "Payload Too Large"
    }
  ]
}

429 trop de demandes​

Vous avez envoyé trop de demandes. Envoiez-en moins, ou regroupez les objets de journalisation dans un seul ensemble de données (array payload).

Autres erreurs réessayables​

Datadog retourne également les valeurs 408 Request Timeout, 500 Internal Server Error et 503 Service Unavailable pour les échecs temporaires. Réessayez la demande avec un mécanisme de retraitement progressif. Envoyez des lots plus petits si le problème 408 Request Timeout persiste.

Grouper les événements de journalisation​

Vous pouvez envoyer jusqu’à 1 000 entrées de journalisation dans une seule demande en passant un tableau. Datadog recommande cette approche pour les services à fort volume.

Payload: batched logs
[
  {
    "message": "User login succeeded",
    "service": "auth-service",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "INFO"
  },
  {
    "message": "Transaction failed: Gateway timeout",
    "service": "payment-gateway",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "ERROR",
    "transaction_id": "txn_998877"
  }
]

Limites :

  • Taille de la charge utile : 5 Mo non compressés.
  • Taille d’un journal individuel : 1 Mo.
  • Entrées du tableau : 1 000 objets de journalisation.

Cas d'utilisation courants​

  • Consommer des journaux (logs) provenant de microservices sans déployer l’agent Datadog.
  • Envoyer des événements structurés de type JSON depuis des fonctions sans serveur telles que Amazon Web Services (AWS) Lambda ou Google Cloud Run.
  • Telemétrie en continu provenant de dispositifs IoT ou de services d’edge computing.
  • Affecter les événements enrichis à des systèmes d’information sur la sécurité et de gestion des événements (SIEM), à des services de stockage en ligne tels que S3, ou à des systèmes d’alerte via des pipelines de traitement des journaux (Log Pipelines).
  • Soumission des journaux de suivi (logs) provenant des pipelines d’intégration continue et de livraison continue (CI/CD), ou des scripts de déploiement.

ProblèmeCause probableSolution

400 Bad RequestFormat incorrect de la donnéeVérifiez avec jq . payload.json avant d’envoyer.
Ne pas se connecter à l’explorateurFiltre de pipeline excluant les logsEffacer les filtres. Vérifier ensuite les règles de routage de l’index.
Horodatage incorrectFormat non UTC ou non ISO 8601, ou datant d’il y a plus de 18 heuresUtilisez le format "2025-11-15T08:30:00Z". Envoyez les journaux d’activité dans les 18 heures suivant l’événement.
