Ingérer des événements avec l'API d'ingestion de logs Datadog

Envoyez des événements de log JSON directement dans Datadog Log Management avec l'API d'ingestion de logs. Vous pouvez envoyer des logs depuis des applications cloud, des microservices ou tout système qui émet de la télémétrie. Les logs apparaissent dans Log Explorer en quelques secondes. Utilisez les pipelines de logs pour les traiter, les acheminer et les archiver.

Ce point de terminaison prend en charge l'ingestion en temps réel et à haut débit de charges utiles JSON structurées et semi-structurées.

Actions prises en charge par cette API​

  • Envoyez des logs directement depuis des applications cloud sans installer l'agent Datadog.
  • Appliquez des processeurs de pipeline, comme Grok Parser, Remapper et Lookup Processor, aux données entrantes.
  • Acheminez les logs vers des index, des archives ou des destinations d'alerte selon leur contenu.
  • Réduisez les coûts d'indexation en combinant ce point de terminaison avec des règles d'échantillonnage et de filtrage.
Remarque

Consultez API et clés d'application Datadog pour gérer les identifiants.

Avant de commencer​

Vérifiez que vous disposez de :

  • Une clé API Datadog avec les autorisations d'ingestion de logs. Trouvez-la dans Paramètres de l'organisation → Clés API.

  • L'adresse de votre site Datadog. Cette adresse varie selon la région :

    RégionAdresse du site
    États-Unis Estdatadoghq.com
    US3 Ouestus3.datadoghq.com
    US5 Centreus5.datadoghq.com
    UEdatadoghq.eu
    AP1 Japonap1.datadoghq.com
    AP2 Australieap2.datadoghq.com

  • curl ou Postman installé.

  • Des charges utiles de logs au format JSON.

Point de terminaison d'ingestion​

POST https://http-intake.logs.{dd_site}/api/v2/logs

Remplacez {dd_site} par l'adresse du site de votre région, comme datadoghq.com ou ap2.datadoghq.com.

En-têtes de requête​

En-têteValeurObligatoireDescription
DD-API-KEY<your_api_key>OuiVotre clé API Datadog
Content-Typeapplication/jsonOuiFormat de la charge utile
Content-EncodinggzipFacultatifFormat de charge utile compressée. Datadog le recommande pour les lots volumineux.

Corps de la requête​

Le corps de la requête est un tableau JSON d'un ou plusieurs objets de log. Chaque objet de log accepte les champs suivants :

ChampTypeObligatoireDescription
messagestringOuiLe corps du message de log
ddsourcestringRecommandéLe nom de l'intégration de la technologie d'où vient le log, comme python ou nginx
ddtagsstringFacultatifDes balises séparées par des virgules, comme env:prod,team:payments
hostnamestringFacultatifLe nom de l'hôte qui a généré le log
servicestringRecommandéLe nom de l'application ou du service
statusstringRecommandéLa gravité de l'événement de log, comme info ou ERROR
timestampstringFacultatifL'heure de l'événement, comme 2025-11-15T08:30:00Z. Consultez la note sur le format d'horodatage.
Remarque

Incluez message. Datadog utilise service, ddsource et ddtags pour filtrer, créer des facettes et faire correspondre les pipelines. Les autres champs sont facultatifs.

Exemple de charge utile​

Payload: single log
[
  {
    "message": "Transaction failed: Gateway timeout",
    "ddsource": "java",
    "ddtags": "env:prod,region:us-east-1",
    "hostname": "payments-host-01",
    "service": "payment-gateway",
    "status": "ERROR",
    "timestamp": "2025-11-15T08:30:00Z",
    "transaction_id": "txn_998877",
    "customer_id": "cus_554433"
  }
]
Remarque

Utilisez le format ISO 8601 (Organisation internationale de normalisation) en temps universel coordonné (UTC) pour timestamp. Datadog aligne la chronologie des logs dans Log Explorer sur cette valeur. Un log sans horodatage utilise l'heure d'ingestion. Datadog accepte un horodatage jusqu'à 18 heures dans le passé.

Exemple cURL​

cURL
export DD_API_KEY="your_datadog_api_key_here"
export DD_SITE="datadoghq.com"

curl -X POST "https://http-intake.logs.$DD_SITE/api/v2/logs" \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "message": "Transaction failed: Gateway timeout",
      "ddsource": "java",
      "ddtags": "env:prod,region:us-east-1",
      "hostname": "payments-host-01",
      "service": "payment-gateway",
      "status": "ERROR",
      "transaction_id": "txn_998877"
    }
  ]'

Codes de réponse​

CodeÉtatDescription
202AcceptéCharge utile acceptée et mise en file pour l'indexation
400Requête incorrecteErreur de formatage ou de validation
401Non autoriséL'en-tête DD-API-KEY est absent
403InterditLa clé API est invalide ou dépourvue des autorisations d'ingestion de logs
408Délai de requête dépasséLa requête a expiré. Réessayez après un court délai.
413Charge utile trop volumineuseLa charge utile dépasse 5 Mo non compressés
429Trop de requêtesLe client a dépassé la limite de débit d'ingestion
500Erreur interne du serveurDatadog a rencontré une condition inattendue. Réessayez après un court délai.
503Service indisponibleDatadog est à saturation. Réessayez après un court délai.

202 Accepté​

Une réponse 202 Accepted confirme que Datadog a reçu la charge utile. Le corps de la réponse contient un objet JSON vide. Les événements de log apparaissent dans Log Explorer en quelques secondes.

Response: 202 Accepted
HTTP/1.1 202 Accepted
Content-Type: application/json
Response body: 202 Accepted
{}

400 Requête incorrecte​

Datadog renvoie ce code lorsque la charge utile échoue à la validation :

  • Syntaxe JSON incorrecte ou caractères non échappés.
  • La charge utile omet le champ message obligatoire.
  • La charge utile non compressée dépasse la limite de 5 Mo.
Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Invalid JSON",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

401 Non autorisé et 403 Interdit​

Datadog renvoie 401 Unauthorized lorsque l'en-tête DD-API-KEY est absent. Datadog renvoie 403 Forbidden lorsque la clé API échoue à la validation ou ne dispose pas des autorisations d'ingestion de logs :

Response: 403 Forbidden
{
  "errors": [
    {
      "detail": "Forbidden",
      "status": "403",
      "title": "Forbidden"
    }
  ]
}

413 Charge utile trop volumineuse​

Datadog renvoie ce code lorsque la charge utile de la requête dépasse 5 Mo non compressés.

Response: 413 Payload Too Large
{
  "errors": [
    {
      "detail": "Payload too large",
      "status": "413",
      "title": "Payload Too Large"
    }
  ]
}

429 Trop de requêtes​

Vous avez envoyé trop de requêtes. Envoyez-en moins, ou regroupez les objets de log dans une seule charge utile de type tableau.

Autres erreurs réessayables​

Datadog renvoie aussi 408 Request Timeout, 500 Internal Server Error et 503 Service Unavailable pour des défaillances passagères. Réessayez la requête avec un backoff exponentiel. Envoyez des lots plus petits si 408 Request Timeout persiste.

Regrouper les événements de log​

Envoyez jusqu'à 1 000 entrées de log dans une requête en passant un tableau. Datadog le recommande pour les services à fort volume.

Payload: batched logs
[
  {
    "message": "User login succeeded",
    "service": "auth-service",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "INFO"
  },
  {
    "message": "Transaction failed: Gateway timeout",
    "service": "payment-gateway",
    "ddsource": "python",
    "ddtags": "env:prod",
    "status": "ERROR",
    "transaction_id": "txn_998877"
  }
]

Limites :

  • Taille de la charge utile : 5 Mo non compressés
  • Taille d'un log : 1 Mo
  • Entrées du tableau : 1 000 objets de log

Cas d'usage courants​

  • Ingérer des logs depuis des microservices sans déployer l'agent Datadog.
  • Envoyer des événements JSON structurés depuis des fonctions serverless comme AWS Lambda (Amazon Web Services) ou Google Cloud Run.
  • Diffuser en continu la télémétrie d'appareils IoT ou de services de périphérie.
  • Acheminer les événements enrichis vers la gestion des informations et des événements de sécurité (SIEM), S3 ou des destinations d'alerte via les pipelines de logs.
  • Envoyer les logs depuis les pipelines d'intégration et de livraison continues (CI/CD) ou les scripts de déploiement.

Dépannage​

ProblèmeCause probableSolution
401 UnauthorizedClé API incorrecte ou absenteVérifiez DD_API_KEY dans Paramètres de l'organisation → Clés API
400 Bad RequestJSON mal forméVérifiez avec jq . payload.json avant l'envoi
Log absent de Log ExplorerFiltre de pipeline qui exclut le logEffacez les filtres. Vérifiez ensuite les règles de routage de l'index.
Horodatage dans le désordreFormat non UTC ou non ISO 8601, ou horodatage de plus de 18 heuresUtilisez le format "2025-11-15T08:30:00Z". Envoyez les logs dans les 18 heures suivant l'événement.
429 Too Many RequestsLimite de débit dépasséeRegroupez les objets de log dans une seule charge utile de type tableau
