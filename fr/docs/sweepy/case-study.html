« Quand 92 % signifie des choses différentes »

Une étude de cas sur l’écriture d’expériences utilisateur concernant les chaînes de caractères qui définissent leur propre contexte dans une interface en texte brut.

Sweepy est un outil de recherche d’emploi basé sur un terminal. Son interface utilise des caractères de dessin de boîtes et du texte coloré pour afficher les informations ; les explications doivent être intégrées directement dans le texte, car aucun bouton d’aide n’est disponible. La ligne d’état de l’outil ne s’affiche pas entièrement à l’écran. Chaque chaîne de caractères doit donc définir clairement son propre contexte.

Une règle fondamentale de l’interface de Sweepy : Chaque chaîne de caractères doit indiquer elle-même son contexte. Les étiquettes de score précisent par exemple qui a généré le chiffre affiché ; les informations d’état suivent la même logique, depuis la ligne d’état principale jusqu’aux suggestions d’aide associées aux différentes fonctionnalités de l’outil. Le calcul du score est particulièrement complexe, car un pourcentage peut sembler informatif même si l’utilisateur ne comprend pas comment l’outil l’a obtenu.

Deux pourcentages, deux questions​

Sweepy évalue les postes en fonction d’un CV de deux manières différentes.

Le premier outil est le scoreur déterministe, et chaque processus d’évaluation l’utilise. sweepy lance le processus d’évaluation, et START SWEEP attribue une note à chaque élément identifié par ce scoreur. sweepy --run réutilise le dernier profil enregistré sans ouvrir de guide d’utilisation. Cette étape compare deux documents : elle compte le nombre de mots communs entre le CV et la publication, en pondérant à 60 % le chevauchement des exigences et à 40 % le chevauchement des mots-clés, puis ajuste le résultat avec resume.keywords_weight. Un terme n’est pris en compte que s’il figure dans les deux documents. Le scoreur ne juge jamais si le lecteur serait capable de réaliser le travail décrit dans le CV.

Le deuxième élément est une évaluation de l’agent, disponible via le Model Context Protocol (MCP). L’agent lit à la fois le CV analysé et l’annonce d’emploi, puis évalue dans quelle mesure le candidat correspond au poste. Il soumet son propre pourcentage de correspondance via submit_judgments.

Le nombre de mots communs et l’appréciation de l’agent répondent à des questions différentes. Le comptage des mots communs mesure le degré d’alignement entre les deux documents, pas leur adéquation ; par conséquent, l’étiquette doit indiquer l’auteur du document. Ce comptage révèle la quantité de texte partagée entre le CV et l’annonce d’emploi. L’agent évalue dans quelle mesure une personne correspond à un poste donné. Un CV peut reproduire mot pour mot le contenu de l’annonce sans pour autant refléter une bonne adéquation ; un CV utilisant un vocabulaire différent peut pourtant démontrer une meilleure correspondance. Le comptage des mots repère le premier cas, mais pas le second, tandis que l’agent peut prendre en compte les deux éléments.

La carte affiche un seul score. C’est l’auteur le plus récent qui définit ce score, et une évaluation réajuste le classement du rapport en fonction de cette nouvelle valeur. L’appréciation de l’agent remplace le score déterministe. Un pourcentage simple ne permet pas au lecteur de savoir quel auteur a établi le score.

Le nom de l’auteur devait être indiqué dans la ligne de la carte, avant que le lecteur n’ouvre l’annonce d’emploi. Le reste de l’interface suit la même règle.

De la plateforme de lancement aux résultats​

Le processus se déroule comme suit : plateforme de lancement → assistant de configuration → analyse → résultats. Lorsque l’analyse dépasse la limite de temps imparti par l’outil du client, elle passe en état de consultation, et ce statut reste affiché jusqu’à la fin de l’opération.

Les cartes 3 à 8 suivent cet ordre. La carte 2 présente le score, qui n’apparaît qu’après la fin de l’analyse et constitue la base sur laquelle le reste de la page est construit. La carte 1 décrit le problème, et la carte 9 explique les contraintes associées à chaque candidat.

01 / 09

Un emplacement de score, deux auteurs​

Chaque analyse attribue un score à chaque carte en se basant sur le nombre de mots communs. Cependant, une évaluation de type MCP remplace ce score par sa propre interprétation. En l’absence de différenciation claire dans les étiquettes, le lecteur ne peut pas déterminer qui a établi le score et ne peut donc pas évaluer la fiabilité de celui-ci.

Distinguer un chiffre d'un jugement​

Même profil, même numéro ; deux écrivains. Un agent a défini la première information (92% MATCH), tandis qu’un système de notation déterministe a défini la seconde (92% KEYWORD OVERLAP). L’étiquette indique l’écrivain responsable de chaque information. Un lecteur qui ne voit que 92 % des données n’a aucun moyen de distinguer les deux informations. L’évaluation remplace la valeur préexistante dans la même case, car les critères et les jugements portent sur des questions différentes.

  • 92% KEYWORD OVERLAP représente le nombre de mots communs entre le CV et le poste proposé.
  • 92% MATCH désigne le score obtenu par l’agent en analysant la pertinence du candidat pour le poste.

L’outil enregistre le résultat de chaque étape de traitement sur chaque carte générée, que ce soit depuis l’interface utilisateur ou via la commande run_sweep via MCP. Seule une réponse validée (match_pct) remplace cette valeur par MATCH.

La ligne concernant le rang PDF répète l’étiquette entre parenthèses : #1 // COMPANY | [92% MATCH] ou [92% KEYWORD OVERLAP]. Le fichier CSV affiche match_value à côté de match_kind, ce qui fournit au lecteur la même information sous une forme lisible par les machines. Un troisième score peut également apparaître à côté du score de la rencontre. [88% PORTFOLIO FIT] affiche son propre étiquette pour la même raison : vos échantillons répondent à une question différente de celle de votre CV.

L’icône de l’application est d’abord affichée sous forme de texte, puis en couleur. “[STANDARD / QUICK APPLY]” indique une soumission standard, tandis que “[EXTENDED RESPONSES REQUIRED]” indique un poste nécessitant des exemples d’écriture. La troisième carte affiche “[EXTENDED RESPONSES REQUIRED]” ainsi que le parcours professionnel du candidat. Les deux étiquettes sont visibles même sans couleur, ce qui est important pour l’accessibilité et pour les appareils qui ne peuvent pas afficher les couleurs.

Identité, portée et état de préparation en une seule ligne​

La ligne “Current profile: none loaded / build one to start” indique l’état actuel du profil et l’action à entreprendre. La ligne “Current profile: Alex Rivera / 4 titles / Ready” confirme le nom du candidat ainsi que son niveau de préparation. Chaque barre oblique sépare les différentes informations ; la ligne ne s’affiche pas sur toute la largeur de l’écran. “Resume missing” remplace “Ready” lorsque le profil sauvé ne contient pas de chemin vers le CV.

Dans une interface graphique, la ligne d’état est le seul élément persistant ; elle sert à la fois de titre et d’indicateur de préparation du candidat.

Verbe, complément d'objet, puis l'objectif du lecteur​

Les paires START SWEEP et Run your job search now correspondent aux éléments de l’interface. Chaque « tuile » affiche deux lignes : un nom et un sous-titre qui résument la fonction de l’option « Entrer » en termes compréhensibles pour l’utilisateur. La ligne SWEEP SETTINGS contient le contenu de la ligne Ranking, cards, tracking ; la ligne SWEEPY'S TOOLBOX contient le contenu de la ligne Edit profile, logs, help. La ligne EXIT SWEEPY présente la fonction de la ligne Save changes and close, qui vise à aider l’utilisateur à conserver son travail (c’est-à-dire à sauvegarder ses données).

Les tuiles représentant des actions commencent par un verbe et son objet ; les autres indiquent un lieu ou une sortie. Les sous-titres expliquent les termes techniques en langage clair. Les nombres à deux chiffres identifient chaque tuile (pas l’ordre dans lequel elles sont disposées). La première ligne du tableau associe les tuiles 01 et 04. Il est possible d’ajouter des tuiles sans modifier l’ordre général du tableau. La navigation se fait à l’aide des flèches et de la touche Enter.

Conseils de mise en forme dans l'invite​

Les instructions sont écrites sur une seule ligne ; lorsque le formatage est important, la règle correspondante est indiquée en retrait.

Job roles
What job titles are you looking for?
  (Separate multiple titles with a comma)

L’instruction relative au salaire mentionne explicitement l’option de saut.

Salary
What is your minimum target salary? (Leave blank to skip):

La règle est affichée juste à côté de l’option permettant de modifier la réponse ; l’utilisateur reste sur l’écran pendant la modification. Les terminaux ne proposent pas d’outils d’aide visuelle (tooltip).

Modifier une réponse sans relancer l'assistant​

L’assistant guide l’utilisateur à travers quinze étapes ; la touche Esc permet de revenir à une question précédente. L’écran d’examen liste les différentes options proposées (← Back, Submit profile, puis neuf autres actions). La commande Edit an answer se trouve directement en dessous de la carte Submit profile. La fonction de révision est accessible après avoir soumis les réponses. Si l’utilisateur souhaite modifier une réponse, il n’est pas nécessaire de réexécuter toutes les étapes.

Libellés des cinq étapes​

L’exécution depuis la ligne de commande marque les cinq étapes, chacune indiquant le travail effectué.

[1/5] Loading profile...
[2/5] Discovering roles...
[3/5] Validating URLs...
[4/5] Scoring against resume...
[5/5] Generating reports...

Les lignes de journal affichent le numéro de l’étape ; les données de progression fournies par MCP décrivent en revanche le détail du travail (comme dans les exemples step 3 et total 5, étiquetées respectivement Validating URLs). La ligne Scoring roles présente la liste des éléments sélectionnés pendant l’évaluation. Les lecteurs peuvent ainsi savoir à quel stade se trouve l’exécution et quels éléments restent à traiter. Une barre de progression pourrait suggérer une durée que l’outil ne peut pas connaître.

L'attente qui renvoie un identifiant de tâche​

Une opération de nettoyage en temps réel peut durer plus d’une minute. En mode MCP, l’appel de l’outil renvoie directement l’état de l’exécution sans attendre la fin de l’opération, ce qui permet de respecter la limite de temps imparti au client et indique que le travail se poursuit.

Par défaut, run_sweep attend 45 secondes ; wait_seconds ajuste cette durée, tandis que SWEEPY_MCP_WAIT_SECONDS réduit cette limite pour certains types de serveurs. L’état de l’exécution comprend des informations telles que l’objet job_id, la valeur progress, la valeur elapsed_seconds, et d’autres données (message).

MCP running state
{
  "status": "ok",
  "sweep_status": "running",
  "job_id": "<job id>",
  "progress": { "step": 3, "total": 5, "label": "Validating URLs" },
  "elapsed_seconds": 41.2,
  "debug_log": "<path>",
  "message": "The sweep is still running. Call get_sweep_status to wait for it, then continue with get_jobs."
}

Le client effectue des demandes à get_sweep_status en utilisant job_id jusqu’à ce que sweep_status ait lu le contenu de "completed". Le processus Sweepy continue de s’exécuter, même si le client reste connecté. Le contenu transmis doit être conforme aux délais impératifs et pouvoir être lu correctement par un client qui se reconnectera ultérieurement. Il s’agit d’un état dynamique qui permet de suivre l’avancement du travail.

La durée de 45 secondes est une valeur par défaut définie par _DEFAULT_WAIT_SECONDS et limitée par _MAX_WAIT_SECONDS ; les valeurs de progress et elapsed_seconds peuvent varier à chaque exécution, tout comme celle de debug_log. La ligne message indique le nom de l’appel d’outil suivant, plutôt que de répéter les numéros déjà connus du client.

Impossible de dissimuler un texte médiocre​

L'interface repose uniquement sur du texte, et le cadre coupe tout ce qui dépasse. Une étiquette doit être autonome, car aucun autre élément à l'écran ne la explique. Les messages d'état indiquent où en est le lecteur, sans qu'il y ait de curseur de chargement sur lequel s'appuyer.

La règle de nommage est respectée : START SWEEP, LOAD PROFILE et BUILD PROFILE commencent par l’action correspondante. Leurs sous-titres la réaffirment en tant qu’objectif du lecteur, de sorte que personne n’a besoin de comprendre le concept de “profil” pour savoir ce qui suit. L’étiquette “score” applique la même règle aux nombres. KEYWORD OVERLAP indique le comptage déterministe, tandis que MATCH représente le jugement d’un agent.

La largeur du cadre tronque les chaînes trop longues​

Le terminal définit les règles de présentation du texte. Le texte est le seul élément qui fournit des informations explicites ; les éléments trop longs sont coupés. Une erreur doit indiquer à la fois le problème et la solution dans la même ligne, afin que le lecteur ne puisse pas passer à une autre ligne pour obtenir plus d’informations.

Chaque chaîne de caractères est contextualisée : Could not parse salary %r. Enter a number like 65000, 65,000, or 65k. indique ce qui a échoué et ce qu’il faut saisir à la place ; %r remplace l’entrée rejetée ; Current profile: none loaded / build one to start fait de même pour un profil manquant. Une interface graphique pourrait afficher la seconde moitié de ces informations dans une aide contextuelle. Ici, chaque ligne contient les deux parties de l’information.

L'étiquette comme seule explication​

L’étiquette indique qui a créé le résultat affiché. Les documents précisent : « Une carte MATCH reflète un jugement ; une carte KEYWORD OVERLAP reflète des informations partagées ». Une étiquette est imprimée à côté du résultat pour que le lecteur sache immédiatement d’où provient cette information.

Chaque étiquette indique également le type de comparaison ayant produit le résultat : KEYWORD OVERLAP concerne deux documents, tandis que MATCH concerne une personne et un poste de travail. Un lecteur qui s’attend à ce que les deux chiffres soient cohérents pourrait interpréter incorrectement les données.

L’étiquette correspond à l’auteur de l’analyse, et non à l’interface utilisée pour effectuer celle-ci. Un agent peut soumettre un jugement sans fournir de pourcentage ; cette carte affiche donc toujours la valeur « KEYWORD OVERLAP », car c’est le chiffre qui a été saisi lors de l’analyse. Le chemin d’exécution des instructions se trouve en dehors de cette carte. Le nom du fichier de rapport indique le type d’exécution (MCP) en utilisant la valeur « mcp », et l’en-tête du journal d’activité affiche la méthode d’exécution utilisée.

La nomination des éléments graphiques (comme les « tiles ») suit la même règle : BUILD PROFILE indique l’action effectuée par cet élément, tandis que son sous-titre Set up your job search présente le résultat attendu par l’utilisateur. LOAD PROFILE précise ensuite Open a search you saved, qui décrit la fonction de ce même élément graphique.

Ce que j’ai rédigé et comment je l’ai vérifié​

Rôle. J’ai rédigé toutes les chaînes de caractères relatives aux produits citées dans ce cas d’étude. Ces chaînes concernent les sous-titres des écrans d’information, les messages d’encouragement affichés par l’assistant, les notifications de progression, ainsi que les informations de validation. Les étiquettes indiquant l’origine des scores et le transfert de données entre les systèmes (message) ont été ajoutées ultérieurement. J’ai supervisé la création de ces éléments à l’aide des outils Copilot et Gemini, en suivant les directives définies au niveau du répertoire et les critères de qualité mis en place par le système de contrôle continu (CI). J’ai également vérifié la précision de ces chaînes de caractères par rapport au code source de Sweepy.

Évaluez le niveau de confiance, puis agissez​

Avant de prendre une décision basée sur un résultat, il est important de s’assurer de la fiabilité du système. L’interface ne peut pas expliquer comment Sweepy a calculé le résultat ou combien de temps a pris le processus. Les étiquettes et les messages d’état le font de manière concise, même en l’absence d’éléments visuels d’information.
