当‘92%’代表不同含义时

关于在纯文本界面中某些字符串如何自行解释其含义的UX写作案例研究。

Sweepy是一款基于终端的求职工具，其界面使用绘图字符和彩色文本来展示信息，并能读取用户的键盘输入。所有说明都必须直接包含在文本中（因为工具没有提示功能）。该工具的状态信息会被截断在屏幕边缘，无法完整显示；如果字符串超出屏幕宽度，其结尾部分也会被截断。

由此得出了一个设计原则：每个字符串都必须自行解释其含义。例如，得分标签会标明分数的来源；状态信息也遵循这一规则（从工具的启动界面底部到每个提示信息的格式说明都是一致的）。其中，得分部分的处理较为复杂——无论用户是否了解工具的具体计算方式，百分比数值本身都具有参考价值。

两种评分方式，两个问题​

Sweepy通过两种不同的方式对求职申请和简历进行评分：

第一种评分方法是“确定性评分器”（deterministic scorer）：每次评估都会使用该方法。sweepy用于启动评分流程，START SWEEP会为评估中发现的每一项内容打分。sweepy --run会重复上次保存的评分结果（无需重新打开评估工具）。该方法会比较简历和招聘信息中的共同词汇，其中职位要求匹配度占60%，关键词匹配度占40%，最终结果会通过resume.keywords_weight进行加权处理。只有当某个术语同时出现在简历和招聘信息中时，才会被计入评分。该评分器不会考虑求职者是否具备完成工作所需的能力。

第二种评分方法是“代理评估”（agent assessment），通过“模型上下文协议”（Model Context Protocol, MCP）实现：代理会同时读取解析后的简历和招聘信息，然后判断求职者是否符合职位要求，并通过submit_judgments提交自己的评分结果。

单词共享统计结果与机器人的判断会回答不同的问题：单词共享统计仅反映文本的相似度，而非匹配程度；因此标签必须标明文档的作者。该统计显示简历与招聘信息中重复出现的文字数量。而机器人则会评估某人是否适合某个职位。即使简历完全照搬了招聘信息中的表述，也可能说明匹配度较低；反之，使用不同词汇的简历可能表明匹配度较高。单词共享统计只能发现第一种情况，而机器人则能同时考虑这两种因素。

该卡片显示一个评分结果。这个评分由最新的文档作者设置，之后系统会根据新的评分重新对报告进行排序。机器人的评估结果会取代原有的固定评分，而不是简单地与其并列显示。仅显示百分比的话，读者无法判断评分是由哪位作者提供的。

在读者打开招聘信息之前，系统必须在徽章区域注明文档的作者。界面的其他部分也遵循这一规则。

从启动平台到结果​

整个流程依次为：启动平台（launchpad）→ 设置向导（setup wizard）→ 数据分析（sweep）→ 结果展示（results）。

当数据分析耗时超过客户设定的时间限制时，系统会将该任务的状态更改为“可投票”状态，并保持该状态直到分析完成。

第3至第8张卡片按照上述顺序排列。第2张卡片展示评分结果（该评分仅在数据分析完成后才会生成），其余卡片则基于此评分进行内容展示。第1张卡片介绍问题背景，第9张卡片说明各卡片内容所遵循的约束条件。

01 / 09

一个评分槽，两位作者​

一个评分槽，两个可能的作者。 每次扫描都会根据确定性的重叠计数为每张卡片评分。但MCP评估会根据其自身的推理逻辑覆盖该数值。如果没有明确的标记差异，读者无法分辨是哪位作者设定的评分，也无法校准信任度。内容设计的核心挑战在于，如何在徽章行内仅用寥寥数词就区分出作者身份。

如下是两张PDF格式的评分报告示例：​

第三名职位的PDF评分报告，显示评分为88%（使用两种评分方法），同时标有“提交轨迹”（submit track）和“扩展回答”（extended-responses）的标志](./screenshots/sweepy-11-pdf-extended-status.png)

使用相同的个人资料和编号，但由两位不同的作者完成填写。第一张卡片的内容由代理设置（因此显示为 92% MATCH），第二张卡片的内容由评分系统设置（因此显示为 92% KEYWORD OVERLAP）。标签用于标识作者的身份。如果读者只能看到其中92%的信息，他们将无法区分这两张卡片的内容。评估结果会覆盖同一位置上的重复分数，因为评分标准和判断依据不同。

  • “92% KEYWORD OVERLAP”表示简历与招聘信息中共同出现的词汇数量。
  • “92% MATCH”表示代理通过分析读者是否符合职位要求得出的评分结果。

“Sweepy”会在生成的每张卡片上记录该评分结果；无论这些卡片是通过终端输入的，还是通过 run_sweep 在 MCP 系统中生成的，只有当评分结果为 match_pct 时，才会被替换为 MATCH。

PDF 格式的文件会在排名信息栏中以括号的形式显示标签（#1 // COMPANY | [92% MATCH] 或 [92% KEYWORD OVERLAP]）；CSV 格式则会在 match_kind 旁边显示 match_value，以便读者能够以机器可读的方式获取相同的信息。有时还会在匹配分数旁边显示第三种评分结果（[88% PORTFOLIO FIT]），这是因为这些评分标准与简历所回答的问题不同。

应用程序的徽标首先以文本形式显示，颜色作为次要信息。[STANDARD / QUICK APPLY] 表示标准提交的申请；[EXTENDED RESPONSES REQUIRED] 表示需要提交写作样本的职位。第三张卡片会在排名信息栏中显示 [EXTENDED RESPONSES REQUIRED]，同时也会列出申请者的简历信息。这两种标签都可以无颜色显示，这对于提高可访问性以及那些无法显示颜色的终端设备来说非常重要。

一行内容中包含身份、工作范围以及申请者的准备情况。​

Current profile: none loaded / build one to start 一行内容同时说明了个人资料的缺失状态及下一步操作；Current profile: Alex Rivera / 4 titles / Ready 则在第一栏确认了申请者的姓名，在最后一栏确认了其准备情况。每个斜杠用于分隔不同的信息项，且该行内容会紧贴界面边缘显示（不会换行）。当保存的个人资料中没有简历路径时，Resume missing 会替换 Ready。

在终端设备中，状态栏是唯一持续显示的信息来源；它既充当标题，也起到准备状态指示的作用。

先列出动词/对象，再说明读者的目标。​

START SWEEP与Run your job search now配对显示；每个评分项会输出两行内容：名称以及用求职者自己的话解释该评分项的作用。SWEEP SETTINGS负责读取Ranking, cards, tracking中的评分结果，SWEEPY'S TOOLBOX负责读取Edit profile, logs, help中的评分结果，EXIT SWEEPY负责读取Save changes and close中的评分说明（承诺会保存用户的评分数据）。

行动相关的瓷砖以动词及其宾语的形式呈现；其他瓷砖则标注了具体位置或退出路径。副标题用通俗的语言解释了其中的专业术语。两位数用于标识每个瓷砖，而非表示网格的顺序。顶部行将01与04配对；新增的瓷砖会直接加入网格，而不会改变其他瓷砖的编号顺序。导航功能通过箭头键和“Enter”键实现。

提示信息中的格式说明：​

提示词可将问题保持在一行内，当格式重要时，将规则置于问题下方并缩进：

Job roles
What job titles are you looking for?
  (Separate multiple titles with a comma)

规则会出现在用户做出选择的那一行；此时用户无需离开屏幕（因为终端没有提示工具）。

Salary
What is your minimum target salary? (Leave blank to skip):

该规则显示在做出决策的那一行。阅读器仍停留在屏幕上。终端没有可作为后备的工具提示。

在不重新运行向导的情况下编辑答案​

这个向导会执行十五个步骤；用户可以通过按 Esc 键逐个撤销之前的回答。审核界面会依次显示 eleven 个条目（← Back、Submit profile）以及九个可执行的操作。Edit an answer 条目位于 Submit profile 的正下方；“Revision”（修订）选项位于提交按钮的下一行。如果用户想要修改某个答案，无需重新运行所有的提示或流程。

这五个步骤的阶段标签​

命令行运行会标记出五个编号的阶段，每个阶段都说明了相应的操作内容。

[1/5] Loading profile...
[2/5] Discovering roles...
[3/5] Validating URLs...
[4/5] Scoring against resume...
[5/5] Generating reports...

日志记录中会显示当前的阶段编号；而来自MCP的进度数据则会实际报告执行的具体工作内容（例如step 3、total 5、Validating URLs）。Scoring roles阶段会记录评分结果。读者可以据此了解当前运行的状态以及剩余的工作内容。不过，进度条可能会给人一种工具能够预测完成时间的错觉，但实际上工具无法做到这一点。

返回作业ID的等待过程​

实时扫描可能需要一分钟或更长时间才能完成。在MCP模式下，工具会立即返回运行状态，而不会等待整个扫描过程结束。这样既能避免超出客户端的超时限制，也能让调用者知道任务仍在继续进行中。

默认情况下，run_sweep阶段的等待时间为45秒；wait_seconds阶段可以调整这个时间范围（介于0到600秒之间）；SWEEPY_MCP_WAIT_SECONDS阶段则针对资源受限的主机进一步缩短等待时间。运行状态包括job_id、progress对象、elapsed_seconds值以及message信息。

MCP running state
{
  "status": "ok",
  "sweep_status": "running",
  "job_id": "<job id>",
  "progress": { "step": 3, "total": 5, "label": "Validating URLs" },
  "elapsed_seconds": 41.2,
  "debug_log": "<path>",
  "message": "The sweep is still running. Call get_sweep_status to wait for it, then continue with get_jobs."
}

客户端会持续向 get_sweep_status 发送请求，并与 job_id 进行交互，直到 sweep_status 读取到 "completed" 的内容为止。无论客户端是否保持连接状态，Sweepy 都会继续执行后续的处理流程。处理后的数据必须能够在规定的超时时间内被传输完毕，并且能够被重新连接的客户端正确地接收。这是一个持续运行的过程，用于实时显示处理进度。

45秒的等待时间是产品的默认设置，由_DEFAULT_WAIT_SECONDS阶段设定，并由_MAX_WAIT_SECONDS阶段进行上限控制；progress和elapsed_seconds阶段会根据每次运行的具体情况进行调整；debug_log阶段也会相应变化。message阶段用于标识下一次需要调用的工具。

薄弱文案无处可藏​

该界面仅依赖文本，且框架会截断超出长度的内容。标签必须自成一体，因为屏幕上没有其他内容对其进行解释。状态消息会显示读者当前所在的位置，且没有旋转图标作为参考。

命名规则如下：START SWEEP、LOAD PROFILE和BUILD PROFILE以具体操作为主；它们的副标题会明确说明读者的目标，因此无需了解内部的“配置文件”概念就能理解接下来的步骤。数字标签也遵循相同的规则：KEYWORD OVERLAP表示确定的操作次数，MATCH则表示代理的判断结果。

界面会截断过长的字符串​

终端负责设定显示规则；只有文本层能够提供完整的信息，而界面会自动截断过长的内容。错误信息必须在同一行中同时说明问题及解决方法。读者无法跳过当前行去查看其他内容。

这些字符串本身就包含了所需的上下文信息：Could not parse salary %r. Enter a number like 65000, 65,000, or 65k.用于报告出错的内容以及应输入的修正值；%r则用于替换被拒绝的数据项；Current profile: none loaded / build one to start用于处理缺失的配置文件。图形用户界面（GUI）可以将这两部分信息分别显示在工具提示框中，但这里的代码直接将它们合并在同一行中。

标签是唯一的解释来源​

分数标签会显示数据的来源（例如“MATCH”表示数据来自某人的判断，“KEYWORD OVERLAP”表示数据来自多人讨论的结果）。每个标签会单独打印在卡片上，读者在查看详细信息前就能知道数据的来源。

每个标签还会说明生成该数值的具体比较依据：KEYWORD OVERLAP用于对比两份文档，MATCH用于对比个人与工作表现等。如果读者误以为这两个数值应该一致，就会产生误解。

标签记录的是数据的生成者，而非界面的设计方式；即使没有提供百分比，系统仍会使用默认的标签（如“KEYWORD OVERLAP”）。执行路径等信息存储在系统外部，报告文件名会用mcp标记MCP（Machine Learning Pipeline）的执行结果，日志头则会显示具体的执行方法。

图标的命名遵循相同的规则：BUILD PROFILE部分说明了图标的功能，其副标题Set up your job search则用更通俗的语言向用户解释该图标的实际用途。LOAD PROFILE部分引用了Open a search you saved的描述，进一步说明该图标的具体作用。

我的编写过程及验证方法​

职责。 这个案例研究中的所有产品相关文本（包括标题、提示信息、进度提示以及验证结果等）都是我亲自编写的。其中，关于分数来源的标签以及客户传递的“MCP handoff message”部分也是由我完成的。我使用 Copilot 和 Gemini 工具进行代码编写，并遵循了仓库级别的开发规范及持续集成（CI）的质量控制流程。在完成编写后，我还将所有产品文本与 Sweepy 源代码进行了逐一核对。

先评估信任度，再采取行动​

在根据分数做出决策之前，读者应先评估系统的可靠性，并了解系统在处理数据时的具体流程。界面本身无法解释数据是如何生成的或某个任务耗时多久；标签和状态信息会用最简洁的方式说明这些细节，即使在没有视觉辅助的情况下也能让读者理解。
