处理支付Webhook

  • 目标受众：需要可靠订单处理触发机制的开发者（即拥有支付流程的开发者）。
  • 先决条件：一个可通过HTTPS访问的服务器端点，以及从Stripe控制台获取的签名密钥。
  • 目标：接收payment_intent.succeeded事件，验证其签名，并仅完成一次订单处理。

完成本教程后，您将掌握一个能够拒绝伪造数据并记录每次订单处理的处理程序；所有操作都必须在响应超时时间内完成。请注意，签名验证会在任何业务逻辑之前执行。

当对象状态发生变化时，Stripe会发送Webhook。您的端点接收到该事件后，需验证签名并采取相应行动；处理程序必须在超时时间内做出响应，否则Stripe会认为配送失败并重新尝试。

传递路径​

当状态发生变化时，Stripe 会在几秒钟内将相关事件推送到您的端点。您的处理程序会通过返回一个 2xx 状态码来确认收到事件，随后再处理该事件。

这些编号步骤是按照一定的顺序排列的。第7步表明：在客户端已经看到结果之后，相关事件才会发生；因此，客户端无法作为触发执行操作的组件（即“fulfillment trigger”）。

配置端点​

在仪表盘的 开发者 → Webhooks → 添加端点 下注册该端点。创建端点时，Stripe 会显示签名密钥。仪表盘稍后会再次显示该密钥。

设置本指南适用的值
端点地址https://api.example.com/webhooks/stripe
需要发送的事件payment_intent.succeeded, payment_intent.payment_failed, charge.refunded
API 版本您编写处理程序时所使用的 API 版本

一个会订阅所有事件的处理程序会接收大量数据，但它实际上并不会读取这些数据。请选择该处理程序需要处理的事件类型，并在代码发生变化时添加更多需要处理的事件。

备注

端点的 API 版本可能与您账户中设置的版本不同；事件会根据绑定到端点的 API 版本来传递，因此在记录事件数据时请务必查看事件的 api_version 状态码。

读取原始请求体​

签名验证需要Stripe发送的原始字节数据。如果将接收到的数据解析成对象（即去除其中的空白字符并重新排列键的顺序），签名验证将会失败。

server.js
import express from "express";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const app = express();

// Keep the raw body for the webhook route only.
app.post(
  "/webhooks/stripe",
  express.raw({ type: "application/json" }),
  handleWebhook
);

// Every other route parses JSON.
app.use(express.json());

在 JSON 解析器之前注册原始解析器；否则，当 JSON 解析器先读取数据流时，会导致请求的原始数据为空，并且签名验证会失败。

验证签名​

Stripe 会使用端点密钥（endpoint secret）对每次配送进行签名处理；系统会在常数时间内计算预期的签名值，并将其与实际签名值进行比对。

server.js
async function handleWebhook(req, res) {
  const signature = req.headers["stripe-signature"];

  let event;

  try {
    event = stripe.webhooks.constructEvent(
      req.body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET
    );
  } catch (err) {
    console.error("Signature verification failed:", err.message);
    return res.status(400).send(`Webhook error: ${err.message}`);
  }

  res.status(200).json({ received: true });

  await dispatch(event).catch((err) => {
    console.error("Handler failed:", err.message);
  });
}

当接收到的数据的时间戳超出允许的范围时，constructEvent 会重新计算签名并拒绝该数据；之后会返回一个错误信息。这三个检查步骤会在您的代码处理数据之前执行。

危险

绝不要信任未经验证的负载数据——如果没有签名验证机制，任何获取到端点地址的人都可以伪造订单状态或触发退款操作。

先响应，再处理​

Stripe 会等待约 20 秒以接收响应；如果处理订单的程序因依赖库运行缓慢而超时，或者同一路径下的数据分析更新导致延迟，系统会重新发送请求。

将处理流程分为两个阶段：

  1. 确认接收事件：验证签名的有效性，并返回 200 状态码。
  2. 处理流程。 将该事件交由能够重试该耗时操作的工作线程处理。

下面的示例中，处理程序在响应后立即调用了 dispatch；如果处理过程耗时较长，建议将该调用放入队列中异步处理。

dispatch.js
async function dispatch(event) {
  switch (event.type) {
    case "payment_intent.succeeded":
      return handleSucceeded(event.data.object);
    case "payment_intent.payment_failed":
      return handlePaymentFailed(event.data.object);
    case "charge.refunded":
      return handleRefunded(event.data.object);
    default:
      return;
  }
}

如果配送失败，Stripe 会尝试重试；如果响应延迟，系统也可能重复发送相同类型的事件。因此，您的处理程序必须能够正确处理重复的数据。

确保仅处理一次​

当交付失败时，Stripe 会尝试重新发送；如果响应速度较慢，它也可能重复发送同一条事件。因此，您的处理程序必须能够正确处理这些重复的事件。

fulfillment.js
async function handleSucceeded(intent) {
  const already = await hasProcessed(intent.id);
  if (already) return;

  const orderId = intent.metadata.order_id;
  if (!orderId) {
    console.warn("Missing order_id on intent", intent.id);
    return;
  }

  await markOrderPaid(orderId, intent.id);
  await recordProcessed(intent.id);
}

将事件ID或对象ID存储在一个唯一的索引中，以便数据库能够拒绝重复的写入操作。当两个请求同时到达时，会触发签名验证（signature check）；唯一性约束可以防止这种竞争情况的发生。

提示

对于一次性事件（one-shot events），去重表使用键event.id进行标识；对于状态更新事件（state events），则使用键object.id进行标识。每次退款操作都会生成一个charge.refunded类型的事件记录。只有对象ID在重复支付的情况下才会被标记为重复项。

处理失败事件​

如果支付失败，系统会发送payment_intent.payment_failed。请查看拒绝支付的代码（decline code），并判断客户是否能够重新尝试支付。

failures.js
async function handlePaymentFailed(intent) {
  const error = intent.last_payment_error;
  const code = error?.decline_code ?? error?.code;

  const recoverable = ["insufficient_funds", "processing_error"];
  const canRetry = recoverable.includes(code);

  await recordDecline(intent.metadata.order_id, code, canRetry);

  if (canRetry) {
    await sendRetryEmail(intent.metadata.order_id);
  }
}

不要自行安排重试失败的支付请求——如果发卡机构（issuer）已经阻止了该卡的支付，再次尝试只会使账户记录中增加一条拒绝记录。

在本地测试端点​

Stripe 命令行工具会将实时测试事件转发到本地服务器，因此您无需部署即可查看交付情况。

stripe login
stripe listen --forward-to localhost:4242/webhooks/stripe

第一个终端会显示事件详情，服务器日志会显示处理程序的输出结果。将签名密钥设置为错误的值，确认端点仍会返回whsec_，从而证明签名验证机制正常运行。

stripe trigger payment_intent.succeeded

第一个终端窗口会显示事件详情，服务器日志则会记录处理程序的输出结果；如果将端点秘钥设置成错误的值，系统仍会返回 400 状态码，这证明签名验证机制确实被触发了。

症状原因解决方法
每次数据传输时都会进行400 验证签名验证失败请使用正确的端点秘钥；同时保持原始数据的原始格式（未解析的状态）。
在库升级后，出现了 400。解析器在验证之前修改了数据内容。将原始解析器的执行位置提前到 JSON 解析器之前。
一次配送任务重复执行了处理程序超时后仍未完成处理。首先需要确认该任务的状态，然后由后台工作进程进行处理。
处理程序日志中显示了重复的记录。响应超时了，或者重试操作发生了重叠。对于状态相关的事件（在 object.id 处处理），以及对一次性发生的事件（在 event.id 处处理），需要执行去重操作。

重放旧事件​

仪表盘会保存事件负载，并允许您重新发送其中一个。打开 开发者 → Webhooks → 您的端点 → 事件，选择该事件，然后点击 重新发送。

重新发送请求是验证处理程序更改效果的最佳方式（使用真实的数据包）。务必记录响应代码，因为如果重新发送请求后仍返回500，那么在实际生产环境中也会出现错误。
