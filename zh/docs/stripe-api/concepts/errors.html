错误与重试

Stripe会以HTTP状态码和JSON错误信息包的形式报告失败情况。状态码显示请求失败的原因；错误信息包则详细说明具体问题所在（当失败由某个参数引起时，还需指出该参数）。

错误封装​

当请求失败时，会返回一个 error 对象。该对象中包含的字段取决于具体的失败原因。

{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds.",
    "charge": "ch_3Rsx4dDtWMrPDtgt1",
    "param": "",
    "doc_url": "https://stripe.com/docs/error-codes/card-declined",
    "request_log_url": "https://dashboard.stripe.com/test/logs/req_UQf6XBwBl9yk66"
  }
}
字段用途
type错误类别。决定错误处理的分支。
code发卡机构的错误说明（例如parameter_invalid_integer）
decline_code发卡机构给出的错误原因（例如 insufficient_funds）。
message引起失败的请求参数
param当失败是由于某个特定字段引起的时，指出问题出在该请求参数上。
charge当存在支付错误时，该字段表示错误的交易ID。
doc_url用于解释具体错误代码的页面。
request_log_url仪表板中的请求日志条目，显示完整的请求内容和响应结果。
备注

对每次失败的情况都应记录request_log_url信息；这有助于快速定位问题所在（即从支持工单到实际出错的请求之间的最短路径）。

错误类型​

共有四种type错误类型，适用于整个平台。

type错误含义重试操作建议
invalid_request_error参数缺失或格式不正确、相关对象不存在，或者访问权限不足。需修复请求数据。
card_error卡片发行方拒绝了此次支付请求，或需要验证卡片信息。处理方式取决于decline_code（相关设置）。
idempotency_error调用者使用了相同的密钥但参数不同。需使用新的密钥。
api_errorStripe无法处理有效的请求。可尝试多次请求（并设置延迟策略）。

状态码​

状态典型值 type原因重试次数
400invalid_request_error参数格式不正确、缺少必填字段，或参数组合不兼容。不支持重试
401invalid_request_error密钥缺失、已被撤销，或属于其他账户。不支持重试
402card_error发卡机构拒绝了该笔交易。是否可以重试取决于 decline_code 的结果
403invalid_request_error该密钥没有访问该资源的权限。不支持重试
404invalid_request_error在当前模式下，该对象不存在。不支持重试
409idempotency_error使用该键的请求仍在运行中。是的，只是暂时暂停了。
429rate_limit_error该键的请求频率超过了限制。是的，需要采取重试策略（backoff）。
500api_errorStripe 出现了意外错误。是的，需要采取重试策略（backoff）。
502api_error上游服务发生故障。是的，需要采取重试策略（backoff）。
503api_errorStripe 当前无法使用。是的，需要采取重试策略（backoff）。
504api_error请求在 Stripe 内部超时。是的，需要采取重试策略（backoff）。

拒付代码​

每个 card_error 对应一个 decline_code，这些代码用于指示重试是否可行。

decline_code代码含义是否可以重试应采取的行动
insufficient_funds账户余额不足可以，稍后再试让客户尝试使用其他银行卡或稍后处理。
expired_card卡片已过期不可以请客户提供新的卡片。
incorrect_cvc卡片的验证码（CVC）不匹配可以重试一次请客户再次提供验证码。
processing_error网络无法完成支付处理可以重试稍后再次尝试。
card_declined发卡机构拒绝支付且未给出具体原因不可以请客户选择其他支付方式。
authentication_required发卡机构要求使用 3D 安全验证需先完成身份验证运行安全验证流程后再确认支付。
lost_card, stolen_card发卡机构因客户报告而冻结了该卡片不可以不要重试，请将此情况上报给风险管理部门。
注意

重复尝试被拒绝的支付请求可能会导致更多拒付记录，从而提高账户的拒付率。仅对标记为“可以重试”的代码进行尝试，并在重试次数用尽后停止操作。

制定重试策略​

仅对那些在第二次尝试时有可能成功的请求进行重试（这些请求属于409、429以及5xx系列）。每次重试之间应采用指数级的时间间隔（backoff）和随机延迟（jitter）策略。同时，需限制重试的次数。

Node.js
// Retry only these status codes.
const RETRYABLE = new Set([409, 429, 500, 502, 503, 504]);

async function requestWithRetry(url, options, attempts = 4) {
  for (let attempt = 0; attempt < attempts; attempt++) {
    const response = await fetch(url, options);
    if (response.ok) return response;

    // Stop on a permanent failure, or when the budget runs out.
    if (!RETRYABLE.has(response.status) || attempt === attempts - 1) {
      return response;
    }

    // Wait 500 ms, then 1 s, then 2 s, plus jitter.
    const base = 2 ** attempt * 500;
    const delay = base + Math.random() * 250;
    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}

每次重试的等待时间分别为约0.5秒、1秒和2秒，并加上随机延迟。这样的调度方式可以在系统短暂中断后快速恢复，而不会对API造成过大的负担。

在每个POST请求中，都需要关联一个幂等性标识符。如果没有这个标识符，超时后的重试可能会导致同一笔交易被重复扣费。

重试前请先阅读响应​

请求头（429）中包含提示何时应再次尝试的信息；请务必阅读这些信息，而不是自行猜测。

请求头含义
Retry-After下一次尝试前需要等待的秒数。
Stripe-Rate-Limited-Reason哪个限制被触发了（例如 global-concurrency 或 endpoint-concurrency）。
  1. 首先阅读429中的错误信息，并根据提示采取相应措施；card_error类型的错误需要客户手动处理，而api_error类型的错误则需要重试。

诊断故障​

  1. 阅读type并根据其内容创建一个新的分支。card_error需要用户的操作；api_error则需要重试。
  2. 请阅读 param 以获取相关的 400 内容。需要修改的是被命名的字段，而不是整个请求数据。
  3. 阅读 request_log_url。确认 Stripe 是否已收到请求，并检查请求中的数据内容（payload）。
  4. 检查操作模式：对有效对象的 404 操作通常表示正在读取测试对象的数据。
  5. 检查所操作的键：403 表示在没有权限的情况下尝试访问受限键。

常见错误​

错误后果修复方法
重新尝试每个 4xx。复制失败的请求；浪费的配额。仅重新尝试 409、429 和 5xx。
修复了1秒的延迟机制；在系统故障后实现了同步重试功能；在所有延迟时间中加入了随机抖动（jitter）元素。
无密钥情况下的重试操作重复收费现象每次 POST 都发送 Idempotency-Key。
向客户展示message内容。造成混淆或泄露内部细节。将decline_code内容映射到您自己的副本中。
Ignoring request_log_url调试过程缓慢。将包含错误的链接记录下来。
