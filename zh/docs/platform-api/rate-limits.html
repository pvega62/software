速率限制与重试机制

速率限制是针对单个凭证设置的，而非整个连接；同一API密钥下的多个调用者会共享该密钥的访问权限；同一服务器上的两个不同密钥之间的访问请求互不影响。

429状态码的含义​

429 Too Many Requests
HTTP/1.1 429 Too Many Requests
content-type: application/problem+json
retry-after: 12
x-ratelimit-remaining: 0

{
  "type": "https://api.bludhavenpets.com/errors/rate-limited",
  "title": "Rate Limited",
  "status": 429,
  "detail": "The credential exceeded its window. Retry in 12 seconds.",
  "instance": "/animals"
}
头部字段含义
Retry-After下一次尝试前需要等待的秒数
X-RateLimit-Remaining当前时间窗口内剩余的请求数量（此处显示为0）

Retry-After | 这是服务器直接返回的值；应严格遵循该延迟时间，避免自行猜测，因为错误的延迟可能导致资源浪费或错过资源补充时机。

公开的访问配额信息​

凭证类型时间窗口每分钟允许的请求数量
收银机操作键当前分钟数300
服务器作业密钥每分钟更新一次持续120分钟
合作伙伴访问令牌每分钟更新一次持续120分钟
采用者会话令牌每分钟更新一次持续60分钟

错误代码“429”具有权威性；请将此表格视为规划指南，将表头内容视为实际数据。

为什么某些系统会达到使用限制​

在繁忙的周六，每次销售后同步库存的系统会耗尽其允许的请求次数；通过以下三个习惯可以避免这种情况：

  • 有效的重试策略​

  • 首先读取GET /retail/inventory的数据，等待相应时间后添加一个随机偏移量，以防止多个系统在同一秒内重复尝试请求。
  • 两个循环都会返回错误代码“429”；如果调用者已用完请求次数，系统应记录此次失败。

一种有效的回退策略​

阅读 Retry-After 中的指令，等待相应的时间；同时添加一个随机的偏移量，以防止多个系统在同一时刻尝试执行相同的操作。

Node.js
async function callWithRetry(request, { attempts = 4 } = {}) {
  for (let attempt = 1; attempt <= attempts; attempt += 1) {
    const response = await request();
    if (response.status !== 429) return response;

    const retryAfter = Number(response.headers.get('retry-after') ?? attempt * 2);
    const jitter = Math.floor(Math.random() * 500);
    await new Promise((resolve) => setTimeout(resolve, retryAfter * 1000 + jitter));

    if (attempt === attempts) return response;
  }
}
Python
import random
import time

import requests


def call_with_retry(request, attempts=4):
    for attempt in range(1, attempts + 1):
        response = request()
        if response.status_code != 429:
            return response
        retry_after = int(response.headers.get("Retry-After", attempt * 2))
        time.sleep(retry_after + random.uniform(0, 0.5))
    return response

这两个循环都会返回结果 429，而不会引发异常（即不会抛出错误）。如果调用者的预算已经用完，那么程序应该记录下这个失败情况。

重试写入操作​

当收到 429 错误时，说明平台在请求执行前就拒绝了该请求。对于 GET、PUT 和 DELETE 来说，重试是安全的。

对于 POST 来说，必须先发送 Idempotency-Key 请求；否则重试会重复原始的写入操作。对于 POST /refunds 来说，需要预先设置相应的请求头信息；出于同样的原因，这些请求头信息也需要在其他写入操作中一并发送。

沙箱环境的作用​

沙箱网关不限制请求次数（即不设置请求配额），它会响应所有的请求，因此用户可以无需关注请求计数器即可查看控制台信息。429 的响应数据存储在合约中，生产环境网关会直接返回这些数据。

如果沙箱环境对请求进行限流处理，那么它就无法正确展示“退避策略”（backoff strategy）的效果；因此这两个网关的设计目的是有区别的。
