参考文档中的测试请求

“Scalar”参考文档会发送实时请求。沙箱网关位于服务器列表的首位，发送到该网关的请求会通过真实网络传输；也可以选择“浏览器演示”模式，此时响应会直接在页面上显示，无需登录或启动本地进程。

浏览器演示的工作原理​

公布的示例合同列出了三个目标地址。其中之一（/software/api-mock）指向您当前所在的页面。参考页面中的请求处理程序会根据合同提供的模式示例生成响应内容来处理对该路径的请求。

这种设计同时解决了三个问题：

  • 禁止混合内容：通过 HTTPS 加载的页面无法调用 http://localhost。使用同源策略可以避免浏览器拒绝该请求。

  • 发送您的第一个请求​

  • 无需维护任何服务器。 GitHub Pages 用于提供静态文件，而静态网站托管服务本身无法运行模拟服务器；相关处理逻辑是在访问者的浏览器中执行的。
响应来自契约

每个数据体（body）都是根据规范示例生成的。字段名称（field names）、枚举值（enums）、微芯片的编码格式（microchip pattern），以及 RFC 9457 中定义的数据结构（shapes）都严格符合相关规范。选择“production”或“sandbox”模式时，实际操作会针对真实的服务器或测试环境进行。

发送您的第一个请求​

  1. 打开交互式API参考文档。
  2. 确认服务器下拉菜单显示的选项为“Sandbox gateway”；该接口无需任何凭证即可使用。
  3. 展开GET /animals/{animalId}，输入pet_krypto_210作为路径值，然后点击“Send”（发送）。

响应结果会返回包含动物微芯片信息（985141002348123）、狂犬病疫苗接种标签信息（RB-2026-9921）以及状态信息（AVAILABLE）的记录。

哪些接口需要凭证？​

收养信息目录以及用于接收测试Webhook请求的接口是公开可用的：潜在收养者在创建账户前可以浏览该目录，接收方进行测试时也不需要凭证。其余接口则需要满足安全要求：

接口名称安全要求
GET /animals无。公开目录。
GET /animals/{animalId}无。公开动物信息页面。
POST /applicants无。注册功能用于创建新账户。
POST /sessions无。登录操作会生成访问令牌。
POST /webhooks/test-dispatch无。接收方进行测试时无需凭证。
其他所有内容在接受密钥的路由中，使用 OAuth 2.0 承载令牌（bearer token），或表示为 X-API-Key。

浏览器演示版 不会验证这些认证要求，因此所有请求都会被无条件处理；而沙箱环境（sandbox）会进行验证，这可能导致某些请求在沙箱中失败，但在演示版中却能正常通过。

请求认证​

该系统定义了一个真实的授权服务器；因此当使用 bludhaven_oauth 时，会显示一个“Connect”按钮而非输入框。点击“Connect”后，系统会在沙箱环境中展示同意页面。

控制台操作执行动作设置请求头（Header）
bludhaven_oauth连接目标设备，完成审批流程后发送数据Authorization: Bearer <token>
api_keyPaste bpk_sandbox_pos_7f3a91c4X-API-Key: <key>

这些规则适用于常规路由；如果需要处理动物相关的数据，请直接粘贴 bpk_sandbox_ops_2d8be05f。认证指南 中列出了每个密钥的具体用途。

在命令行环境下，系统会跳过同意页面并直接发送请求头。

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

如果某个安全路由缺少请求头，系统会返回 401 Unauthorized，同时附带 ProblemDetails 数据和 WWW-Authenticate 挑战信息；伪造的密钥也会导致请求失败（因为沙箱环境会检查密钥的有效性）。

值得尝试的操作流程​

阅读动物记录​

发送 GET /animals/pet_krypto_210。响应会返回包含嵌套健康记录以及 $150 放置费用的 Animal 数据结构。请将路径值替换为 pet_krypto_999，此时处理程序仍会作出响应（因为该请求符合路由模板，而非存储在数据库中的记录）。

尝试执行冲突性的“暂留”操作。​

将 animal_id 设置为 pet_krypto_210 并包含任何 applicant_id，然后发送 POST /adoptions/holds。第一次调用会返回 201 Created，附带新的等待编号、30分钟的 expires_at 以及 seconds_remaining 倒计时。再次发送相同的 animal_id，处理程序会返回 409 Conflict，并包含指出阻碍您等待的 ProblemDetails 信息。

从第一次响应中复制暂留 ID，然后发送 GET /adoptions/holds/{holdId} 以查看倒计时信息，或发送 DELETE /adoptions/holds/{holdId} 以释放动物。释放操作会解除锁定状态，从而允许下一次暂留请求成功；锁定状态仅在当前页面会话期间有效，重新加载页面后会被重置。

该流程展示了客户端如何读取来自冲突情况的 type、title 和 detail 数据，并向领养者提供等待列表（而非直接显示操作失败的信息）。

记录退款信息。​

将 POST /refunds 发送出去，并将 application_id 设置为 app_2026_1188，将 amount_cents 设置为 10000，将 reason 设置为 CANCELLATION_AFTER_48H。处理程序会返回安置费用以及被分开的物资清单（存储在 breakdown 中），同时还会说明它所扣留的押金和许可费用的具体金额。对账工作就是按照这样的格式进行的。

请求执行合同未规定的操作。​

发送 GET /animals/pet_krypto_210/notes。没有与该路径匹配的操作，因此处理程序返回包含 ProblemDetails 内容的 404。该响应触发了客户端所需的错误处理流程。

调用沙箱网关。​

沙箱网关 会为所有请求提供相同的响应内容；该网关通过非浏览器方式处理所有操作请求。

curl https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210

安全路由需要经过沙箱网关签名的令牌或网关能够识别的密钥；密钥路径仅接收一个请求头信息，无需任何数据交换。

curl https://sandbox.bludhaven-pets.workers.dev/retail/inventory \
  -H "X-API-Key: bpk_sandbox_pos_7f3a91c4"

令牌路径以 “mint” 开头。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=bludhaven-staff-portal" \
  -d "scope=write:animals"

从响应中复制 access_token 并将其用于下一次调用。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Orion", "species": "dog", "microchip_id": "985141002348999", "intake_branch_id": "loc_harbor_04"}'

删除该头部信息后，相同的调用会返回包含 401、ProblemDetails 和 WWW-Authenticate 的响应内容；可以发送任意类型的伪造数据，网关会以相同方式进行处理（验证签名或查找密钥）。如果发送缺少 write:animals 的真实凭证，调用会返回包含 403 和 insufficient_scope 的响应。

认证指南 中介绍了同意界面、已发布的两个密钥以及十个权限范围（scopes）。

这些功能的行为与控制台中的相同：先发送两次 POST /adoptions/holds，再发送一次 animal_id，第二次调用会返回一个表示“正在等待中”的状态码 409。接着可以使用 GET /adoptions/holds/{holdId} 查看倒计时信息，或者使用 DELETE /adoptions/holds/{holdId} 释放被等待的动物。

GET /health 会报告网关加载的合约信息、操作次数、实时持有资源的数量、OAuth 端点以及发布的密钥数量；在部署后运行该命令以确认网关已成功接入网络。

测试直接上传到存储的功能：生成一个已签名的上传 URL，然后将二进制数据直接传输到存储系统（无需通过应用程序 API）。​

生成一个经过签名的上传 URL，直接将二进制文件传输到存储系统，无需通过应用程序 API 中间处理。

# 1. Request presigned upload URL (needs write:animals scope)
curl -X POST https://sandbox.bludhaven-pets.workers.dev/animals/pet_krypto_210/photos \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"content_type": "image/jpeg", "caption": "Krypto in harbor yard"}'

如果签名被篡改或已过期，系统会返回 upload_url；成功的上传操作会返回包含经过验证的 SHA-256 校验和及公共 CDN URL 的 PUT。

# 2. PUT binary file directly to storage endpoint
curl -X PUT "<UPLOAD_URL>" \
  -H "Content-Type: image/jpeg" \
  --data-binary "@photo.jpg"

如果签名被篡改或过期，系统会返回错误响应（403）；成功上传后，系统会返回包含验证后的 SHA-256 校验和及公共 CDN URL 的响应（200）。

测试模拟的 Webhook 发送功能​

向本地接收方发送一个已签名的 Webhook 事件，以验证您的 HMAC 接收器是否正常工作。

curl -X POST https://sandbox.bludhaven-pets.workers.dev/webhooks/test-dispatch \
  -H "Content-Type: application/json" \
  -o webhook-dispatch.json

网关会对其生成的完整数据包（payload）进行签名处理，并将响应结果写入到 webhook-dispatch.json。请使用 node scripts/verify-webhook.mjs webhook-dispatch.json 进行验证。Webhooks 使用指南 中介绍了在 Node.js 和 Python 中实现签名功能的步骤。

参考控制台也会在 Webhooks 部分列出相关调用信息。请针对 浏览器演示版 发送请求；响应中的头部信息可以用来验证签名是否正确（因为演示版会在请求时自动进行签名操作）。

保留可能会重置

该网关运行在临时创建的边缘隔离环境中（即这些隔离环境仅用于短暂使用）。被回收的隔离环境会丢失其创建的所有“hold”状态；因此，某个“hold”标识可能会在刚刚失效后立刻再次变为“404”状态。在这种情况下，应重新创建一个新的“hold”，而不要将“404”视为已被释放的资源。
