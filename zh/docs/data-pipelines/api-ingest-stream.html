使用 Datadog 日志摄取 API 收集事件数据

该接口支持高吞吐量、实时的结构化及半结构化数据摄取。

该 API 支持的操作： 半结构化的JSON数据负载（semi-structured JSON payloads）。

开始使用前，请确保具备以下条件：​

  • 可以直接从云应用程序中发送日志，无需安装 Datadog 代理程序。
  • 对传入的数据应用管道处理程序（pipeline processors），例如 Grok 解析器（Grok Parser）、重映射器（Remapper）和查找处理程序（Lookup Processor）。
  • 根据日志内容，将日志路由到相应的索引、归档目录或警报系统。
  • 通过将此端点与采样和过滤规则结合使用，降低索引成本。
备注

请参阅Datadog API和应用程序密钥以管理凭据。

在开始之前​

请确保您已准备好以下内容：

  • 一个具有日志采集权限的 Datadog API密钥。可以在 组织设置（Organization Settings）→ API密钥（API Keys）中找到该密钥。
  • 您的 Datadog 网站地址。该地址因地区而异：
地区网站地址
东海岸（US East）datadoghq.com
US3 Westus3.datadoghq.com
US5 中部地区us5.datadoghq.com
欧盟datadoghq.eu
AP1 Japanap1.datadoghq.com
AP2 澳大利亚ap2.datadoghq.com
  • curl 或者已经安装了 Postman。
  • 0格式化的日志数据（log payloads）。

数据采集端点​

POST https://http-intake.logs.{dd_site}/api/v2/logs

将 {dd_site} 替换为您的地区站点地址（例如 datadoghq.com 或 ap2.datadoghq.com）。

请求头​

头部字段值是否必填说明
DD-API-KEY<your_api_key>是您的 Datadog API 密钥
Content-Typeapplication/json是数据格式
Content-Encodinggzip可选压缩后的数据格式（Datadog 鼓励在处理大量数据时使用此格式）。

请求体​

请求体是一个包含一个或多个日志对象的数组。每个日志对象包含以下字段：

字段类型是否必填说明
message字符串是日志内容本身
ddsource字符串推荐日志来源技术的名称（例如 python 或 nginx）
ddtags字符串可选用逗号分隔的标签（例如 env:prod,team:payments）
hostname字符串可选生成日志的主机名称
service字符串推荐应用或服务的名称
status字符串推荐日志事件的严重程度（例如 info 或 ERROR）
timestamp字符串可选事件时间，例如 2025-11-15T08:30:00Z。请参阅时间戳格式说明。
备注

请务必包含 message；Datadog 使用 service、ddsource 和 ddtags 来过滤、分类和匹配日志数据。其他字段为可选。

示例数据格式​

Payload: single log
[
  {
    "message": "Transaction failed: Gateway timeout",
    "ddsource": "java",
    "ddtags": "env:prod,region:us-east-1",
    "hostname": "payments-host-01",
    "service": "payment-gateway",
    "status": "ERROR",
    "timestamp": "2025-11-15T08:30:00Z",
    "transaction_id": "txn_998877",
    "customer_id": "cus_554433"
  }
]
备注

使用国际标准化组织（ISO）8601协调世界时（UTC）格式来表示时间戳（timestamp）。Datadog会根据这个时间戳来对日志时间线进行对齐；没有时间戳的日志将使用数据摄入时间。Datadog接受最多18小时之前的时间戳。

cURL 示例​

cURL
export DD_API_KEY="your_datadog_api_key_here"
export DD_SITE="datadoghq.com"

curl -X POST "https://http-intake.logs.$DD_SITE/api/v2/logs" \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "message": "Transaction failed: Gateway timeout",
      "ddsource": "java",
      "ddtags": "env:prod,region:us-east-1",
      "hostname": "payments-host-01",
      "service": "payment-gateway",
      "status": "ERROR",
      "transaction_id": "txn_998877"
    }
  ]'

响应代码​

代码状态描述
202请求成功数据已接收并进入索引处理流程
400请求错误格式或验证失败
401未经授权缺少必要的请求头信息（DD-API-KEY）
403被禁止访问API密钥无效或缺乏日志上传权限
408请求超时请稍后再试。
413数据过大数据体积超过5MB（未压缩状态）
429请求次数过多客户端超出请求频率限制
500服务器内部错误Datadog遇到异常情况，请稍后再试。
503服务暂时不可用Datadog正在满负荷运行，请稍后再试。

共有 202 条内容被接受。​

当收到数据后，Datadog会返回202 Accepted响应，响应体中包含一个空的JSON对象。日志事件将在几秒钟内显示在日志浏览器中。

Response: 202 Accepted
HTTP/1.1 202 Accepted
Content-Type: application/json
Response body: 202 Accepted
{}

400 错误请求（表示客户端发送的请求格式不正确或无法被服务器理解）​

当数据格式验证失败时，Datadog会返回 400 错误代码：

  • 使用了错误的 JSON 语法，或者未对某些字符进行转义处理。
  • 该数据包缺少必需的 message 字段。
  • 未压缩的数据量超过了 5 MB 的限制。
Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Invalid JSON",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

当数据体积超过5MB（未压缩状态）时，Datadog会返回 429“请求过多”错误。​

如果缺少DD-API-KEY头部信息，Datadog会返回401 Unauthorized；如果API密钥验证失败或没有日志摄入权限，也会返回401 Unauthorized。

Response: 403 Forbidden
{
  "errors": [
    {
      "detail": "Forbidden",
      "status": "403",
      "title": "Forbidden"
    }
  ]
}

413 载荷过大​

当请求的数据量（未压缩）超过 5 MB 时，Datadog 会返回此代码。

Response: 413 Payload Too Large
{
  "errors": [
    {
      "detail": "Payload too large",
      "status": "413",
      "title": "Payload Too Large"
    }
  ]
}

429 请求过多​

您发送的请求太多了。请减少请求数量，或者将多个日志对象合并到一个数组中作为数据包发送。

其他可重试的错误​

当系统出现短暂性故障时，Datadog 也会返回 408 Request Timeout、500 Internal Server Error 和 503 Service Unavailable 等错误信息。此时应使用指数级退避策略重试请求；如果问题持续存在（即 408 Request Timeout 状态仍未改变），则应分批发送请求数据。

常见使用场景​

  • 在不部署 Datadog Agent 的情况下，从微服务中收集日志数据。
  • 从无服务器函数（如 Amazon Web Services (AWS) Lambda 或 Google Cloud Run）发送结构化的 JSON 事件。
  • 来自物联网设备或边缘服务的实时数据流（streaming telemetry data）。
  • 将相关事件路由到安全信息管理系统、事件管理工具（SIEM）、S3 存储服务，或通过日志管道（Log Pipelines）发送警报。
  • 从持续集成（CI）和持续交付（CD）流程或部署脚本中提交日志。

故障排除​

问题可能原因解决方案
401 UnauthorizedAPI密钥错误或缺失请在组织设置→API密钥中验证DD_API_KEY。
400 Bad Request数据格式错误（JSON）发送前请先与jq . payload.json确认。
不要通过 Explorer 登录。使用管道过滤器（pipeline filter）排除日志数据。清除所有过滤器，然后检查索引路由规则（index routing rules）。
时间戳顺序错误。日志格式不符合 UTC 或 ISO 8601 标准，或者记录时间早于事件发生 18 小时前。请使用 "2025-11-15T08:30:00Z" 格式来标记时间戳。请在事件发生后的 18 小时内发送日志。
429 Too Many Requests超过速率限制将多个日志对象合并到一个数组中作为数据传输内容
