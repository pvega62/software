创建一个 Postman 模拟服务器

使用提供的 Postman 示例文件在本地模拟 Datadog 的日志导入 API。检查请求格式和错误响应，并运行相关示例，而无需将数据发送到真实的 Datadog 账户。

先决条件​

  • Postman（桌面版或网页版）。
  • 本项目附带的 JSON 文件。开始之前请下载所有文件：
文件用途
DataPipeline-Environment.json定义了可重用的变量：dd_site、mock_base_url 和 dd_api_key。
DataPipeline-postman-collection.json向 Datadog 日志采集 API（/api/v2/logs）发送真实请求。
DataPipeline-MockServer-Collection.json使用 Postman 模拟服务器为相同的端点配置模拟响应。
请在 GitHub 上的软件仓库 中浏览这些文件。

1. 将文件导入 Postman​

  1. 打开 Postman，然后选择 导入。
  2. 一次性选中这三个已下载的 JSON 文件。
  3. 在工具栏的环境选择器中，选择 数据管道环境。 导入完成后，Postman 列出了三项内容：
  • 数据管道文档项目 负责发送实时请求。
  • 数据管道模拟服务器集合 定义了已保存的模拟响应。
  • 数据管道环境 提供这两个集合共用的变量。

2. 创建模拟服务器​

  1. 在 Postman 侧边栏中，打开“添加”菜单，然后选择 模拟服务器。
  2. 选择 现有收藏集。
  3. 在 集合 下，选择 数据管道模拟服务器集合。在 环境 下，选择 数据管道环境。
  4. 选择 部署。
  5. 从工作台复制模拟服务器的地址。 Postman 会为模拟服务器生成一个唯一的地址，例如： https://a12b34cd-1234-5678.mock.pstmn.io

3. 更新环境变量​

  1. 转到 环境，然后打开 数据管道环境。
  2. 找到 mock_base_url 变量。
  3. 请将占位符替换为您复制的地址：
mock_base_url
# Before
https://mock-server-url-from-postman.io

# After
https://a12b34cd-1234-5678.mock.pstmn.io

  1. 选择 “保存” 以保留更改。

  2. 在 数据管道模拟服务器集合 中打开 POST /api/v2/logs。

  3. 请确认环境选择器显示为 数据管道环境。

  4. 选择“发送”。

模拟服务器会返回一个模拟的 202 Accepted 响应，并重新播放之前保存的示例数据内容。

4. 发送您的第一个模拟请求​

Response: 202 Accepted
{
  "status": "accepted",
  "message": "Log event received by mock server."
}

真实的 Datadog 日志采集 API 会返回 202 Accepted 状态码，并附带一个空的 JSON 对象（{}）。模拟实现会返回一个可读的对象，以便您确认模拟服务器已收到该请求。

如果事件缺少必填的 message 字段，Datadog 会拒绝该事件。要重现这种拒绝情况，请从请求正文中删除 message 字段，然后再次点击 发送。Postman 会将请求正文与每个已保存的示例进行比对，并返回 400 示例：

5. 测试错误响应​

Response: 400 Bad Request
{
  "errors": [
    {
      "detail": "Malformed payload: the 'message' field is required",
      "status": "400",
      "title": "Bad Request"
    }
  ]
}

若要无论请求正文内容如何都返回特定的响应，请添加一个 x-mock-response-code 头，并设置为所需的状态码，例如 400。

模拟服务器会重放之前保存的请求数据，且不会验证用户的凭据；因此它不会返回任何响应（即没有 401 类型的响应）。要测试缺少 API 密钥的情况，请删除 DD-API-KEY 标头，然后从 Data Pipeline Documentation Project 中发送请求 POST /api/v2/logs。登录处理 API 页面会列出每种错误代码对应的响应内容。

6. 在实时测试和模拟测试之间切换​

这两个集合都使用同一个环境配置文件。要在真实环境和模拟环境之间切换，只需更改该文件即可。 测试：可以更换所使用的集合（collection）。

目标数据集合基本地址变量
使用真实的 Datadog 进行测试DataPipeline-postman-collection.json{{dd_site}} → datadoghq.com
在本地或离线环境中进行测试DataPipeline-MockServer-Collection.json{{mock_base_url}} → 使用您的模拟地址（your mock address）

在发送实时请求之前，请将 dd_api_key 设置到环境中。这种方法会在您将数据发送到 Datadog 账户之前，验证请求和响应的格式。

在正式上线流量之前进行验证​

这个模拟服务器的设置演示了您在开发或记录真实API集成时所使用的相同验证流程：

  • 确认Content-Type中的数据负载是否符合预期的格式：一个包含多个日志对象的数组，每个对象都包含一个DD-API-KEY字段。
  • 确认 JSON 有效载荷 与预期模式一致：一个由日志对象组成的数组，每个对象都包含一个 message 字段。
  • 测试错误处理机制（400, 401, 429），同时确保不消耗 API 配额，也不污染生产环境的日志索引。
  • 针对一个稳定且可复现的端点，开发和验证文档示例。

在记录 Galileo软件开发工具包（SDK） 的文档时，同样需要遵循这一模式。您需要对经过性能监控和调试的代码进行测试。 在将函数从dev日志流中提取并提升到production之前，确保对其进行相应的配置（即进行评估或处理）。 在真实用户流量开始流动之前，必须先正确设置各项指标（metrics）。
