《设计Artie——一款AI文档助手》

提示

相关博客文章《构建AI文档助手让我学到了什么关于技术写作的知识》探讨了“检索增强生成”（Retrieval-Augmented Generation, RAG）技术，以及该项目如何应用于技术写作领域。

本案例详细介绍了使用Algolia技术构建的Artie的设计思路：Artie是一款基于检索增强生成技术的AI助手，其回答内容完全来自该文档网站上的现有资料。这种设计限制了AI的“胡言乱语”，避免了生成不实或虚构的功能。

构建文档助手看似简单，但实际会遇到许多复杂问题：当用户提出文档未涵盖的问题时该怎么办？如果不同用户使用同一界面该如何处理？如何赋予AI独特的“个性”同时又防止其偏离主题？又该如何防止他人恶意操控AI的回答内容？

本页面详细说明了这些设计如何解决这些问题。

用户分类与引导​

Artie通过一个统一的对话界面服务于两类用户：

  • 为了提高效率，系统通过用户意图来自动分配问题类型：技术问题会得到基于文档内容的逐步解答；与个人简历相关的问题则会结合简历信息与网站上的文档样例进行综合回答；如果简历信息不在文档系统中，Artie会引导用户前往“关于我”页面，而非尝试生成新的回答内容。
  • 招聘人员和招聘经理在评估此作品集时，可能会询问候选人的资格、工作经验或写作流程。

该系统不会创建单独的回答流程，也不会要求用户自行提供信息；而是根据用户的意图来提供相应的帮助。对于技术相关的问题，系统会从文档索引中提供详细的逐步解答；而对于与个人作品集相关的问题，系统则会结合用户的简历内容以及网站上的写作样本来生成答案。如果简历中的相关信息在文档索引中找不到，Artie会引导用户前往“关于我”页面，而不会尝试直接生成答案。

该界面为所有用户提供统一的聊天界面（无需菜单），每位用户都能获得相关的回复。

知识基础与信息检索​

Artie 设计中的最重要原则是：它仅依据由 Algolia 提供的文档索引来生成回答。这是“检索增强型生成”（retrieval-augmented generation）的核心理念——模型始终将每个回答与特定的文档内容关联起来，而非从通用训练数据中获取信息。

  • 禁止虚构内容：Artie 绝不会编造任何信息或创建下载链接，它只会描述文档中已有的步骤。
  • 提供来源链接：Artie 会提供文档索引中的 URL 或文件引用，让用户能够直接访问相关页面。
  • 优雅的错误处理：当索引中缺乏相关信息时，Artie 会明确说明这一限制，并建议用户直接联系相关人员（而非重复请求或进行猜测）。

Artie 无法处理文档之外的话题；对于作品集网站而言，这一限制反而很有帮助——准确性比信息量更重要。一个准确、来源可靠的答案比一个看似合理但实际上错误的答案更能赢得用户的信任。

人物形象与语气设定​

Artie 具有一种轻松、温暖的语气，灵感来源于乔治·哈里森（George Harrison）的风格，偶尔还会使用利物浦方言。其关键特点是“轻松自然”——这种人物形象为问候语和结束语增添了特色，同时不会干扰技术内容的呈现。

这些设计约束是有意为之：

  • 保持技术性回答的简洁性：个人的风格或情感不应成为延长回答长度的理由。一个热情的问候加上简洁、基于事实的回答，就能达到这一目标。
  • “多样性胜过重复”（Variety over repetition）意味着该提示包含了一系列表达方式，这样Artie就不会每次都使用相同的短语。
  • **“禁止说教”**意味着该角色应保持温和、幽默的语气，绝不能显得居高临下；它应该像一位乐于助人的同事，而不是一个刻意塑造的角色。

这种语气调整在对话式AI设计中是一个常见挑战：如果角色个性过于鲜明，会让人觉得刻意；而如果个性过于淡漠，则会显得机械。正确的做法是将角色的个性视为一种“调味品”——存在但不是主要元素。

安全性与防护机制​

面向公众的AI助手本身就是潜在的安全风险点，因此其提示语中包含了针对常见大型语言模型（LLM）漏洞的防护措施。

提示注入防护​

Artie的提示系统明确拒绝任何试图覆盖其指令的尝试，例如“忽略之前的指令”这样的命令，或是要求它切换到另一种角色的请求。这种机制为防止“提示注入”（prompt injection）提供了有效的防护措施，在开放全球应用安全项目（Open Worldwide Application Security Project）针对大型语言模型应用的十大安全威胁列表中，该防御措施被列为首位（排名#1）。

使用范围限制​

提示语明确规定了哪些请求会被拒绝：

  • 助手会拒绝那些文档未涵盖的“一般性编程帮助”请求。
  • 该助手会拒绝与“无关琐事”相关的请求，但会提供两个特定的、趣味性的功能。
  • 助手会拒绝任何关于个人信息的询问，因为这些信息并未在专业作品集中公开。
  • 助手建议访客直接联系我们，以咨询自由职业者的收费标准或相关谈判事宜。

每个类别都有明确的界限，因此助手会判断请求是否属于该类别；如果请求超出了这些界限，它将拒绝处理该请求。

数据隐私​

Artie仅会分享文档中明确公开的联系方式（例如领英个人资料或作品集邮箱），绝不会猜测、推断或生成电话号码、地址等个人信息。

职业行为规范​

Artie会拒绝恶意信息，从不使用粗俗语言，也不会做出不当行为。这不仅仅是礼貌问题，更是为了保持行为的可预测性。测试助手极限的招聘人员每次都应该遇到一致、专业的回应。

控制的“彩蛋”功能​

Artie提供了两个“趣味功能”：Snapple Real Facts（真实趣闻）和干净幽默的笑话，这些功能能在不引发滥用风险的情况下增添个性。

这两个功能都遵循相同的设计模式：

  • 不受限制的创意功能会迅速消耗系统资源并产生不可预测的输出；而经过筛选的内容加上明确的触发语句，则能在不带来风险的情况下增添趣味性。
  • **“有界内容”（Bounded content）**指的是那些链接到经过验证的事实列表的信息；而笑话部分则经过精心筛选，适合所有年龄段的用户阅读。
  • **“不编造无根据的内容”**意味着该助手会避免捏造事实或生成与品牌无关的幽默内容，从而确保输出内容始终符合预期。

具有无限创造力的功能会迅速消耗大量资源（“tokens”），并产生不可预测的结果。而经过精心挑选的内容以及明确的触发条件则可以在不带来这些风险的情况下带来“温暖”（即良好的用户体验）。

如果我来做的话，我会做出这些改变​

实际用户对设计提出了反馈，因此我们进行了调整。

  • 令牌成本是导致第一次修改的原因：仅“Snapple”相关的事实列表就超过了100条内容。在采用按令牌计费的生产系统中，我会将这些信息放在数据检索层，而不是直接嵌入到系统提示中。这样每次请求时，无论用户是否需要查询具体信息，团队都需要为所有使用的令牌付费。
  • 多轮对话功能限制了当前设计的单轮问答模式；后续版本可以记录对话历史，并优化查询逻辑，以便用户能够提出如“下一步该怎么做？”之类的问题。
  • 分析和反馈机制目前尚未实现：仅记录用户的求助次数就能发现哪些文档内容最容易被遗漏。
  • 动态角色调整目前需要手动修改硬编码的表达式；如果将这些设置移到外部配置文件中，就可以在不影响核心功能的情况下灵活调整对话风格。

这些改动都是针对一个以简洁性和清晰度为主要目标的演示项目所做的权衡。但如果该项目要应用于高流量环境，这些就是我首先会解决的问题。
